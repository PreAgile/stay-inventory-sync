# 진짜 병목은 어디인가

## 결론부터

**내부 처리량이 아니라 외부 채널 API의 레이트 리밋이다.**

이 판단이 아키텍처 결정 전체를 좌우한다.
내부가 병목이면 스케일아웃과 캐싱을 논해야 하지만,
외부 리밋이 병목이면 **배치와 스로틀링**이 답이 된다.

---

## 근거: Channex 공개 스펙

채널매니저 Channex의 공개 문서 기준으로,

| 항목 | 제약 |
|---|---|
| ARI 총량 | 프로퍼티당 분당 20**회** |
| 가용성(availability) 요청 | 프로퍼티당 분당 10회 |
| 제약·가격(restrictions·price) 요청 | 프로퍼티당 분당 10회 |
| 초과 시 | 지수 백오프 **요구**. 429 를 받으면 최소 1분 중지 후 재시도 |
| 권장 전송 방식 | 변경분을 모아 6초 간격 1회 호출로 배치 |
| 전체 동기화 | 24시간에 1회, 오프피크 시간에만 |
| 웹훅 재시도 | 5XX 시 최대 10회, 1분→2분→4분→8분→15분→30분→1시간→2시간→4시간→6시간→10시간 |

**분당 20은 총량이고 가용성만 보면 10이다.** 그리고 이 10은 변경 건수가 아니라
**요청 횟수**다. 공개 문서는 100일치 변경을 1건씩 100번 보내지 말고 100개를 담은
1건으로 보내라고 권고한다. 즉 배치가 있으면 변경 건수는 리밋에 직접 부딪히지 않는다.

## 산정

26개 지점 규모를 가정한다.

```
지점당 룸타입 평균 5종
변경 이벤트: 예약 1건당 (체크아웃-체크인) 일수만큼의 날짜 재고 변경
평균 숙박 2박 → 예약 1건 = 재고 변경 2건

성수기 주말 지점당 시간당 예약 30건 가정
→ 지점당 분당 재고 변경 = 30 * 2 / 60 = 1건

여유가 있어 보이지만, 문제는 평균이 아니라 버스트다.
프로모션 오픈, 대량 취소, 요금 일괄 변경 시
지점당 수백 건의 변경이 초 단위로 몰린다.
→ 개별 전송이면 분당 10회 리밋을 즉시 초과한다.
```

**따라서 개별 변경을 즉시 전송하는 설계는 성립하지 않는다.**

거꾸로 말하면, **레이트 리밋은 처리량의 상한이 아니라 배치를 강제하는 제약이다.**

### 다만 배치가 429 를 없애 주지는 않는다

6초 간격은 공개 문서가 제시하는 **배치·스로틀링 기준이지 429 미발생 조건이 아니다.**
버스트 안전이 성립하려면 셋이 더 있어야 한다.

| 필요한 것 | 없으면 |
|---|---|
| 프로퍼티 단위 레이트 리미터 | 여러 경로가 동시에 보내는 것을 6초 간격만으로는 막지 못한다 |
| 동시 실행 제어 | 릴레이 인스턴스가 둘이면 실효 간격이 절반이 된다 |
| 재시도 조정 | 백오프 중인 요청이 정상 배치와 겹치면 순간 초과한다 |

**즉 6초는 필요조건이고 충분조건이 아니다.** 셋 중 어느 것도 아직 구현되어 있지 않으므로,
현재 상태에서 말할 수 있는 것은 **"개별 전송은 확실히 성립하지 않는다"** 까지다.
토큰버킷 스로틀러(`#15`)가 첫 번째 항목이고, 나머지 둘은 릴레이 구현(`#4`·`#8`)에 딸린다.
그리고 배치가 강제되면 동일 키 병합이 필요해지고, 병합이 순서 문제를 만든다 —
아래 "순서는 인스턴스 수의 문제가 아니다"로 이어지는 인과가 이것이다.

## 설계 귀결

Outbox 릴레이는 단순 폴링-전송 루프가 될 수 없다.

```
필요한 것:
1. 프로퍼티 단위 배치 윈도우 (6초)
2. 동일 (room_type_id, stay_date)에 대한 변경 병합 — 마지막 값만 전송
3. 채널별 토큰버킷 스로틀러
4. 429 / 5xx에 대한 지수 백오프
5. 백오프 중에도 순서가 뒤집히지 않는 보장
```

### 이번 범위에서 구현한 것

- **1번(배치 윈도우)까지.** 릴레이가 프로퍼티 단위로 PENDING 이벤트를 모아 전송한다.
- **4번(백오프).** `next_attempt_at`과 `retry_count` 컬럼으로 처리.
  재시도 간격은 Channex의 실제 스케줄(1/2/4/8/15/30분)을 따랐다 — 임의 설정이 아니다.

### 남긴 것

- **2번(변경 병합)**: 배치 내 동일 키 병합. Tier 2 백로그.
- **3번(토큰버킷)**: 채널별 리밋이 실제로 달라야 의미가 있다. 스텁 환경에서는 검증 가치가 낮다.
- **5번(순서 보장)**: **미해결. 단일 인스턴스에서도 이미 깨져 있다.**
  아래 "순서는 인스턴스 수의 문제가 아니다" 참고. Tier 2 백로그(B4)로 넘긴다.

---

## 순서는 인스턴스 수의 문제가 아니다

4번(백오프)을 구현한 순간 5번(순서 보장)이 깨진다.
릴레이가 하나뿐이어도 그렇다.

```
t1  (룸타입A, 3/15) 예약 → 잔여 3→2   이벤트 #1 생성
    #1 발행 실패 → next_attempt_at = +1분

t2  (룸타입A, 3/15) 취소 → 잔여 2→3   이벤트 #2 생성
    #2 즉시 발행 성공 → 채널 잔여 3   ✓

t3  #1 재시도 성공 → 채널 잔여 2      ✗   실제는 3인데 채널은 2
```

`id` 순서로 폴링해도 소용이 없다.
**`next_attempt_at`이 발행 시각을 `id` 순서에서 떼어내기 때문이다.**
결과는 아래 "순서가 뒤집히면 무슨 일이 생기는가"에 서술한 그대로다 —
이 방향은 기회손실, 반대 방향은 오버부킹.

다중 인스턴스는 이 문제를 **악화**시키는 것이지 **발생**시키는 것이 아니다.
최초 작성 시 "단일 인스턴스이므로 `id` 순서로 자연히 보장된다"고 적은 것은 오류다.

### 왜 낡은 값이 최신 값을 덮어쓰는가

두 가지를 먼저 분리해야 한다.

**1. 릴레이는 통보만 한다. 내부 재고를 쓰지 않는다.**

```
예약 API / 취소 API  ──▶  daily_inventory 변경     ← 내부 진실을 바꾸는 유일한 주체
                          outbox_event 기록        같은 트랜잭션 (ADR-0003)
                              │
                   릴레이 ────┘ ──▶  채널          ← 통보. 우리가 밀어넣은 사본
```

`#1`은 "우리 재고가 2가 됐다"는 **통보**이지 우리 DB에 대한 명령이 아니다.
발행이 성공해도 바뀌는 것은 `outbox_event.status`뿐이다.

발행 실패 시 도메인 트랜잭션을 롤백하지 않는 이유도 같다.
예약은 이미 확정된 진실이며, 외부 통보 실패로 되돌릴 수 없다.
되돌린다면 외부 장애가 예약 접수를 막는 구조가 되고,
그것은 ADR-0003이 기각한 대안 1 그 자체다.

| 시각 | 내부 DB를 바꾼 주체 | 내부 DB | 릴레이 | 채널 |
|---|---|---|---|---|
| t1 | 예약 API | 3→2 | `#1` 전송 실패 | 3 |
| t2 | 취소 API | 2→3 | `#2` 전송 성공 | 3 ✓ |
| t3 | **없음** | 3 | `#1` 재시도 성공 | 2 ✗ |

**t3 행에 주체가 비어 있다는 것이 이 문제의 전부다.**
아무 사건도 일어나지 않았는데 채널의 값이 뒤로 굴러갔다.

**2. 이벤트가 델타가 아니라 절대값이기 때문에 마지막 도착이 이긴다.**

```
델타    #1 = "-1",     #2 = "+1"       순서가 바뀌어도 결과가 같다 (교환법칙)
절대값  #1 = "잔여 2", #2 = "잔여 3"   마지막에 도착한 값이 이긴다
```

채널 ARI API는 절대값을 받는다. 델타를 쓸 수 없기 때문이다 —
at-least-once 전달에서 `-1`을 중복 수신하면 재고가 두 번 줄지만,
"잔여 2"는 몇 번을 적용해도 2다.

즉 **멱등성을 얻기 위해 절대값을 택했고, 그 대가로 순서 의존성이 생겼다.**
이것은 설계 실수가 아니라 구조적 트레이드오프이며,
"정확히 한 번은 수신 측에서 만들어진다"(ADR-0003)는 명제의 이면이다.

### 이 창은 얼마나 넓은가

t1과 t3 사이에 같은 키의 변경이 끼어야 하므로 드물어 보이지만,
**창의 폭은 백오프 간격만큼 벌어진다.**

재시도 스케줄이 `1분 → 2분 → 4분 → 8분 → 15분 → 30분 → 1시간 → ...`이므로,
몇 번 실패하면 몇 시간짜리 창이 열린다.
성수기 인기 날짜에서 그 시간 동안 아무 변동이 없기를 기대하는 편이 비현실적이다.

### 해법의 방향 — 순서를 지키지 말고 낡음을 판별한다

재시도가 있는 한 도착 순서를 보장하는 것은 비싸다.
대신 **키 단위로 낡은 이벤트를 식별해 버리면 된다.**

```
outbox_event 에 (room_type_id, stay_date) 와 단조 증가 version 을 둔다.
릴레이는 같은 키에 대해 더 큰 version 이 이미 PUBLISHED 면 그 이벤트를 skip 한다.
```

같은 키의 마지막 값만 보내면 되므로,
**B4(배치 내 동일 키 병합)와 동일한 메커니즘으로 한 번에 해결된다.**
레이트 리밋 소비도 함께 줄어든다.

### 이 해법도 창을 완전히 닫지는 못한다

`PUBLISHED` 마킹은 **외부 호출이 성공한 뒤에** 일어난다.
그 사이에 릴레이가 죽으면 실제로는 나갔는데 DB 에는 나가지 않은 것으로 남는다.

```
외부 호출 성공 ──▶ (릴레이 종료) ──▶ PUBLISHED 마킹 없음
                                      낡은 재시도가 skip 검사를 통과한다
```

T4 가 다루는 창과 같은 창이다(`03-testing-strategy.md`).
그런데 **결과의 성격이 다르다.**

| 창 안에서 벌어지는 일 | 절대값 전송이라서 |
|---|---|
| 중복 발행 | 멱등하게 흡수된다 — 안전 (T4 가 증명하는 것) |
| 낡은 값 재전송 | 흡수되지 않는다 — 최신 값을 덮어쓴다 |

**T4 는 통과하는데 B4 의 주장만 이 구간에서 무너진다.**

닫는 방법은 두 가지인데 둘 다 완전하지 않다.

| 방법 | 한계 |
|---|---|
| 수신 측이 `version` 을 보고 거절 | 채널 API 가 제공하지 않는다. 순서 보장을 연동사 책임으로 넘기기 때문이다 |
| 키별 `last_sent_version` 워터마크를 따로 둔다 | 갱신 시점이 여전히 외부 호출 뒤라 같은 창이 남는다. 폭만 줄어든다 |

**따라서 창을 0으로 만드는 대신, 좁히고 수렴시킨다.**
주기적으로 키별 현재값을 전량 재전송해 채널 상태를 내부 진실로 되돌린다 — B6.
순서 문제의 최종 방어선은 순서가 아니라 **재동기화**다.

외부 채널 쪽 요구와도 맞다. Expedia는 연동 문서에서
먼저 보낸 오래된 메시지가 나중에 도착해 최신 정보를 덮어쓰는 일이 없도록 하는 것을
**연동사 책임**으로 규정한다. 수신 측이 순서를 정렬해주지 않는다.

이 문제는 Kafka로 옮겨가도 사라지지 않는다.
파티션 키가 `property_id`가 아니라 `(room_type_id, stay_date)`여야 하는 이유가 여기 있고,
그마저도 재시도가 파티션 순서를 벗어나는 경우까지는 막지 못한다(ADR-0004).

## 순서가 뒤집히면 무슨 일이 생기는가

동일 `(room_type_id, stay_date)`에 대해 이런 이벤트가 연달아 발생했다고 하자.

```
t1: 잔여 3 → 2   (예약)
t2: 잔여 2 → 3   (취소)
```

t1이 백오프에 걸리고 t2가 먼저 도달하면, 채널에는 최종적으로 `2`가 남는다.
실제 잔여는 `3`인데 채널은 `2`로 알고 있다 — **기회손실**이다.
반대 방향으로 뒤집히면 **오버부킹**이다.

그래서 순서 보장은 선택이 아니라 요구사항이며,
Kafka 도입 시 파티션 키가 `property_id`가 아니라
`(room_type_id, stay_date)`여야 하는 이유가 된다.
