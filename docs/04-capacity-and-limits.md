# 진짜 병목은 어디인가

## 결론부터

**내부 처리량이 아니라 외부 채널 API의 레이트 리밋이다.**

이 판단이 아키텍처 결정 전체를 좌우한다.
내부가 병목이면 스케일아웃과 캐싱을 논해야 하지만,
외부 리밋이 병목이면 **배치와 스로틀링**이 답이 된다.

---

## 근거: Channex 공개 스펙

채널매니저 Channex의 공개 문서 기준으로,

| 항목 | 제약 |
|---|---|
| ARI(가용성/요금) 갱신 | 프로퍼티당 분당 20건 |
| 제약·가격 요청 | 프로퍼티당 분당 10건 |
| 초과 시 | 지수 백오프 요구 |
| 권장 전송 방식 | 변경분을 모아 6초 간격 1회 호출로 배치 |
| 전체 동기화 | 24시간에 1회, 오프피크 시간에만 |
| 웹훅 재시도 | 5XX 시 최대 10회, 1분→2분→4분→8분→15분→30분→1시간→2시간→4시간→6시간→10시간 |

## 산정

26개 지점 규모를 가정한다.

```
지점당 룸타입 평균 5종
변경 이벤트: 예약 1건당 (체크아웃-체크인) 일수만큼의 날짜 재고 변경
평균 숙박 2박 → 예약 1건 = 재고 변경 2건

성수기 주말 지점당 시간당 예약 30건 가정
→ 지점당 분당 재고 변경 = 30 * 2 / 60 = 1건

여유가 있어 보이지만, 문제는 평균이 아니라 버스트다.
프로모션 오픈, 대량 취소, 요금 일괄 변경 시
지점당 수백 건의 변경이 초 단위로 몰린다.
→ 분당 20건 리밋을 즉시 초과한다.
```

**따라서 개별 변경을 즉시 전송하는 설계는 성립하지 않는다.**

## 설계 귀결

Outbox 릴레이는 단순 폴링-전송 루프가 될 수 없다.

```
필요한 것:
1. 프로퍼티 단위 배치 윈도우 (6초)
2. 동일 (room_type_id, stay_date)에 대한 변경 병합 — 마지막 값만 전송
3. 채널별 토큰버킷 스로틀러
4. 429 / 5xx에 대한 지수 백오프
5. 백오프 중에도 순서가 뒤집히지 않는 보장
```

### 이번 범위에서 구현한 것

- **1번(배치 윈도우)까지.** 릴레이가 프로퍼티 단위로 PENDING 이벤트를 모아 전송한다.
- **4번(백오프).** `next_attempt_at`과 `retry_count` 컬럼으로 처리.
  재시도 간격은 Channex의 실제 스케줄(1/2/4/8/15/30분)을 따랐다 — 임의 설정이 아니다.

### 남긴 것

- **2번(변경 병합)**: 배치 내 동일 키 병합. Tier 2 백로그.
- **3번(토큰버킷)**: 채널별 리밋이 실제로 달라야 의미가 있다. 스텁 환경에서는 검증 가치가 낮다.
- **5번(순서 보장)**: **미해결. 단일 인스턴스에서도 이미 깨져 있다.**
  아래 "순서는 인스턴스 수의 문제가 아니다" 참고. Tier 2 백로그(B4)로 넘긴다.

---

## 순서는 인스턴스 수의 문제가 아니다

4번(백오프)을 구현한 순간 5번(순서 보장)이 깨진다.
릴레이가 하나뿐이어도 그렇다.

```
t1  (룸타입A, 3/15) 예약 → 잔여 3→2   이벤트 #1 생성
    #1 발행 실패 → next_attempt_at = +1분

t2  (룸타입A, 3/15) 취소 → 잔여 2→3   이벤트 #2 생성
    #2 즉시 발행 성공 → 채널 잔여 3   ✓

t3  #1 재시도 성공 → 채널 잔여 2      ✗   실제는 3인데 채널은 2
```

`id` 순서로 폴링해도 소용이 없다.
**`next_attempt_at`이 발행 시각을 `id` 순서에서 떼어내기 때문이다.**
결과는 아래 "순서가 뒤집히면 무슨 일이 생기는가"에 서술한 그대로다 —
이 방향은 기회손실, 반대 방향은 오버부킹.

다중 인스턴스는 이 문제를 **악화**시키는 것이지 **발생**시키는 것이 아니다.
최초 작성 시 "단일 인스턴스이므로 `id` 순서로 자연히 보장된다"고 적은 것은 오류다.

### 해법의 방향 — 순서를 지키지 말고 낡음을 판별한다

재시도가 있는 한 도착 순서를 보장하는 것은 비싸다.
대신 **키 단위로 낡은 이벤트를 식별해 버리면 된다.**

```
outbox_event 에 (room_type_id, stay_date) 와 단조 증가 version 을 둔다.
릴레이는 같은 키에 대해 더 큰 version 이 이미 PUBLISHED 면 그 이벤트를 skip 한다.
```

같은 키의 마지막 값만 보내면 되므로,
**B4(배치 내 동일 키 병합)와 동일한 메커니즘으로 한 번에 해결된다.**
레이트 리밋 소비도 함께 줄어든다.

외부 채널 쪽 요구와도 맞다. Expedia는 연동 문서에서
먼저 보낸 오래된 메시지가 나중에 도착해 최신 정보를 덮어쓰는 일이 없도록 하는 것을
**연동사 책임**으로 규정한다. 수신 측이 순서를 정렬해주지 않는다.

이 문제는 Kafka로 옮겨가도 사라지지 않는다.
파티션 키가 `property_id`가 아니라 `(room_type_id, stay_date)`여야 하는 이유가 여기 있고,
그마저도 재시도가 파티션 순서를 벗어나는 경우까지는 막지 못한다(ADR-0004).

---

## 순서가 뒤집히면 무슨 일이 생기는가

동일 `(room_type_id, stay_date)`에 대해 이런 이벤트가 연달아 발생했다고 하자.

```
t1: 잔여 3 → 2   (예약)
t2: 잔여 2 → 3   (취소)
```

t1이 백오프에 걸리고 t2가 먼저 도달하면, 채널에는 최종적으로 `2`가 남는다.
실제 잔여는 `3`인데 채널은 `2`로 알고 있다 — **기회손실**이다.
반대 방향으로 뒤집히면 **오버부킹**이다.

그래서 순서 보장은 선택이 아니라 요구사항이며,
Kafka 도입 시 파티션 키가 `property_id`가 아니라
`(room_type_id, stay_date)`여야 하는 이유가 된다.
