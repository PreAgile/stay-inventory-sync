# 문제 정의

## 배경

숙박 사업자는 하나의 객실 재고를 여러 판매 채널에 동시에 노출합니다.
자사 웹/앱(직판), 에어비앤비, 야놀자, 여기어때, 부킹닷컴 등입니다.

채널을 늘리는 것은 점유율 관점에서 합리적입니다.
그러나 **동일한 물리적 자산을 여러 시스템이 동시에 판매한다**는 구조는
필연적으로 정합성 문제를 만듭니다.

## 왜 이것이 어려운 문제인가

숙박 재고는 세 가지 성질을 동시에 갖습니다.

1. **소멸성** — 오늘 팔지 못한 객실은 내일 팔 수 없습니다. 재고 이월이 불가능합니다
2. **분할 불가** — 하나의 객실을 두 예약이 나눠 가질 수 없습니다
3. **다일 연속성** — 3박 예약은 3개의 날짜 재고를 **전부** 확보해야 성립합니다

3번이 이 문제를 일반적인 재고 차감과 구별짓습니다.
전자상거래의 재고 차감은 단일 카운터를 원자적으로 하나 줄이는 일입니다.
숙박은 **여러 카운터를 동시에, 전부 성공하거나 전부 실패하도록** 줄여야 합니다.

여기서 다중 락이 등장하고, 다중 락이 등장하는 순간 데드락이 등장합니다.

## 두 가지 불일치

### (a) Dual-write

```
[예약 확정]
  ├─ 내부 DB: 재고 차감, 예약 저장     ← 트랜잭션 A
  └─ 외부 채널: 재고 변경 통보          ← 트랜잭션 B (HTTP)

A는 성공, B는 실패 → 다른 채널이 이미 팔린 객실을 계속 노출
A는 실패, B는 성공 → 실재하는 재고가 채널에서 사라짐 (기회손실)
```

2PC는 외부 채널이 참여하지 않으므로 불가능합니다.

### (b) 중복 수신

채널은 예약 알림을 **at-least-once**로 전달합니다. 한 번 이상은 반드시 보내지만,
딱 한 번만 보낸다는 보장은 없다는 뜻입니다.
네트워크 타임아웃, 수신 측 5xx, 애매한 응답은 모두 재전송을 유발합니다.

Channex 공개 스펙 기준으로, 5XX 응답 시 최대 10회 재시도하며
간격은 1분 → 2분 → 4분 → 8분 → 15분 → 30분 → 1시간 → 2시간 → 4시간 → 6시간 → 10시간입니다.
**최종 시도는 원본 이벤트로부터 약 24시간 후**입니다.

즉 중복은 예외 상황이 아니라 **계약의 일부**입니다.

## 비용의 소재

두 경우 모두 결과는 오버부킹입니다.
그리고 오버부킹의 비용은 시스템이 아니라 **현장이 지불합니다.**

```
오버부킹 1건
  → 고객 응대 (누가 취소될 것인가)
  → 대체 객실 확보 또는 인근 숙소 수배
  → 차액 부담, 환불 처리
  → 리뷰 리스크
  → 이 모든 것을 조율하는 운영자의 시간
```

## "확인 업무"라는 신호

숙박 운영 조직에서 자동화 대상으로 거론되는 업무는 보통 세 가지로 묶입니다.

- **수기 업무** — 사람이 직접 입력합니다
- **확인 업무** — 사람이 맞는지 대조합니다
- **운영 병목** — 특정 단계에서 처리가 막힙니다

이 중 **확인 업무가 가장 많은 것을 말해 줍니다.**

수기 업무는 자동화가 아직 안 된 것입니다. 도구를 만들면 해결됩니다.
그러나 **확인 업무는 시스템이 이미 존재하는데도 그 결과를 믿지 못한다는 뜻입니다.**

```
"채널 재고가 실제 재고와 맞는지 아침마다 확인한다"
  → 시스템이 동기화를 하고 있다
  → 그런데 사람이 매일 대조하고 있다
  → 즉, 동기화가 틀릴 수 있다는 것을 조직이 알고 있다
```

확인 업무를 자동화하는 것(대조 스크립트를 짜는 것)은
증상을 빠르게 만들 뿐 원인을 없애지 않습니다.
**확인이 필요 없어지려면 틀리지 않아야 합니다.**

### 이 프로젝트의 두 층위

| 층위 | 대상 | 이 저장소에서 |
|---|---|---|
| **원인** | 애초에 불일치가 생기지 않게 합니다 | Outbox + 멱등 (Tier 0) |
| **증상** | 이미 생긴 불일치를 사람이 볼 수 있게 합니다 | diff 리포트 (Tier 1, B1) |

순서가 중요합니다. **원인을 먼저 다룹니다.**

diff 리포트를 먼저 만들면 "매일 눈으로 하던 대조를 화면으로 하게 됐다"에서 끝납니다.
확인 업무의 형태만 바뀌고 총량은 그대로입니다.

반면 정합성을 구조적으로 보장한 뒤의 diff 리포트는 성격이 다릅니다.
그것은 일상 업무가 아니라 **예외 감지 장치**가 됩니다.
평소에는 비어 있고, 뭔가 뜨면 진짜 이상이 생긴 것입니다.

**자동화로 줄여야 할 반복 업무의 상당 부분은
애초에 정합성이 깨졌기 때문에 생긴 뒷수습입니다.**

수기 업무를 자동화하기 전에, 그 수기 업무를 만들어내는 구조를 없애는 것이
더 근본적인 접근이라고 판단했습니다.
이것이 기능의 폭 대신 하나의 정합성 축을 택한 이유입니다.

### (c) 역방향 쓰기

채널 쪽에서도 값이 바뀝니다. 사장님이 채널 앱에서 마감을 풀고,
채널매니저 화면에서 노출 수를 손으로 조정합니다.
Channex 가 `ari` 웹훅을 제공한다는 것 자체가 이 경로가 실재한다는 증거입니다.

최초 작성 시 이 문서는 (a)와 (b) 두 지점만 다룬다고 선언했고,
(c)는 선언되지도 제외되지도 않았습니다(#21).

**(c)를 범위에 들입니다. 다만 전면 양방향 동기화가 아니라 축을 나눠서입니다.**

`ari` 웹훅은 하나의 사건이 아니라 여러 필드의 변경을 함께 실어 옵니다.
필드마다 어느 축인지를 가르면 **대부분이 정책**이고, 재고 축으로 넘어오는 하나
(`availability` 를 올리는 경우)는 **오버부킹 한도 요청으로 번역됩니다** — ADR-0009 · ADR-0007.

번역이 성립하는 한 원본은 축마다 하나로 유지됩니다.

## 이 프로젝트가 다루는 것

위 (a)와 (b), 그리고 축을 좁힌 (c)를 다룹니다.

- (a)는 **Outbox 패턴**으로 — 이벤트를 도메인 트랜잭션에 묶어 dual-write를 소거합니다
- (b)는 **멱등 3중 방어**로 — DB 제약 / 애플리케이션 / 어댑터
- (c)는 **재고와 정책의 축 분리**로 — ADR-0009, 대사 설계는 `07-reconciliation.md`

그리고 이 둘이 실제로 작동함을 **테스트로 증명합니다.**
증명되지 않은 정합성 주장은 주장이 아닙니다.

## 다루지 않는 것

요금 정책, 정산, 청소 스케줄링, 개별 호실 배정, 인증.
모두 실재하는 문제이지만 **이 문제와 직교합니다.**
함께 다루면 어느 것도 증명 수준에 도달하지 못합니다.

범위 판단의 전체 근거는 `02-scope.md` 입니다.
