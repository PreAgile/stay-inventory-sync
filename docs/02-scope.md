# 범위 판단

## 절단 기준

3일이라는 시간 제약 아래서 다음 질문으로 모든 항목을 걸렀다.

> **이것이 없으면 "재고 정합성을 보장한다"는 주장이 무너지는가?**

무너지면 포함, 아니면 제외. 예외 없음.

여기에 하나의 순서 규칙이 더해진다.

> **원인을 다루는 것이 증상을 다루는 것보다 먼저다.**

불일치 감지(diff 리포트)는 명백히 유용하지만, 정합성이 보장되지 않은 상태에서 만들면
사람이 매일 하던 대조를 화면으로 옮긴 것에 지나지 않는다.
확인 업무의 형태만 바뀌고 총량은 그대로다.

그래서 감지 기능은 Tier 1로 내려갔다.

## 계층별 판단

### Tier 0 — 코어 (없으면 주장이 무너짐)

| 항목 | 이유 |
|---|---|
| 다일 재고 원자적 차감 | 주장 그 자체 |
| 락 순서 고정 | 없으면 다일 예약에서 데드락 |
| Outbox + 트랜잭션 결합 | dual-write 제거의 유일한 수단 |
| 웹훅 멱등 처리 | at-least-once 전제의 필연적 귀결 |
| 안정성 테스트 4종 | 증명이 없으면 주장은 주장일 뿐 |

### Tier 1 — 운영 (있으면 문제가 완결됨)

| 항목 | 이유 |
|---|---|
| 채널 재고 diff 리포트 | 불일치가 이미 발생했을 때 사람이 개입할 통로 |
| Outbox DLQ + 재처리 | 영구 실패 이벤트의 종착지 |

### Tier 2 — 깊이 (여유가 있으면)

| 항목 | 이유 |
|---|---|
| 릴레이 `FOR UPDATE SKIP LOCKED` | 다중 인스턴스에서 이벤트 중복 처리 방지 |
| 프로퍼티 단위 배치 + 스로틀링 | 진짜 병목(외부 레이트 리밋) 대응 — `04-capacity-and-limits.md` |
| 지표 2종 | 오버부킹 차단 건수, Outbox 발행 지연 |

### Tier 3 — 문서만 (구현하지 않음)

| 항목 | 왜 문서로만 |
|---|---|
| Kafka 도입 | 도입 조건이 아직 충족되지 않음 (ADR-0004) |
| Debezium CDC | 폴링 릴레이의 다음 단계이나 인프라 부담이 큼 |
| 토큰버킷 채널별 스로틀러 | Tier 2 배치의 정교화. 경계만 정의 |
| 개별 호실 배정 | 별개 문제 축 |

## 명시적 제외와 근거

| 제외 | 근거 |
|---|---|
| **프론트엔드** | 검증 대상은 API 계약과 정합성이다. UI는 이 주장에 아무 기여도 하지 않으며, 만드는 순간 시간의 절반이 사라진다 |
| **PG 연동** | 결제 **결과 신호를 받는 엔드포인트까지**가 범위다. 승인·청구(authorization / capture) 모델을 근거로 적고 실제 게이트웨이는 붙이지 않는다. 이 모델을 택한 이유는 거절 시 청구를 안 하므로 **환불 경로가 상태 기계에 들어오지 않는다**는 것이다 (ADR-0010) |
| **조기 퇴실 (부분 복원)** | 노쇼는 범위 안(`TERMINATED`)이지만 조기 퇴실은 아니다. 남은 날짜만 복원하려면 복원이 전부/전무에서 **날짜별 부분 연산**으로 바뀌고, `INV-2` 가 "이 예약이 이 날짜를 점유하는가"를 상태만으로 판정할 수 없게 된다 — 예약당 유효 날짜 범위가 필요해진다 (ADR-0010) |
| **한도·시한 운영 UI** | 오버부킹 한도와 결제·승인 시한을 **담을 자리와 의미**까지가 범위다. 사람이 조정하는 화면과 노쇼율 예측은 다루지 않는다 (ADR-0007 · ADR-0010) |
| **인증/권한** | 문제 정의와 직교. 필터 체인에 붙는 위치만 명확하면 충분 |
| **요금(Rate) 정책** | 재고와 독립적인 축. 함께 다루면 두 문제 모두 얕아진다 |
| **실제 OTA 연동** | 파트너 계약과 인증 절차가 선행되어야 함. 공개 스펙을 모방한 스텁이 검증 목적에는 오히려 우월하다 (실패를 결정론적으로 주입할 수 있으므로) |
| **배포 / Terraform / ECS** | 3일 내 검증 불가. `docker compose up` 재현성으로 대체 |
| **H2 등 인메모리 DB** | `SELECT FOR UPDATE` 시맨틱이 PostgreSQL과 다르다. 락 검증이 무의미해지므로 Testcontainers 필수 |

## 차단 기준

> **토요일 23:00 시점에 안정성 테스트 4종이 전부 통과하지 않으면 Tier 1 이하는 전부 폐기한다.**

Tier 0가 불완전한 채로 Tier 1을 붙이는 것은 이 프로젝트가 하는 주장 자체를
약화시키는 선택이다. 기능 개수는 이 프로젝트의 평가 축이 아니다.

## 기존 오픈소스와의 대비

조사한 오픈소스 PMS(QloApps, miniCal, HotelDruid, HAIP)는 공통적으로
**기능의 폭**으로 승부한다 — 예약, 청소, 인보이스, 리포트, CRM.
채널 동기화는 대부분 cron 기반 폴링으로 처리되며,
동시성이나 중복 수신에 대한 방어는 명시적으로 검증되지 않는다.

이 프로젝트는 정반대의 선택을 했다.
**기능은 하나만. 대신 그 하나가 깨지지 않음을 테스트로 증명한다.**
