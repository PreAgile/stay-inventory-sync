# 테스트 전략

## 원칙

테스트의 이름은 "무엇을 했는가"가 아니라 **"무엇을 증명하는가"**를 말해야 합니다.

**DB 를 만지는 테스트는 전부** Testcontainers 기반 실제 PostgreSQL 에서 실행합니다.
H2 를 쓰지 않는 이유는 `SELECT FOR UPDATE` 의 의미가 달라 락 검증이 성립하지 않기 때문입니다.

DB 를 만지지 않는 스펙이 둘 있습니다 — `ReservationStatusTest`(상태 전이표)와
`ArchitectureTest`(클래스 파일만 읽습니다). **둘은 결함이 아니라 `domain` 과
`persistence` 를 가른 것의 의도된 효과입니다**(ADR-0008) — 상태 규칙이 틀렸는지 보려고
컨테이너를 띄울 이유가 없습니다.
H2는 사용하지 않습니다 — `SELECT FOR UPDATE`의 동작이 다르므로 락 검증이 성립하지 않습니다.

테스트 프레임워크는 **Kotest**(`FunSpec`)를 기본으로 씁니다. 절대 규칙은 아닙니다 —
JUnit 스타일이 명백히 쉬운 자리에서는 씁니다. 조건은 하나입니다: **불변식 훅이 두 엔진
모두에 걸려 있어야 합니다.** 한쪽에만 걸면 다른 쪽 테스트가 검사를 조용히 건너뜁니다.
근거와 등록 방법은 `AGENTS.md` 「테스트 규약」에 있습니다.
테스트 이름이 자연어 문장이므로 "무엇을 증명하는가"를 그대로 표현할 수 있습니다.

## 안정성 테스트 4종

### T1. 오버부킹은 물리적으로 불가능합니다

```
Given  잔여 1인 날짜
When   동일 룸타입/날짜로 동시 100건의 예약 요청
Then   성공 정확히 1건, 실패 99건
And    sold == total
And    INV-1, INV-2 만족
```

가장 직접적인 증명입니다. 100은 임의의 수가 아니라 커넥션 풀 크기를 초과하도록 잡아
풀 고갈 상황에서도 정확성이 유지되는지를 함께 봅니다.

### T2. 다일 예약에서 데드락이 발생하지 않습니다

```
Given  겹치는 날짜 범위 두 개 — [3/1~3/5], [3/3~3/7]
When   두 스레드가 서로 반대 순서로 요청, 200회 반복
Then   데드락 예외 0건
And    모든 요청이 성공 또는 재고부족으로 명확히 종료
```

**락 순서 고정(ADR-0002)의 유효성을 검증합니다.**

> **이 문장은 원래 이렇게 적혀 있었습니다.**
> *"이 테스트는 정렬 로직을 제거하면 즉시 실패해야 한다.
> 실패하지 않는다면 테스트가 잘못 짜인 것이다."*
>
> **구현하고 보니 그 조작이 표현되지 않습니다.** 지우지 않고 남깁니다 — 무엇을
> 기대했는지가 기록이고, 아래가 왜 그것이 성립하지 않는지입니다 (`#48`).

날짜 목록이 `generateSequence(checkIn) { it.plusDays(1) }` 로 만들어져
**생성 자체가 오름차순**입니다. 지울 `sorted()` 한 줄이 없습니다.

그리고 더 중요한 것 — **두 스레드를 모두 내림차순으로 바꿔도 데드락은 나지 않습니다.**

```
A: 3/5 → 3/4 → 3/3   (내림차순)
B: 3/7 → 3/6 → 3/5   (내림차순)     ← 순환 없음. 여전히 순서가 일치한다
```

**데드락에 필요한 것은 오름차순이 아니라 순서의 일치입니다.**
코드 경로가 하나뿐이면 그 경로를 어떻게 바꿔도 두 트랜잭션의 순서는 항상 일치합니다.
즉 *"정렬 로직을 제거한다"* 는 **단일 경로 구현에서는 정의되지 않는 조작**입니다.

방어가 약해진 것이 아니라 **지울 수 있는 형태로 두지 않은 것**입니다.
다만 반증할 수 없는 주장은 검증됐다고 말할 수 없으므로 증명을 셋으로 나눕니다.

| 무엇을 | 어떻게 | 없으면 |
|---|---|---|
| 순서가 어긋나면 **실제로** 데드락이 납니다 | 반대 순서로 잠그는 두 트랜잭션을 `CountDownLatch` 로 교차, `SQLSTATE 40P01` 확정 재현 | `T2` 통과가 "원래 데드락이 안 나는 상황" 과 구분되지 않습니다 |
| 같은 순서면 안 납니다 | 같은 두 행, 순서만 일치. 둘 다 커밋 | 첫 번째가 "이 환경이 원래 잘 죽는다" 로 읽힙니다 |
| 이 구현은 어긋날 수 없습니다 | 실제 서비스로 200회 교차 + `stayDates()` 가 항상 오름차순임을 단위 테스트로 고정 | 메커니즘만 증명하고 이 코드는 증명하지 않은 것입니다 |

`SQLSTATE` 확인이 중요합니다. `lock_timeout`(`55P03`)으로 죽으면 *"순환"* 이 아니라
*"느렸다"* 는 뜻이고 그건 증명 대상이 아닙니다.
`deadlock_timeout`(1s) 이 `lock_timeout`(5s) 보다 먼저 걸리도록 값을 잡았습니다.

**`T6`(테이블 간 순서)도 같은 사정이며 같은 방식으로 증명합니다.**

### T3. at-least-once 웹훅을 멱등하게 흡수합니다

```
Given  동일한 channel_reservation_id를 가진 예약 웹훅
When   10회 반복 수신 (일부는 동시)
Then   reservation 1건
And    재고 차감 1회
And    2회차 이후는 200 OK 반환 (재시도를 유발하지 않음)
```

at-least-once 는 한 번 이상은 반드시 보내지만 딱 한 번만 보낸다는 보장은 없다는 뜻입니다.
마지막 조건이 중요합니다. 중복을 4xx로 거절하면
채널이 이를 실패로 간주해 재시도를 계속합니다.

### T4. Outbox 재발행이 부작용을 중복시키지 않습니다

```
Given  발행 후 published 마킹 직전에 릴레이가 죽은 상황
When   릴레이 재기동 후 동일 이벤트를 다시 발행
Then   ChannelAdapter의 실질 부작용은 1회
And    멱등키로 중복이 흡수되었음을 어댑터가 기록
```

Outbox는 at-least-once입니다. **정확히 한 번은 발행 측이 아니라 수신 측에서 만들어집니다.**

## 취소·복원 테스트 2종

`T1` · `T2` 가 차감 경합을 증명하는데 복원 쪽에는 대응물이 없었습니다. 그 대칭을 채웁니다.

### T5. 중복 취소는 재고를 두 번 복원하지 않습니다

```
Given  CONFIRMED 예약 1건
When   동시 50건의 취소 요청
Then   실제 복원 1회, sold 정확히 room_count 만큼 감소
And    나머지 49건은 2xx (이미 취소됨)
And    INV-1 ~ INV-4 만족
```

**조건부 UPDATE 의 `AND status = 'CONFIRMED'` 를 제거하면 이 테스트가 실패해야 합니다.**
취소 웹훅도 at-least-once 이므로 이것은 이론적 경합이 아니라 일상적으로 들어오는 입력입니다.

### T6. 취소와 예약이 같은 날짜에서 교차해도 데드락이 없습니다

```
Given  잔여 0인 날짜 + 해당 날짜의 CONFIRMED 예약 1건
When   취소 1건과 신규 예약 100건을 동시에
Then   데드락 0건, 성공 예약 정확히 1건
And    INV-1 ~ INV-4 만족
```

**`T6` 이 `ADR-0011`(락 순서)의 증명입니다.** `T2` 가 `stay_date` 정렬의 증명이듯,
**테이블 간 순서를 뒤집으면 `T6` 이 실패해야 합니다.** 실패하지 않으면 테스트가 잘못 짜인 것입니다.

`T2` 와 역할이 다릅니다 — `T2` 는 **한 테이블 안**의 순서를, `T6` 은 **테이블 사이**의 순서를 증명합니다.

## 선점 테스트 4종 (ADR-0010)

`T1`~`T4` 가 확정 경로를 증명하듯, 확정 **전** 구간을 증명합니다.

### T7. 만료된 선점은 재고를 잠그지 않습니다

```
Given  잔여 1인 날짜에 만료된 선점 1건 (expires_at 을 과거로)
When   신규 예약 1건
Then   성공. INV-1 · INV-4 만족
And    expires_at > now() 조건을 제거하면 이 테스트가 실패해야 한다
```

**만료를 만들려고 시계를 조작할 필요가 없습니다.** `expires_at` 을 과거 값으로 넣으면 끝입니다.
`ADR-0010` 결정 2 가 만료를 상태 전이가 아니라 데이터로 표현한 덕에 얻는 부수 효과이며,
동시성 테스트에서 시간을 다루지 않아도 된다는 점이 큽니다.

### T8. 선점 경합에서 과선점이 발생하지 않습니다

```
Given  잔여 1인 날짜
When   동시 100건의 선점 요청
Then   성공 정확히 1건, 실패 99건. INV-4 만족
And    daily_inventory 행 락(FOR UPDATE)을 제거하면 실패해야 한다
```

**T8 이 절대 규칙 11 의 증명입니다.** 그 락은 값을 바꾸지 않으므로
**없어도 되는 것처럼 보입니다** — 그것이 이 테스트가 필요한 이유입니다.

### T9. 승인 대기 중인 재고는 다른 예약에 팔리지 않습니다

```
Given  잔여 1인 날짜에 PENDING_APPROVAL 예약 1건 (승인 시한 내)
When   신규 예약 100건
Then   전부 실패. 사장님 승인 후 sold == 1, 유효 선점 == 0
And    INV-2 · INV-4 만족
And    INV-4 의 released_at IS NULL 을 제거하면 실패해야 한다
```

마지막 줄이 중요합니다. 조건을 지우면 **확정된 예약이 남은 시한 동안 재고를 두 번 차지**하고,
잔여가 음수로 계산됩니다. 즉 확정이 곧 품절을 만듭니다.

### T10. 만료 후 도착한 결제 성공은 재고가 없으면 확정되지 않습니다

```
Given  잔여 1인 날짜. 선점 1건이 만료되고 그 자리를 다른 예약이 확정
When   만료된 선점의 결제 성공 신호가 도착
Then   전이 거부. 승인 취소 이벤트 1건 발행. sold 는 1 그대로
And    같은 상황에서 재고가 남아 있으면 재선점되어 전이가 성공한다
And    INV-1 · INV-4 만족
```

**T10 이 결정 9 의 증명입니다.** 재검증을 생략하면 만료된 선점이 확정으로 올라가 `INV-4` 를 뚫습니다.

## 불변식 검증

4종 테스트 모두 종료 시 공통 assertion을 실행합니다.

```kotlin
inventoryInvariants.assertAll()
// INV-1  0 <= sold <= total  (total = physical_total + overbooking_limit)
// INV-2  sold == 재고 점유 예약의 room_count 합 (occupiesInventory)
// INV-3  checkIn < checkOut
// INV-4  sold + SUM(유효 선점의 room_count) <= total  (holdsInventory)
```

개별 시나리오가 아니라 시스템 전체의 참을 확인하므로,
예상하지 못한 경로로 발생한 불일치도 잡힙니다.

## 아키텍처 테스트 (ArchUnit)

정합성 보장 구조가 우회되지 않도록 강제합니다.

```
- domain 패키지는 spring-web, jpa 어노테이션에 의존하지 않는다
- ChannelAdapter 구현체는 Repository를 직접 참조하지 않는다
- 재고를 변경하는 코드는 InventoryService를 통해서만 접근한다
- 엔티티에 연관 매핑 어노테이션(`@OneToMany`/`@ManyToOne`/`@ManyToMany`)이 없다
- Outbox 릴레이 패키지는 JPA Repository 에 의존하지 않는다
- OutboxEvent 삽입은 도메인 트랜잭션 내부에서만 일어난다
```

연관 매핑 금지와 릴레이 격리, 이 두 규칙은 **dirty checking 우회 경로를 봉인합니다.**
연관을 타고 들어가 필드를 바꾸면 `InventoryService` 에 대한 정적 참조가 생기지 않으므로
"재고를 변경하는 코드는 `InventoryService` 를 통해서만" 규칙이 UPDATE 를 놓칩니다.
막을 수 없는 경로는 아예 만들지 않습니다 (ADR-0008).

마지막 규칙이 핵심입니다. Outbox가 별도 트랜잭션에서 삽입되면
dual-write 문제가 그대로 돌아옵니다. 이건 리뷰로 막을 게 아니라 컴파일 타임에 막습니다.

## 반증이 통과하면 반증 절차를 먼저 의심한다

*"방어를 지우면 테스트가 실패해야 한다"* 는 이 문서의 기본 수법입니다.
그런데 **지웠는데 통과하는 일이 실제로 네 번 있었고, 네 번 다 원인은 테스트였습니다.**

| 무엇을 지웠나 | 왜 통과했나 | 무엇을 고쳤나 |
|---|---|---|
| 조건부 UPDATE 의 `AND status = 'CONFIRMED'` | 초과 복원이 `CHECK` 에 걸려 예외로 죽었는데 **그 예외가 `Future` 안에 갇혔습니다** | 동시성 헬퍼가 새어 나온 예외를 실패로 만듭니다 |
| 조기 반환의 `IS NOT DISTINCT FROM` | 조기 반환이 죽어도 **DB UNIQUE 가 같은 결과를 냈습니다** | 관측 결과가 아니라 **판정 쿼리 자체**를 검사 |
| 순서 키의 `aggregate_type` | 두 이벤트의 버전이 **우연히 둘 다 1** 이라 비교가 발동하지 않았습니다 | 버전이 갈리는 시나리오로 교체 |
| — (`#23` 창 재현) | 재현한 방향을 **B4 가 이미 막고 있었습니다** | 창이 열리는 방향을 실측으로 확인 |

세 가지가 반복됩니다.

1. **예외가 사라집니다** — 스레드·비동기 경계에서 실패가 조용해집니다
2. **방어선이 겹칩니다** — 뒤쪽 방어가 같은 결과를 내면 앞쪽 방어의 생사가 관측되지 않습니다
3. **경계값이 우연히 같습니다** — 비교 연산이 아예 발동하지 않는 픽스처

그래서 **반증 실험이 통과하면 두 가지 중 하나입니다** — 방어가 불필요했거나,
**반증 절차가 틀렸거나.** 네 번 다 후자였습니다.

이 문서가 요구하는 것은 *"깨뜨려 봤다"* 가 아니라 **"깨뜨렸더니 실패했다"** 이며,
실패하지 않았을 때 멈춰서 이유를 찾는 것이 그 요구의 절반입니다.

## 하지 않는 것: Lincheck

Lincheck은 JVM 메모리 모델 상의 **인메모리 동시 자료구조**에 대해
선형화 가능성을 모델 체킹으로 검증하는 도구입니다.
탐색 대상은 JVM 스레드 인터리빙입니다.

이 프로젝트의 동시성은 인메모리가 아니라 **DB 트랜잭션과 행 수준 락**에 있습니다.
PostgreSQL의 락 대기 그래프나 MVCC 스냅숏은 Lincheck의 탐색 공간이 아닙니다.

**적용해도 이 시스템이 주장하는 정합성을 증명하지 못합니다.**
따라서 쓰지 않습니다. 자세한 근거는 ADR-0005.

도구를 쓰는 것보다 도구의 적용 경계를 아는 것이 중요하다고 판단했습니다.

## 하지 않는 것: 부하 테스트

nGrinder / k6 / Gatling을 도입하지 않았습니다. 세 가지 이유가 있습니다.

**1. 측정 대상이 다릅니다.**
부하 테스트는 처리량을 봅니다. 이 문제의 본질은 정확성입니다.
"초당 500건 처리"는 오버부킹을 막았다는 증거가 되지 못합니다.
반대로 T1(동시 100건 → 성공 정확히 1건)은 완결된 증거입니다.

**2. 로컬 수치는 해석 불가능합니다.**
개발 머신에서 나온 TPS는 인스턴스 사양과 네트워크에 종속됩니다.
근거 없는 숫자를 제시하는 것은 정보가 아니라 노이즈입니다.

**3. 진짜 병목은 내부에 없습니다.**
`04-capacity-and-limits.md` 참고. 병목은 외부 채널 API의 레이트 리밋이며,
이는 부하 테스트로 측정되지 않고 산정으로 도출됩니다.

대신 T1의 동시 요청 수를 100 → 1000으로 올려 **락 경합 시 응답시간 분포**만
기록합니다. 별도 도구 없이 JUnit 안에서 끝납니다.
