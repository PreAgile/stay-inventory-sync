# 대사(reconciliation) 설계

`ADR-0009`가 정한 세 축을 실제 호출로 옮긴다.
이 문서는 **어느 API 를 어떤 순서로 부르는가**만 다룬다. 축을 나눈 근거는 ADR-0009 에 있다.

---

## 결론부터

**인바운드 대사는 대조가 아니라 큐 소비다.**

Channex 는 `booking_revisions/feed` 에 **아직 ack 하지 않은 리비전만** 남긴다.
ack 하면 사라지고, 30분간 미확인이면 경고가 온다.

즉 우리가 만들어야 하는 것은 "우리 DB 와 채널을 비교하는 로직"이 아니라
**큐를 끝까지, 순서대로, 정확히 한 번 비우는 소비자**다.

이것이 문제의 난이도를 한 단계 내린다.
`00-problem-definition.md`가 (b) 중복 수신에 대해 세운 전제와 같은 구조이며,
방어 수단도 같다 — 멱등.

---

## 웹훅은 데이터가 아니라 트리거다

Channex 공개 문서가 직접 말한다.

> 웹훅 호출의 순서는 이벤트 발생 순서와 다를 수 있다

그리고 웹훅을 트리거로 쓰고 **현재 상태는 API 로 당겨오라**고 권고한다.

이 원칙 하나가 인바운드의 순서 문제를 구조적으로 없앤다.

```
❌  웹훅 payload 의 숫자를 그대로 반영한다     → 순서 역전에 그대로 노출
✅  웹훅을 "지금 당겨라"는 신호로만 쓴다       → 순서는 우리가 정한다
```

`04-capacity-and-limits.md`가 아웃바운드에서 겪은 순서 문제(B4 버전 스탬프)를
인바운드에서는 **겪지 않아도 되는 이유**가 이것이다.
두 방향의 해법이 다른 것은 비대칭이 아니라, 인바운드에는 당겨올 원본이 있기 때문이다.

| 방향 | 원본이 어디 있나 | 순서 해법 |
|---|---|---|
| 아웃바운드 (우리 → 채널) | 우리 DB | 버전 스탬프 + 재동기화 (B4 · B6) |
| 인바운드 (채널 → 우리) | **채널의 feed** | feed 를 정렬해 직렬 소비 |

## 방향 1. 인바운드 예약 — 큐 소비

```
웹훅(booking_new / booking_modification / booking_cancellation) 수신
        │   payload 는 버린다. 트리거로만 쓴다
        ▼
GET  /api/v1/booking_revisions/feed
       ?filter[property_id]=..&order[inserted_at]=asc
        │   ack 하지 않은 리비전만 돌아온다
        ▼
[트랜잭션]  재고 차감 / 복원  +  예약 upsert  +  outbox_event 적재
        │   커밋
        ▼
POST /api/v1/booking_revisions/:id/ack
```

### 절대 규칙 A — ack 은 커밋 뒤에

ack 을 먼저 하고 트랜잭션이 롤백되면 그 리비전은 feed 에서 영구히 사라진다.
**유실이다.** 반대로 커밋 후 ack 이 실패하면 다음 폴링에 다시 온다 — 중복이다.

```
ack 먼저 → 롤백    :  유실.  복구 수단이 없다
커밋 먼저 → ack 실패 :  중복.  멱등으로 흡수한다 (T3 가 증명하는 그 성질)
```

**유실과 중복 중 중복을 택한다.** 이 프로젝트가 at-least-once 를 받아들인 이유와 같다.

이것은 우리 판단이 아니라 Channex 의 권고이기도 하다 —
*"성공적으로 저장했을 때만 ack 해야 한다. ack 되었다면 그것은 PMS 에 들어 있다는 뜻이다."*

### 절대 규칙 B — 프로퍼티 단위 직렬

같은 예약의 `new → modified → cancelled` 가 순서 없이 처리되면
없는 예약을 취소하거나, 취소된 예약을 되살린다.

feed 를 `inserted_at` 오름차순으로 **프로퍼티마다 하나씩** 처리하면 순서가 확정된다.
프로퍼티끼리는 병렬이어도 무해하다 — 재고 행이 겹치지 않는다.

ADR-0002 가 재고 행을 `stayDate` 오름차순으로 잠가 데드락을 없앤 것과 같은 수법이다.
**순서를 보장하는 가장 싼 방법은 순서를 정하는 것이다.**

### 스키마에 없는 것 — 리비전

Channex 의 예약은 **리비전의 최신 상태**다.
같은 `booking_id` 가 `new → modified → cancelled` 로 여러 번 오고,
`unique_id` 는 리비전 전체에서 변하지 않는다.

현재 `reservation` 스키마에는 리비전 개념이 없다.
`UNIQUE(channel, channel_reservation_id)` 는 **예약의 중복 생성**은 막지만,
**같은 리비전의 재적용**은 막지 못한다.

필요한 것은 처리한 리비전의 기록이다.

```
reservation.last_revision_id   마지막으로 적용한 리비전
processed_revision(revision_id) 처리 완료 원장 — 재적용 차단
```

`revision_id` 는 UUID 이므로 대소 비교로 낡음을 판별할 수 없다.
**직렬 소비가 전제되므로 비교가 필요 없다** — 원장에 있으면 건너뛴다.
직렬을 포기하는 순간 `inserted_at` 기반 판정이 필요해진다.

## 방향 2. 인바운드 정책 — `ari` 웹훅

판정 흐름은 ADR-0009 에 있다. 여기서는 호출 순서만 적는다.

```
ari 웹훅 수신
        │
        ├─ payload.user_id == 우리 앱 → 버린다 (에코)
        │
        ▼
GET  /api/v1/availability?filter[property_id]=..
       &filter[date][gte]=..&filter[date][lte]=..
        │   payload 의 숫자를 쓰지 않고 현재 상태를 당겨온다
        ▼
정책 장부와 비교  →  [흡수] 또는 [교정]
```

`ari` 웹훅도 순서 보장이 없으므로 payload 의 값을 그대로 쓰지 않는다.
웹훅 = 트리거 원칙이 여기에도 적용된다.

### 에코 문제가 여기서 닫힌다

`user_id` 는 Channex 가 payload 에 넣어 주는 값이고,
공개 문서가 용도를 명시한다 — *"자기 앱이 만든 변경을 무시하고 싶을 때 쓸 수 있다"*.

우리가 밀어넣은 변경이 `ari` 로 되돌아오는 것을 이 한 필드로 걸러낸다.
**#18 의 에코 우려는 우리가 만들 장치가 아니라 이미 제공되는 필드로 해소된다.**

## 방향 3. 아웃바운드 drift 검출 — B6 의 구현 수단

우리가 밀어넣은 값이 채널에 실제로 반영됐는지 확인하는 **유일한** 수단이다.

```
GET /api/v1/availability
      ?filter[property_id]=..&filter[date][gte]=..&filter[date][lte]=..

→ {"data": {"<room_type_id>": {"2026-09-01": 20, "2026-09-02": 20}}}

우리 계산값과 대조  →  다르면 재발행
```

`availability` 는 **절대값**이므로 재발행이 멱등하다.
몇 번 밀어넣어도 무해하고, 순서가 뒤집혔더라도 다음 주기가 최신값으로 덮어 자동 치유된다.

`06-backlog.md` 의 **B6(정기 재동기화)** 가 정확히 이것이고,
지금까지 "전량 재전송"으로만 서술되어 있던 부분의 실제 API 가 이 GET 이다.
**대조 없이 전량 재전송**하는 것보다 **읽어서 다른 것만 재전송**하는 편이 리밋 소비가 적다.

B1(diff 리포트)도 같은 GET 을 쓴다. B1 은 사람에게 보여주고, B6 은 고친다.

## 취소와 수정

취소는 별도 객체가 아니라 **같은 `booking_id` 의 새 리비전**(`status: cancelled`)으로 온다.
수정도 같다(`status: modified`).

여기서 실제로 어려운 것은 네 가지이고, 전부 이미 열린 결정과 맞물린다.

| 상황 | 문제 | 어디서 다루나 |
|---|---|---|
| 취소 리비전이 생성보다 먼저 도착 | 없는 예약을 취소 | **직렬 소비로 해소** (규칙 B) |
| 체크인 이후 취소 | 재고를 복원하면 쓴 방이 다시 팔린다 | #26 · #28 |
| 날짜 변경 수정 | 옛 날짜 복원 + 새 날짜 차감 + 예약 행을 한 트랜잭션에 | #27 (락 순서) |
| 배정분에서 팔린 예약의 취소 | 배정 잔여로 되돌리나 공유로 되돌리나 | 아래 |

### 배정 취소는 예약 시점에 결정한다

보장형 하이브리드(ADR-0001)를 쓰면 마지막 줄이 새로 생긴다.
"이 취소는 배정분에서 나왔나 공유분에서 나왔나."

**취소 시점에 판정하지 않는다. 예약 시점에 어디서 차감했는지를 예약 행에 기록한다.**

```
reservation.deducted_from = ALLOTMENT | SHARED
```

기록해 두면 복원 대상이 조회로 결정된다. 판정 로직이 없으므로 틀릴 자리도 없다.
`AGENTS.md` 절대 규칙 7(재고 복원은 `CONFIRMED -> CANCELED` 에서만)의 확장이다 —
**언제 복원하는가에 이어 어디로 복원하는가를 데이터로 둔다.**

## 팬아웃 계수는 1이다

`04-capacity-and-limits.md` 와 #18 은 통보 대상 채널 수를 용량 산정의 계수로 놓았다.
**Channex 를 경유하는 구조에서는 그 계수가 1이다.**

`availability` push 는 룸타입 단위이며 채널별 값을 받지 않는다.

```
우리  ──(1회 호출)──▶  Channex  ──▶  채널 A
                                 ──▶  채널 B
                                 ──▶  채널 C     팬아웃은 Channex 안에서 일어난다
```

즉 **"어느 채널에 보낼지"라는 결정 자체가 이 구조에는 없다.**
#18 이 물은 팬아웃 대상 선택은 형태가 바뀐다 —
보낼 채널을 고르는 문제가 아니라, **규칙(`close_out` 등)으로 제외할 채널을 고르는 문제**다.

계수가 1이 아니게 되는 조건은 하나다. **채널을 Channex 없이 직접 연동하면** 되돌아온다.
그때는 채널 수만큼 어댑터를 호출해야 하고 계수가 N 이 된다.

## 레이트 리밋 예산

공개 문서 기준으로 프로퍼티당 분당 제한은 이렇게 쪼개진다.

| 대상 | 제한 |
|---|---|
| Availability 요청 | **분당 10회** |
| Restrictions · Price 요청 | 분당 10회 |
| 합계 (ARI 총량) | 분당 20회 |

**"분당 20"은 총량이고, availability 만 보면 10이다.**

그리고 이 10은 **변경 건수가 아니라 요청 횟수**다.
공개 문서의 권고가 명확하다 — *"100일치 요금을 갱신하려면 1건씩 100번 보내지 말고
100개 변경을 담은 1건을 보내라."*

여기서 이미 구현된 6초 배치 윈도우의 값이 확인된다.

```
6초 윈도우 → 분당 10회 → availability 리밋과 정확히 일치
```

**버스트는 리밋을 초과하지 않는다. 배치가 흡수한다.**
수백 건의 변경이 몰려도 윈도우 하나에 병합되어 1회 호출로 나간다.

즉 레이트 리밋은 처리량의 상한이 아니라 **배치를 강제하는 제약**이다.
그리고 배치가 강제되면 동일 키 병합이 필요해지고, 병합이 필요해지면 순서 문제가 생긴다.
`04-capacity-and-limits.md`가 도달한 결론의 인과가 이것이다.

대사가 추가로 소비하는 예산은 다음과 같다.

| 호출 | 분류 | 빈도 |
|---|---|---|
| `GET /booking_revisions/feed` | ARI 아님 | 웹훅 트리거 + 안전망 폴링 |
| `POST /booking_revisions/:id/ack` | ARI 아님 | 리비전당 1회 |
| `GET /availability` | **미확인** | drift 검출 주기 |
| `POST /availability` | Availability (10/분) | 배치 윈도우당 1회 |
| Availability Rules 갱신 | **미확인** | 정책 변경 시 |

## 확인되지 않은 것

아래 세 가지는 공개 문서에 없다. **보장형 하이브리드의 성립 여부를 가른다.**

### U1. `GET /availability` 와 규칙 갱신이 ARI 리밋에 포함되는가

리밋 문서는 "Availability Requests" 라고만 적고 어느 엔드포인트가 여기 속하는지 열거하지 않는다.
읽기까지 10회에 포함되면 drift 검출 주기가 쓰기 예산을 잠식한다.

### U2. 같은 룸타입에 여러 규칙이 걸리면 우선순위가 어떻게 되는가

문서에 없다. 캡형(`max_availability`)과 보장형(`availability_offset`)을 동시에 쓰려면 필수다.

### U3. 규칙의 날짜 granularity 와 갱신 비용

규칙의 범위는 `기간 + 요일`이다. 날짜마다 배정 잔여가 다르면 규칙이 날짜 수만큼 늘어난다.
값이 같은 연속 구간을 병합하는 처리가 필요하고, 그 갱신이 리밋에 걸리는지도 U1 에 달렸다.

**세 가지 모두 staging 환경에서 실측 가능하다.** 절차는 `docs/experiments/channex-unknowns.md`.

## 무엇을 언제 하는가

`06-backlog.md` 는 확정된 목록이며 이 문서가 항목을 추가하지 않는다.
아래는 **대사 축이 성립하기 위한 순서**이며, 백로그 항목과의 대응을 함께 적는다.

| 순서 | 내용 | 백로그 대응 |
|---|---|---|
| 1 | feed + ack 소비. 커밋 후 ack, 프로퍼티 직렬, 리비전 원장 | 신규 (인바운드 축) |
| 2 | `GET /availability` 기반 drift 검출 + 멱등 재발행 | **B6** 의 구현 수단 |
| 3 | `ari` 웹훅 + `user_id` 에코 필터 + 정책 장부 | ADR-0009 적용 · #21 · #18 |
| 4 | 캡형 하이브리드 (`max_availability`) | ADR-0001 재검토 조건 3 |
| 5 | 보장형 하이브리드 (`availability_offset` + 배정 장부) | U1~U3 실측 후 |

**3번이 두 개의 열린 문제를 동시에 닫는다** — #21(역방향 쓰기)과 #18(에코).
4·5번은 3번 없이 성립하지 않는다. 채널이 우리 값을 지키는지 모르는 상태에서
채널별 정책을 얹으면 지킬 수 없는 약속이 늘어난다.

### 증명해야 할 것

`AGENTS.md` 의 규약대로, 각 항목은 깨뜨렸을 때 실패하는 테스트를 가진다.

| # | 증명 대상 | 깨뜨리는 방법 |
|---|---|---|
| T7 | ack 실패 후 재수신에서 예약이 중복 생성되지 않는다 | 리비전 원장을 제거하면 실패해야 한다 |
| T8 | 커밋 실패 시 ack 하지 않아 다음 폴링에 다시 처리된다 | ack 을 커밋 앞으로 옮기면 실패해야 한다 |
| T9 | 우리가 밀어넣은 변경의 `ari` 웹훅은 장부를 바꾸지 않는다 | `user_id` 필터를 제거하면 실패해야 한다 |

T8 이 가장 중요하다. **유실은 테스트 없이는 보이지 않는다** —
성공한 것처럼 조용히 사라지기 때문이다.
