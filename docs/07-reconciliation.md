# 대사(reconciliation) 설계

---

# 0. 처음 보는 사람을 위한 설명

이 문서는 저장소 내부 용어를 모르는 상태에서 읽을 수 있게 시작합니다.

## 등장하는 것 넷

```
   숙소                방 10개. 물리적으로 존재하는 것
     │
   PMS  (우리)         방이 몇 개 남았는지를 아는 시스템. 이 저장소가 이것이다
     │
   채널매니저          우리와 여러 채널 사이의 중개 소프트웨어.
     │                 채널마다 따로 연동하지 않게 해준다
     ├── 판매 채널 A    손님이 실제로 예약하는 곳
     ├── 판매 채널 B
     └── 판매 채널 C
```

**PMS(Property Management System)** 는 숙소 운영 시스템입니다.
이 저장소는 그중 **재고**만 다룹니다 — 청소, 정산, 요금은 다루지 않습니다(`02-scope.md`).

## 오가는 것은 두 방향입니다

```
아웃바운드   우리 → 채널     "이제 7개 남았습니다"
인바운드     채널 → 우리     "손님이 하나 예약했습니다"
```

두 방향 다 **네트워크를 건너갑니다.** 그리고 네트워크는 실패합니다.

## 대사가 무엇인가

**대사(對査)** 는 두 장부를 맞춰 보는 일입니다. 회계에서 온 말입니다.

여기서는 **우리가 아는 재고와 채널이 아는 재고가 같은지 확인하고, 다르면 맞추는 일**을 뜻합니다.

왜 필요한가. 두 시스템이 각자 숫자를 들고 있고 그 사이를 네트워크가 잇고 있으면,
**언젠가 반드시 어긋납니다.** 어긋나지 않게 만드는 것은 불가능하고,
어긋난 것을 유한 시간 안에 되돌리는 것은 가능합니다.

## 어긋나는 경우는 셋입니다

각각 무슨 일이 벌어지는지가 이 문서의 출발점입니다.

**(1) 우리가 보낸 것이 가지 않았습니다**

```
방 하나 팔림  →  우리 DB 7 로 줄임  →  채널에 통보 실패  →  채널은 아직 8 로 알고 있다
                                                              → 이미 팔린 방을 또 판다
                                                              → 오버부킹
```

**(2) 채널이 보낸 것이 오지 않았습니다**

```
손님이 채널에서 예약  →  채널이 우리에게 알림  →  전달 실패  →  우리는 그 예약을 모른다
                                                              → 그 방을 또 판다
                                                              → 오버부킹
```

**(3) 사람이 채널 화면에서 직접 바꿨습니다**

```
사장님이 채널 앱을 열어 "오늘은 2개만 팔자" 로 바꿈
   → 우리 DB 에는 그 사실이 없다
   → 우리가 다음에 값을 밀어넣으면 사장님의 조작이 지워진다
```

세 경우의 결과가 다르다는 점이 중요합니다.
(1)과 (2)는 **오버부킹**이고, (3)은 **현장과 시스템의 충돌**입니다.

## 이 저장소가 이미 다루는 것과, 이 문서가 다루는 것

| | 문제 | 다루는 곳 |
|---|---|---|
| (1) | 우리가 보낸 것이 가지 않았습니다 | **이미 다룹니다** — Outbox 패턴 (ADR-0003) |
| (2) | 채널이 보낸 것이 오지 않았습니다 | **이 문서** |
| (3) | 사람이 채널에서 직접 바꿨습니다 | **이 문서** + ADR-0009 |

(1)의 해법을 한 줄로 요약하면 이렇습니다.
**나갈 통보를 우리 DB 트랜잭션에 같이 적어 두고, 별도 프로세스가 나중에 보냅니다.**
그러면 "DB 는 바뀌었는데 통보는 안 나간" 상태가 생기지 않습니다. 이것이 Outbox 입니다.

**이 문서의 결론을 먼저 말하면, (2)의 해법은 Outbox 의 거울상입니다.**

```
Outbox   나갈 것을 우리 트랜잭션에 묶는다
Inbox    들어온 것을 우리 트랜잭션에 묶는다
```

이 저장소는 아웃바운드를 Outbox 로 풀었지만 **인바운드에는 아직 아무 장치가 없습니다.**
그것이 이 문서가 채우는 공백입니다.

## 왜 채널매니저 문서를 읽었는가

**우리가 특정 채널매니저를 붙이려는 것이 아닙니다.** 이 저장소의 채널 어댑터는 스텁입니다(#4).

읽은 이유는 하나입니다.

> **이 문제를 실제로 겪는 회사가 어떤 장치를 만들어 두었는지 보려고.**

채널매니저의 공개 API 문서는 **이 도메인의 실패 모드가 공개적으로 적혀 있는 드문 자료**입니다.
그들이 만든 장치는 곧 그 실패가 실재한다는 증거입니다.
장치가 있다는 것은 그것 없이 시스템이 깨진 적이 있다는 뜻이기 때문입니다.

그래서 이 문서는 두 층으로 나뉩니다.

| 층 | 내용 |
|---|---|
| **1장** | 참고한 것 — 채널매니저 문서에서 확인된 실패 모드와, 그들이 만든 장치 |
| **2장** | **우리가 만들 것** — 그 장치의 우리 쪽 대응물. 우리 스키마와 우리 컴포넌트로 |

**2장이 이 문서의 본론입니다.** 1장은 근거일 뿐입니다.

# 1. 참고한 것 — 남들은 무엇을 만들었나

Channex 공개 문서를 근거로 확인한 사실만 적습니다. 출처는 문서 끝에 있습니다.
특정 제품을 채택한다는 뜻이 아니라, **이 도메인에 실재하는 장치의 목록**으로 읽습니다.

| 남들이 만든 장치 | 그것이 있다는 것은 | 우리 쪽 대응물 (2장) |
|---|---|---|
| **미확인 예약 큐 + 확인(ack) 절차** | 알림은 유실됩니다. 받았다는 확인이 없으면 다시 보내야 합니다 | **Inbox 테이블** |
| **알림에 "누가 바꿨나" 표시** | 자기가 밀어넣은 변경이 자기에게 되돌아옵니다 | **에코 판별** |
| **현재 상태 조회 API** | 보낸 것이 실제로 반영됐는지 알 수 없습니다 | **drift 검출** |
| **채널별 노출 규칙 (전량이 아니라 규칙)** | 채널마다 다르게 보여야 하지만 재고를 쪼개지는 않습니다 | **정책 장부** |
| **알림 순서 보장 없음을 명시** | 순서를 보장하는 것보다 순서를 재구성하는 편이 쌉니다 | **순서 키 기반 처리** |

### 특히 값이 컸던 문장 두 개

**하나.** 공개 문서가 순서에 대해 이렇게 적습니다.

> 웹훅 호출의 순서는 이벤트 발생 순서와 다를 수 있다

그리고 웹훅을 **트리거로 쓰고 현재 상태는 조회로 확인하라**고 권고합니다.
알림을 만든 당사자가 알림의 내용을 믿지 말라고 하는 것입니다.

**둘.** 확인 절차의 순서를 이렇게 규정합니다.

> 성공적으로 저장했을 때만 확인(ack) 해야 한다. 확인되었다면 그것은 PMS 에 들어 있다는 뜻이다

이 두 문장이 2장 설계의 뼈대가 됩니다.

### 우리 재고 모델과 관련해 확인된 사실 하나

재고 전송은 **룸타입 단위 절대값**이며 채널별 값을 받지 않습니다.
채널별 차등은 규칙(전량 차단 / 일정 수 차감 / 상한)으로만 표현됩니다.

이것이 ADR-0001 의 hybrid 서술을 고치게 만든 근거입니다 —
**채널별 재고 카운터라는 것은 이 도메인에 존재하지 않습니다.**
존재하는 것은 **카운터 하나와 채널별 투영 규칙**입니다.

# 2. 우리가 만들 것

여기서부터 특정 제품 이야기는 없습니다. **우리 스키마와 우리 컴포넌트입니다.**

## 2.1 Inbox — 인바운드의 Outbox

### 지금 없는 것

현재 인바운드 경로는 이렇게 되어 있습니다.

```
웹훅 수신  →  [트랜잭션] 재고 변경 + 예약 저장  →  2xx 응답
```

문제는 **받았다는 사실이 어디에도 남지 않는다**는 점입니다.
처리 도중 죽으면 그 알림은 사라집니다. 채널이 재전송해 주기를 기대할 뿐입니다.

Outbox 를 도입한 이유와 정확히 같은 문제입니다.
Outbox 가 없으면 "DB 는 바뀌었는데 통보가 안 나간" 상태가 생기고,
Inbox 가 없으면 **"알림은 왔는데 처리는 안 된" 상태가 생깁니다.**

### 스키마

```sql
CREATE TABLE inbound_message (
    id              BIGSERIAL PRIMARY KEY,
    channel         VARCHAR(32)  NOT NULL,
    kind            VARCHAR(32)  NOT NULL,   -- BOOKING | POLICY
    external_id     VARCHAR(128) NOT NULL,   -- 채널이 부여한 식별자
    sequence_key    VARCHAR(128),            -- 순서 판정용. 없을 수 있다
    payload         JSONB        NOT NULL,   -- 받은 그대로. 해석하지 않는다
    status          VARCHAR(16)  NOT NULL,   -- PENDING | PROCESSED | IGNORED | DEAD
    received_at     TIMESTAMPTZ  NOT NULL,
    processed_at    TIMESTAMPTZ,
    attempt_count   INT          NOT NULL DEFAULT 0,

    UNIQUE NULLS NOT DISTINCT (channel, external_id, sequence_key)
);
```

`UNIQUE NULLS NOT DISTINCT (channel, external_id, sequence_key)` 가 이 테이블의 핵심 한 줄입니다.
`reservation` 의 `UNIQUE(channel, channel_reservation_id)` 가 예약의 중복 생성을 막는 것처럼,
이 제약이 **같은 알림의 재처리**를 DB 레벨에서 막습니다.

#### `NULLS NOT DISTINCT` 가 없으면 제약이 아무것도 막지 않습니다

`sequence_key` 는 **NULL 일 수 있습니다** — 순서키를 주지 않는 채널이 있기 때문입니다. 그리고
PostgreSQL 의 기본 동작에서 **NULL 은 NULL 과 같지 않습니다.** 그냥 `UNIQUE` 로 쓰면
`sequence_key IS NULL` 인 행은 서로 중복으로 판정되지 않습니다.

```
UNIQUE (channel, external_id, sequence_key)      -- 기본: NULLS DISTINCT

('YANOLJA', 'BK-1', NULL)   INSERT  ->  성공
('YANOLJA', 'BK-1', NULL)   INSERT  ->  성공   <- 같은 알림이 두 번 들어왔다
```

**순서키를 주지 않는 채널에서만 멱등이 뚫립니다.** 순서키를 주는 채널로 테스트하면
통과하므로 조용합니다. 그리고 이 테이블의 존재 이유가 그 하나이므로,
제약이 이렇게 새면 Inbox 를 둔 의미가 없습니다.

`NULLS NOT DISTINCT` 는 **PostgreSQL 15 이상**입니다. 이 저장소의 스택은 16 이므로 쓸 수 있고,
이 문장이 곧 **PostgreSQL 15 미만으로 내려갈 수 없다는 제약**이 됩니다.

> **`sequence_key NOT NULL DEFAULT ''` 로 바꾸는 안을 기각했습니다.** 동작은 같지만
> "채널이 순서키를 주지 않았다"와 "빈 문자열을 주었다"를 구분할 수 없게 됩니다.
> 순서 역전 판정(`#9` B4)이 그 구분을 씁니다.

`payload` 를 해석하지 않고 그대로 넣는 이유는, 수신을 최대한 빨리 끝내야 하기 때문입니다.
해석에서 실패해도 받은 사실은 남아야 합니다.

### 흐름 — 두 단계로 쪼갭니다

```
① 수신 (빠르게, 얕게)
   웹훅 도착
      → inbound_message INSERT   (중복이면 UNIQUE 위반 → 무시)
      → 즉시 2xx 응답             (절대 규칙 5)

② 처리 (별도 워커, 트랜잭션)
   PENDING 을 순서대로 꺼냄
      → [트랜잭션]  재고 변경
                    예약 upsert
                    outbox_event INSERT
                    inbound_message.status = PROCESSED
      → 커밋
```

### 이 구조가 없애는 문제

**확인(ack) 순서 문제가 사라집니다.**

큐가 채널 쪽에 있으면 "처리 후에 확인해야 한다"는 순서 규칙이 필요합니다.
확인을 먼저 하고 롤백되면 그 알림은 영구히 사라지기 때문입니다.

**큐를 우리가 들면 그 규칙 자체가 필요 없습니다.**
`status = PROCESSED` 를 도메인 변경과 **같은 트랜잭션**에서 쓰므로 원자적입니다.
둘이 함께 커밋되거나 함께 롤백됩니다.

```
외부 큐   :  처리 → 확인.  두 단계라서 순서가 문제가 된다
Inbox     :  처리와 표시가 한 트랜잭션.  순서라는 개념이 없다
```

**이것이 Outbox 의 논증과 완전히 동일합니다**(ADR-0003).
Outbox 는 "DB 변경과 이벤트 기록을 한 트랜잭션에 묶어" dual-write 를 없앱니다.
Inbox 는 "DB 변경과 처리 표시를 한 트랜잭션에 묶어" 같은 문제를 인바운드에서 없앱니다.

### 수신 실패 시

`inbound_message` INSERT 조차 실패하면 2xx 를 줄 수 없습니다. 5xx 를 줍니다.
채널은 재전송합니다 — at-least-once 의 정상 동작입니다.
한 번 이상은 반드시 보내지만 딱 한 번만 보낸다는 보장은 없다는 뜻입니다.
**우리가 지켜야 하는 것은 "2xx 를 줬으면 최소한 적어는 뒀다"** 뿐입니다.

## 2.2 웹훅 payload 를 상태에 반영하지 않습니다

순서 보장이 없다는 것은 이런 뜻입니다.

```
실제 발생 순서   :  예약 생성  →  예약 수정  →  예약 취소
알림 도착 순서   :  예약 취소  →  예약 생성  →  예약 수정      ← 이럴 수 있다
```

도착 순서대로 처리하면 **없는 예약을 취소하고, 취소된 예약을 되살립니다.**

### 두 가지 대응 — 채널이 무엇을 주느냐에 달려 있습니다

| 채널이 제공하는 것 | 우리 처리 |
|---|---|
| **현재 상태 조회 경로가 있습니다** | 웹훅은 트리거로만 씁니다. 워커가 조회해서 권위 있는 상태를 가져옵니다 |
| **순서 키(리비전 번호·시각)가 payload 에 있습니다** | `sequence_key` 에 넣고, 같은 `external_id` 안에서 순서대로 처리합니다 |
| **둘 다 없습니다** | 순서를 복원할 수 없습니다. **이 사실을 문서에 남기고 어댑터별 제약으로 표시합니다** |

세 번째 줄을 비워 두지 않는 것이 중요합니다.
**복원할 수 없는 채널이 있다는 사실 자체가 설계 정보입니다.** 그 채널은 drift 검출에 더 의존해야 합니다.

### 처리 순서 규칙

```
같은 external_id 안에서는  sequence_key 순서로 처리한다
서로 다른 예약끼리는       순서를 신경 쓰지 않는다
프로퍼티가 다르면          병렬로 처리해도 무해하다 — 재고 행이 겹치지 않는다
```

`ADR-0002` 가 재고 행을 `stayDate` 오름차순으로 잠가 데드락을 없앤 것과 같은 수법입니다.
**순서를 보장하는 가장 싼 방법은 순서를 정하는 것입니다.**

## 2.3 에코 판별 — 우리가 밀어넣은 것이 되돌아옵니다

우리가 채널에 "7개 남았다"를 보내면, 채널은 "값이 바뀌었다"는 알림을 우리에게 되돌려 줍니다.
그것을 다시 처리하면 무한 루프가 됩니다.

### 세 가지 판별 수단 — 있는 것부터 씁니다

| 수단 | 조건 | 신뢰도 |
|---|---|---|
| **변경 주체 식별자** | 채널이 payload 에 "누가 바꿨나"를 넣어 줍니다 | 높음 |
| **상관 식별자 대조** | 우리가 보낼 때 붙인 식별자가 알림에 돌아옵니다 | 높음 |
| **값 비교** | 알림의 값이 우리가 방금 보낸 값과 같으면 에코로 봅니다 | **낮음** |

세 번째는 최후 수단입니다. **우연히 같은 값일 수 있습니다.**
사장님이 손으로 바꾼 값이 우리 값과 우연히 일치하면, 진짜 조작을 에코로 오인해 버립니다.
값 비교만 가능한 채널은 그 한계를 문서에 남깁니다.

에코 판별에 성공하면 `status = IGNORED` 로 표시하고 끝냅니다.
**버리지 않고 표시하는 이유는, 나중에 "왜 반영되지 않았나"를 물을 수 있어야 하기 때문입니다.**

## 2.4 정책 장부 — 재고와 분리합니다

(3) 사람이 채널 화면에서 직접 바꾼 경우입니다. 판단 근거는 ADR-0009 에 있고 여기서는 형태만 적습니다.

핵심은 **`ari` 를 통째로 읽지 않고 필드별로 축에 배분한다**는 점입니다.
갈라 보면 채널 화면에서 사람이 하는 일의 **대부분이 정책**입니다 —
"오늘은 2개만 팔자"는 방이 2개가 되었다는 뜻이 아니라 **그 채널의 노출 상한이 2가 되었다**는 뜻입니다.

재고 축으로 넘어오는 것은 **`availability` 를 올린 경우** 하나이며,
그것은 오버부킹 한도 요청으로 번역됩니다. 배분 표와 번역 근거는 ADR-0009 에 있습니다.

```sql
CREATE TABLE channel_policy (
    room_type_id  BIGINT       NOT NULL,
    stay_date     DATE         NOT NULL,
    channel       VARCHAR(32)  NOT NULL,
    kind          VARCHAR(16)  NOT NULL,  -- CLOSED | CAP | OFFSET
    value         INT,
    source        VARCHAR(16)  NOT NULL,  -- OURS | CHANNEL   ← 누가 정했나
    updated_at    TIMESTAMPTZ  NOT NULL,

    PRIMARY KEY (room_type_id, stay_date, channel, kind)
);
```

`source` 컬럼이 이 테이블의 핵심입니다. **정책의 출처를 데이터로 둡니다.**
그래야 "이 값은 우리가 정했나 현장이 정했나"를 나중에 물을 수 있습니다.

### 판정

```
정책 알림 도착
   ├─ 에코다                      → IGNORED
   ├─ 장부와 같다                 → 아무것도 하지 않는다
   └─ 다르다
        ├─ 흡수 허용 목록에 있다   → 장부 갱신, source = CHANNEL
        └─ 그 외                   → 장부 값을 다시 밀어넣고 알린다
```

**기본값은 교정, 흡수는 허용 목록입니다.** 근거는 예약 축과의 대칭입니다 —
예약은 되돌릴 수 없으니 무조건 흡수하고, 정책은 되돌릴 수 있으니 기본은 교정합니다.
조용히 흡수하면 장부가 언제 왜 바뀌었는지 아무도 모릅니다.

### 불변식은 늘지 않습니다

```
재고 :  언제 어느 순간에도 참이어야 한다        → INV-1 · INV-2 · INV-3
정책 :  유한 시간 안에 장부 값으로 수렴하면 된다  → 불변식이 아니다
```

채널의 정책 값이 지금 우리 장부와 다른 것은 **위반이 아닙니다.** 다음 주기에 수렴하면 정상입니다.
따라서 이 설계는 `INV-` 를 하나도 추가하지 않고, **T1~T4 가 그대로 유효합니다.**

## 2.5 drift 검출 — 이미 백로그에 있습니다

우리가 보낸 값이 실제로 반영됐는지 확인하는 유일한 방법은 **읽어서 대조하는 것**입니다.

```
채널의 현재 값을 읽는다  →  우리 계산값과 비교  →  다른 것만 다시 보낸다
```

`06-backlog.md` 의 **B6(정기 재동기화)** 가 이것이고, **B1(diff 리포트)** 는 같은 대조를 사람에게 보여줍니다.

| | 하는 일 |
|---|---|
| B1 | 다른 것을 목록으로 보여줍니다. 사람이 판단합니다 |
| B6 | 다른 것을 고칩니다 |

지금까지 B6 은 "전량 재전송"으로만 서술되어 있었습니다.
**읽어서 다른 것만 보내는 편이 전량 재전송보다 낫습니다** — 레이트 리밋 소비가 적고,
무엇이 어긋났는지가 로그에 남기 때문입니다.

재고 전송이 **절대값**이라는 점이 여기서 값을 합니다.
같은 값을 몇 번 보내도 무해하고, 순서가 뒤집혔더라도 다음 주기가 최신값으로 덮어 자동 치유됩니다.

# 3. 취소와 수정

취소는 별도의 사건이 아니라 **같은 예약의 다음 상태**로 옵니다. 수정도 같습니다.
`external_id` 는 그대로이고 상태만 바뀝니다.

실제로 어려운 것은 네 가지이고, 전부 이미 열린 결정과 맞물립니다.

| 상황 | 문제 | 어디서 다루나 |
|---|---|---|
| 취소가 생성보다 먼저 도착 | 없는 예약을 취소합니다 | **2.2 순서 규칙으로 해소** |
| 체크인 이후 취소 | 재고를 복원하면 쓴 방이 다시 팔립니다 | #26 · #28 |
| 날짜 변경 수정 | 옛 날짜 복원 + 새 날짜 차감 + 예약 행을 한 트랜잭션에 | #27 (락 순서) |
| 배정분에서 팔린 예약의 취소 | 배정 잔여로 되돌리나 공유로 되돌리나 | 아래 |

### 배정 취소는 예약 시점에 결정합니다

보장형 hybrid(ADR-0001)를 쓰면 마지막 줄이 새로 생깁니다.

**취소 시점에 판정하지 않습니다. 예약 시점에 어디서 차감했는지를 예약 행에 기록합니다.**

```
reservation.deducted_from = ALLOTMENT | SHARED
```

기록해 두면 복원 대상이 조회로 결정됩니다. **판정 로직이 없으므로 틀릴 자리도 없습니다.**

`AGENTS.md` 절대 규칙 7(재고 복원은 `CONFIRMED -> CANCELED` 에서만)의 확장입니다 —
언제 복원하는가에 이어 **어디로 복원하는가를 데이터로 둡니다.**

# 4. 팬아웃 계수는 채널매니저를 경유하면 1입니다

`04-capacity-and-limits.md` 와 #18 은 통보 대상 채널 수를 용량 산정의 계수로 놓았습니다.

**채널매니저를 경유하면 그 계수가 1입니다.** 재고 전송이 룸타입 단위이고 채널별 값을 받지 않으므로,
팬아웃은 채널매니저 안에서 일어납니다.

```
우리  ──(1회)──▶  채널매니저  ──▶  채널 A
                              ──▶  채널 B
                              ──▶  채널 C
```

즉 **"어느 채널에 보낼지"라는 결정 자체가 이 구조에는 없습니다.**
#18 이 물은 팬아웃 대상 선택은 형태가 바뀝니다 —
보낼 채널을 고르는 문제가 아니라, **정책으로 제외할 채널을 고르는 문제**입니다.

계수가 N 으로 돌아오는 조건은 하나입니다. **채널매니저 없이 채널을 직접 연동하면** 돌아옵니다.
그때는 채널 수만큼 어댑터를 호출해야 합니다.

**어느 쪽을 택할지는 아직 결정하지 않았습니다.** 이 문서는 두 경우의 계수가 다르다는 사실만 남깁니다.

# 5. 순서와 증명

`06-backlog.md` 는 확정된 목록이며 이 문서가 항목을 추가하지 않습니다.
아래는 **대사 축이 성립하기 위한 순서**이며, 백로그와의 대응을 함께 적습니다.

| 순서 | 내용 | 대응 |
|---|---|---|
| 1 | **Inbox 테이블 + 워커.** 수신과 처리를 쪼갭니다 | 신규 (인바운드 축) |
| 2 | 순서 규칙 — `sequence_key` 기반 처리, 없는 채널은 제약으로 표시 | 신규 |
| 3 | drift 검출 — 읽어서 다른 것만 재발행 | **B6** 의 구현 형태 |
| 4 | 에코 판별 + 정책 장부 | ADR-0009 · #21 · #18 |
| 5 | 캡형 hybrid (노출 상한) | ADR-0001 재검토 조건 3 |
| 6 | 보장형 hybrid (배정 장부) | 연동 시점 확인 후 |

**1번이 값어치 대비 가장 쌉니다.** 테이블 하나와 워커 하나이고,
그것만으로 "알림은 왔는데 처리는 안 된" 상태가 사라집니다.

**4번이 두 개의 열린 문제를 동시에 닫습니다** — #21(역방향 쓰기)과 #18(에코).

5·6번은 4번 없이 성립하지 않습니다.
채널이 우리 정책을 지키는지 모르는 상태에서 채널별 정책을 얹으면 지킬 수 없는 약속이 늘어납니다.

## 증명해야 할 것

`AGENTS.md` 규약대로, 각 항목은 **깨뜨렸을 때 실패하는** 테스트를 가집니다.

| # | 증명 대상 | 깨뜨리는 방법 |
|---|---|---|
| T7 | 같은 알림을 두 번 받아도 예약이 중복 생성되지 않습니다 | `UNIQUE(channel, external_id, sequence_key)` 제거 |
| T8 | 처리 중 죽어도 알림이 유실되지 않고 다시 처리됩니다 | Inbox 를 거치지 않고 직접 처리하도록 되돌립니다 |
| T9 | 도착 순서가 뒤집혀도 최종 상태가 옳습니다 | `sequence_key` 정렬을 제거합니다 |
| T10 | 우리가 밀어넣은 변경의 알림은 장부를 바꾸지 않습니다 | 에코 판별을 제거합니다 |

**T8 이 가장 중요합니다.** 유실은 테스트 없이는 보이지 않습니다 —
성공한 것처럼 조용히 사라지기 때문입니다.

T9 는 이 저장소가 아웃바운드에서 이미 겪은 문제(B4)의 인바운드 대응물입니다.
`04-capacity-and-limits.md` 의 "순서는 인스턴스 수의 문제가 아니다"와 같은 성질입니다.

# 6. 실제 연동 시점에 확인할 것

이 문서의 설계는 특정 채널매니저에 의존하지 않습니다.
다만 **실제로 연동을 붙이는 시점**에는 상대가 무엇을 주는지 확인해야 합니다.

| 확인 대상 | 없으면 어떻게 되나 |
|---|---|
| 현재 상태 조회 경로가 있는가 | 없으면 웹훅 payload 를 믿어야 합니다. 순서 위험을 감수합니다 |
| 순서 키(리비전·시각)가 있는가 | 없으면 순서를 복원할 수 없습니다. drift 검출에 더 의존합니다 |
| 변경 주체 식별자가 있는가 | 없으면 에코 판별이 값 비교로 내려갑니다. 오인 위험이 있습니다 |
| 읽기가 레이트 리밋을 소비하는가 | 소비하면 drift 검출 주기가 쓰기 예산을 잠식합니다 |
| 채널별 정책 규칙의 표현 범위 | 좁으면 보장형 hybrid 를 표현할 수 없습니다 |

구체적 측정 절차는 `docs/experiments/channex-unknowns.md` 에 있습니다.
**지금 필요한 것이 아닙니다.** 연동 대상이 정해진 뒤에 실행합니다.
