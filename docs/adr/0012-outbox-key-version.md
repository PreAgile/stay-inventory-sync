# ADR-0012. Outbox 에 키 단위 버전을 붙여 순서 역전을 막는다

## 상태
확정

## 맥락

`ADR-0003` 이 Outbox 를 도입하면서 백오프(`next_attempt_at` · `retry_count`)를 함께 들였다.
**그 순간 발행 순서가 생성 순서와 달라진다.**

```
t1  (룸타입A, 3/15) 예약 → 3→2   #1 생성, 발행 실패 → +1분 뒤 재시도
t2  (룸타입A, 3/15) 취소 → 2→3   #2 즉시 발행 성공 → 채널 잔여 3  ✓
t3  #1 재시도 성공               → 채널 잔여 2  ✗  실제는 3
```

**인스턴스 수의 문제가 아니다.** 단일 릴레이에서도 백오프만 있으면 일어난다.
`docs/04-capacity-and-limits.md` 가 *"4번(백오프)을 구현한 순간 5번(순서 보장)이 깨진다"* 로
이미 지적한 항목이다.

결과는 기회손실이고, **반대 방향이면 오버부킹**이다 — 이 저장소가 막겠다고 선언한 실패다.

외부 요구와도 맞다. 주요 OTA 는 오래된 메시지가 나중에 도착해 최신 정보를 덮어쓰지 않게 하는 것을
**연동사 책임**으로 규정한다. **수신 측이 정렬해 주지 않는다.**

---

## 결정

**`outbox_event` 에 `(room_type_id, stay_date)` 키와 그 키 안에서 단조 증가하는 `version` 을 둔다.**
릴레이는 같은 키의 더 큰 버전이 **이미 발행됐으면** 그 이벤트를 보내지 않고 `SUPERSEDED` 로 표시한다.

같은 판정을 **배치 안에서도** 적용한다. 한 번에 집은 이벤트들 중 같은 키가 여럿이면
가장 새 것만 보낸다.

### 단조성을 보장하는 것은 시퀀스가 아니라 기존 락이다

```kotlin
version = SELECT COALESCE(MAX(version), 0) + 1
            FROM outbox_event WHERE room_type_id = ? AND stay_date = ?
```

이 읽기-쓰기 사이에 다른 트랜잭션이 끼어들면 두 이벤트가 같은 번호를 받고,
그러면 `>` 비교가 어느 쪽도 낡았다고 판정하지 못해 방어가 통째로 사라진다.

**그 경합은 이미 막혀 있다.** 같은 키의 통보를 만드는 모든 트랜잭션은
그 `(room_type_id, stay_date)` 의 `daily_inventory` 행을 `FOR UPDATE` 로 잠그고 지나간다
(`ADR-0002` · 절대 규칙 2). **재고 카운터를 직렬화하는 락이 버전도 함께 직렬화한다.**

새 동시성 장치를 들이지 않았다는 것이 이 결정의 값어치다.
그리고 **그래서 이 결정은 락 순서 규칙에 종속된다** — 재고 락 없이 통보를 만드는 경로가
생기면 버전의 단조성이 조용히 깨진다.

### 건너뛴 이벤트를 `PUBLISHED` 로 적지 않는다

`SUPERSEDED` 상태를 새로 둔다. 발행한 적이 없는데 발행했다고 적으면
*"왜 채널에 안 갔는가"* 를 되짚을 수 없고, 지표(`#10`)에서 발행량이 부풀려진다.

## 기각한 대안 1: 전역 단조 시퀀스

키를 두지 않고 `outbox_event.id` 순서만으로 판정하는 안.

**모든 키가 하나의 순서에 묶인다.** 3/15 의 통보가 백오프에 걸려 있으면
3/16 의 통보도 "더 오래된 것이 아직 안 나갔다" 는 이유로 대기하거나,
아니면 순서 보장이 아무 의미가 없어진다.

키가 다르면 순서를 비교할 이유가 없다 — 채널에서 서로 다른 날짜의 재고는 독립적인 값이다.

---

## 기각한 대안 2: 수신 측이 버전을 보고 거절하게 한다

가장 깨끗한 해법이다. 요청에 버전을 실어 보내고 채널이 낡은 것을 거절하면
발행 측은 순서를 신경 쓸 필요가 없다.

**채널 API 가 그 기능을 제공하지 않는다.** 그리고 제공하지 않는 이유가
순서 보장을 연동사 책임으로 규정했기 때문이다 — 즉 이 대안은 그들이 이미 거절한 것이다.

---

## 기각한 대안 3: 키별 `last_sent_version` 워터마크 테이블

발행 성공 시 키별 워터마크를 갱신하고, 그보다 낮은 버전은 보내지 않는 안.

**갱신 시점이 여전히 외부 호출 뒤다.** 채널 호출은 성공했는데 워터마크를 쓰기 전에
죽으면 낡은 재시도가 검사를 통과한다. 지금 채택한 방식(`PUBLISHED` 상태를 보는 것)과
**같은 창이 남고, 테이블만 하나 는다.**

폭을 줄이는 효과는 있지만 0 으로 만들지 못한다. 그 창의 최종 방어선은 순서가 아니라
**재동기화**이며 `#23`(B6)이 담당한다.

---

## 기각한 대안 4: 타임스탬프 비교 (LWW)

`ADR-0009` 가 이미 기각했다. 시계 신뢰성·정밀도·동률 처리가 확인되기 전에는 쓰지 않는다.
버전은 우리가 만드는 값이므로 그 셋이 모두 통제 아래 있다.

---

## 기각한 대안 5: 키별 단일 처리자 (파티셔닝)

키를 해시해 인스턴스에 나눠 주면 같은 키가 한 인스턴스에서만 처리되므로 순서가 보장된다.

**문제를 잘못 짚었다.** 순서 역전은 인스턴스가 여럿이라서 생기는 것이 아니라
**백오프 때문에 생긴다.** 단일 인스턴스로 줄여도 그대로 남는다.
그리고 인스턴스 소유권을 관리하는 순간 재분배·장애 감지가 따라온다 — `ADR-0004` 가
Kafka 를 미룬 것과 같은 이유로 이 규모에서 정당화되지 않는다.

---

## 결과

- **발행-마킹 창은 여전히 남는다.** `PUBLISHED` 마킹이 외부 호출 뒤에 일어나므로,
  호출 성공 직후 죽으면 낡은 재시도가 검사를 통과한다.
  `T4` 가 다루는 창과 같은 창인데 **결과의 성격이 다르다** —
  중복 발행은 멱등하게 흡수되지만 **낡은 값 재전송은 흡수되지 않는다.**
  창을 0 으로 만드는 대신 유한 시간 안에 스스로 고쳐지게 한다 → `#23`
- 배치 내 병합이 같은 메커니즘으로 해결되어 레이트 리밋 소비가 준다
- `INV-1` ~ `INV-4` 는 늘지 않는다. 이 결정은 내부 상태가 아니라 **발행 순서**에 관한 것이다

## 검증

`OutboxVersionStampTest` — 백오프에 빠진 낡은 통보가 재시도에서 채널 상태를 되돌리지 않는다.
**버전 스탬프를 제거하면 이 테스트가 실패해야 한다.**
