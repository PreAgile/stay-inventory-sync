# ADR-0013. 순서키를 어댑터가 정규화하고, 늦게 온 생성은 묘비로 막는다

## 맥락

`inbound_message.sequence_key` 는 `VARCHAR(128)` 이고 워커의 조회가 이렇게 정렬했다.

```sql
ORDER BY external_id, sequence_key NULLS FIRST, id
```

**문자열 정렬이다.** 실측하면 이렇게 된다.

```
 sequence_key |  ev
--------------+------
 10           | 취소     ← 먼저 처리된다
 2            | 생성
```

그 결과가 이 순서로 이어진다.

1. 취소(rev `10`)가 먼저 처리되고, 예약이 없으므로 `IGNORED`
2. 이어서 생성(rev `2`)이 처리되어 **예약이 확정된다**
3. **최신 상태인 취소가 사라진다** — 팔리지 않아야 하는 방이 팔린 채 남는다

**순서 역전을 막으려고 넣은 정렬이 숫자 키에서는 역전을 만들었다.**

코드 주석은 이 상황을 이미 예상하고 있었다 — *"없는 예약의 취소. 생성 알림이
아직 안 왔거나 순서가 뒤집혔다."* 뒤집힘을 **외부 요인으로만** 보고 정렬 자체가
원인이 될 수 있다는 것은 보지 못했다.

## 정렬만 고쳐도 부족하다

정렬은 **한 배치 안에서만** 순서를 정한다. 취소와 생성이 서로 다른 폴링 주기에
도착하면 정렬이 개입할 자리가 없다.

```
주기 1:  취소(rev 10) 도착 → 예약 없음 → IGNORED
주기 2:  생성(rev 2)  도착 → 예약 확정
         → 취소가 사라진다. 정렬은 아무 역할도 하지 않았다
```

**두 개를 같이 고쳐야 한다.**

| 문제 | 고치는 것 |
|---|---|
| 같은 배치 안의 역전 | 정렬을 비교 가능한 값으로 |
| **배치를 넘는 역전** | **이미 본 취소를 기억한다 (묘비)** |

## 결정

### 1. 어댑터가 순서키를 비교 가능한 값으로 정규화한다

`sequence_key` 형식은 채널마다 다르다 — 숫자 리비전, ISO 타임스탬프, 불투명 문자열.
**한 컬럼으로 비교하려면 정규화가 선행이고, 형식을 아는 것은 어댑터다.**

```kotlin
fun sequenceRank(sequenceKey: String?): Long?
```

결과를 `inbound_message.sequence_rank` 에 저장하고 정렬이 그것을 쓴다.

**원본 `sequence_key` 는 그대로 보존한다.** `payload` 를 받은 그대로 두는 것과 같은
이유이고, 멱등 판정(`UNIQUE NULLS NOT DISTINCT`)도 **원본**에 걸린 채로 둔다 —
정규화가 두 값을 같은 rank 로 뭉개도 서로 다른 알림이라는 사실은 남아야 한다.

### 2. 정규화할 수 없으면 `null` 이다

불투명 문자열은 순서를 복원할 수 없다. 그때 `sequence_rank` 는 `null` 이고
정렬은 도착 순서(`id`)로 떨어진다.

**이것을 숨기지 않는다.** 복원할 수 없는 채널이 있다는 사실 자체가 설계 정보이고,
그 채널은 drift 검출에 더 의존해야 한다(`docs/07-reconciliation.md`).

### 3. 늦게 온 생성은 묘비가 막는다

생성 알림을 처리할 때 **같은 `(channel, external_id)` 에 더 높은 rank 의 취소가
이미 기록돼 있으면** 그 생성은 낡은 것이므로 `IGNORED` 다.

```
이미 받은 것:  취소 rank=10  (IGNORED — 예약이 없었다)
지금 온 것:    생성 rank=2
판정:          생성이 낡았다 → IGNORED. 예약을 만들지 않는다
```

**"이미 본 것" 을 근거로 판정하므로 `inbound_message` 가 곧 묘비다.**
별도 테이블을 만들지 않는다 — 받은 사실을 그대로 보존하는 것이 Inbox 의 임무이고,
그 기록이 이미 필요한 정보를 갖고 있다.

## 기각한 대안

### (1) `sequence_key` 를 숫자 컬럼으로 바꾼다

형식이 채널마다 다르므로 성립하지 않는다. ISO 타임스탬프를 주는 채널의 값을
`BIGINT` 컬럼에 넣을 수 없고, 넣으려면 어차피 정규화가 필요하다.
**그러면 원본을 잃는다.**

### (2) 정렬을 `id`(도착 순서)로만 한다

순서키를 주는 채널의 정보를 버리는 것이다. 그리고 도착 순서는 채널의 재시도
때문에 실제 사건 순서와 다르다 — **at-least-once 에서 도착 순서는 순서가 아니다.**

### (3) 취소를 `PENDING` 으로 남겨 재시도한다

원래 코드가 이것을 이미 기각했다 — *"PENDING 으로 남기면 무한 재시도가 된다."*
생성이 영영 오지 않는 취소(에코·오발송)가 큐를 영구히 점유한다.

### (4) 생성을 확정한 뒤 취소를 다시 적용한다

재고를 한 번 깎고 되돌린다. 결과는 같지만 **그 사이에 다른 예약이 그 방을 볼 수
있고**, 무엇보다 `outbox_event` 가 두 번 나가 채널에 잘못된 중간 상태를 보낸다.
**중간 상태를 만들지 않는 쪽이 낫다.**

## 결과

- 같은 배치 안의 역전은 `sequence_rank` 정렬이 막는다
- 배치를 넘는 역전은 묘비 검사가 막는다
- **rank 가 `null` 인 채널은 둘 다 성립하지 않는다.** 그 사실을 어댑터별 제약으로
  표시하고 drift 검출에 맡긴다
- 정규화 실패는 조용하지 않다 — `sequence_rank IS NULL` 인 비율이 관측 대상이다

## 이 결정이 만드는 새 제약

**어댑터가 순서키의 형식을 알아야 한다.** 지금까지 어댑터는 payload 의 구조를
모르는 것이 규칙이었다(`ArchitectureTest`). 순서키는 **payload 가 아니라 메타데이터**
이므로 그 규칙과 충돌하지 않지만, 경계가 한 칸 넓어진 것은 사실이다.

넓힌 근거는 **다른 곳에 둘 자리가 없다는 것**이다. 도메인이 형식을 알면 채널이
하나 늘 때 도메인이 바뀐다. 그것이 어댑터를 둔 이유다.
