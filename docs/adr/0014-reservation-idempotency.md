# ADR-0014. 예약 생성의 멱등 키는 호출부가 줍니다

## 맥락

`POST /reservations` 는 응답을 못 받은 클라이언트가 재시도하면 **중복 예약을
만들었습니다.**

```kotlin
channelReservationId = request.channelReservationId ?: UUID.randomUUID().toString()
```

**요청마다 새 키가 생깁니다.** `UNIQUE (channel, channel_reservation_id)` 는 살아
있는데 **판정 대상이 사라졌습니다** — 재시도가 서로 다른 두 요청으로 보입니다.

이 UUID 는 원래 반대 목적으로 들어왔습니다. 주석이 그렇게 적고 있습니다 —
*"NULL 을 허용하면 `UNIQUE` 가 직접 예약을 막지 못한다."* `NULL` 을 없앤 판단은
맞았지만, **키를 서버가 만들면 그 제약이 재시도를 식별할 수 없습니다.**

그리고 키를 **주는** 경우에도 중복은 `500` 이었습니다. `DataIntegrityViolationException`
을 잡지 않고 `@ControllerAdvice` 도 없습니다. 테스트가 그 사실을 그대로 단언합니다 —
*"이 슬라이스는 아직 멱등 처리를 하지 않는다."*

**같은 저장소의 웹훅 경로는 이 문제를 이미 3중으로 풀었습니다.** 취소는 더 나아가
이미 취소된 것도 `200` 을 줍니다. **직접 예약만 그 규율 밖에 있었습니다.**

## 결정

### 1. 멱등 키는 호출부가 줍니다. 서버가 만들지 않습니다

> **멱등은 서버가 혼자 만들 수 없습니다.** "같은 요청" 을 정의하는 것은 호출부이고,
> 호출부가 키를 주지 않으면 서버가 볼 수 있는 것은 서로 다른 두 요청뿐입니다.

키의 출처를 둘로 받습니다.

| 경로 | 키 |
|---|---|
| 채널 예약 | `channelReservationId` (채널이 부여한 식별자) |
| 직접 예약 | **`Idempotency-Key` 헤더** |

**둘 다 없으면 `400` 입니다.** 서버가 대신 만들지 않습니다.

### 2. 중복은 `409` 가 아니라 `200` 이고, 기존 예약을 돌려줍니다

재시도한 호출부가 알고 싶은 것은 "실패했나" 가 아니라 **"내 예약이 어떻게 됐나"**
입니다. 기존 예약의 id 를 그대로 주면 재시도가 **첫 시도와 같은 답**을 받습니다.

취소가 이미 그 형태입니다 — `ALREADY_CANCELED` 에도 `2xx` 를 줍니다(절대 규칙 5).

### 3. 판정은 DB 가 합니다

애플리케이션이 먼저 조회해서 이미 있으면 그것을 돌려주는 것만으로는 부족합니다 —
**읽기와 쓰기 사이에 다른 요청이 들어옵니다.** 웹훅 경로와 같은 2단 방어를 씁니다.

| 층 | 무엇 | 막는 것 |
|---|---|---|
| 조기 조회 | `findByChannelAndChannelReservationId` | 흔한 재시도 |
| `UNIQUE` 위반 포착 | `DataIntegrityViolationException` | 경합으로 조기 조회가 뚫린 경우 |

두 번째 방어가 없으면 동시 재시도 둘이 모두 조기 조회를 통과해 하나가 `500` 으로
죽습니다.

## 기각한 대안

### (1) 서버가 UUID 를 만들되 요청 본문 해시를 키로 씁니다

같은 내용의 **서로 다른 두 예약**을 구분할 수 없습니다. 같은 손님이 같은 날짜에 방
둘을 따로 잡는 것은 정상이고, 해시는 그것을 재시도로 봅니다.
**기회손실이 중복 예약보다 낫다는 보장이 없습니다.**

### (2) 중복에 `409` 를 줍니다

채널이 `4xx` 를 실패로 보고 **최대 24시간 재시도합니다**(절대 규칙 5).
재시도할 때마다 `409` 를 받으므로 영구히 반복됩니다.

### (3) `channelReservationId` 를 무조건 필수로 만듭니다

동작은 맞지만 **직접 예약에 채널 식별자를 요구하는 이름**이 됩니다. 호출부가
"채널 예약 번호" 를 만들어 넣게 되고, 그 값이 무엇을 뜻하는지 아무도 모릅니다.
`Idempotency-Key` 는 **그 값이 멱등 키라는 것을 이름이 말합니다.**

### (4) 재시도 창을 시간으로 둡니다 (예: 5분 안의 같은 요청은 중복)

시계에 의존합니다. 그리고 창 밖의 재시도는 다시 중복 예약을 만듭니다 —
**"대개 막힌다" 는 정합성 보장이 아닙니다.**

## 결과

- 재시도가 첫 시도와 같은 답을 받습니다
- 키가 없으면 **거부합니다.** 조용히 중복을 만들지 않습니다
- 판정이 DB 제약에 남으므로 경합으로 뚫리지 않습니다
- **`Idempotency-Key` 는 `channel` 과 함께 키를 이룹니다.** 두 채널이 같은 헤더 값을
  보내도 서로 다른 예약입니다 — 기존 `UNIQUE (channel, channel_reservation_id)` 를
  그대로 씁니다

## 이 결정이 남기는 것

**호출부가 키를 만들 책임을 집니다.** 우리 프론트엔드도 호출부이고, 그쪽이 재시도할
때 같은 키를 보내야 합니다. 그것을 안 하면 이 ADR 은 아무것도 막지 못합니다 —
**서버가 할 수 있는 것은 키가 없을 때 거부하는 것까지입니다.**
