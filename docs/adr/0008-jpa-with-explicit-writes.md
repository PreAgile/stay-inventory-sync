# ADR-0008. JPA를 쓰되 암묵적 쓰기를 봉인합니다

## 상태
확정 (재검토 조건 명시)

## 맥락

ADR-0001~0006은 모두 **기각한 대안**을 가지고 있습니다. 영속성 매핑 계층만 그것이 없습니다.

JPA는 선택된 적이 없고 **전제되어 있었습니다.**
`AGENTS.md`의 기술 스택, ADR-0005의 `data class` 금지 규칙,
`01-domain-model.md`의 컴파일러 플러그인 설명 —
전부 "JPA를 쓴다"를 이미 참으로 놓고 시작합니다.

이 질문은 ADR-0006에서 파생됐습니다.
**"블로킹 JDBC라서 코루틴·가상 스레드가 이득이 없다"면,
그 JDBC 위에 JPA를 얹는 것은 별도로 답변되어야 합니다.**

### 먼저 두 축을 분리합니다

| 축 | 선택지 | ADR-0006에 영향 |
|---|---|---|
| 전송 계층 | JDBC ↔ R2DBC | **있음** — 커넥션 점유 모델이 바뀝니다 |
| 매핑 계층 | JPA ↔ jOOQ ↔ JdbcTemplate | **없음** — 셋 다 아래는 블로킹 JDBC입니다 |

JPA를 걷어내도 여전히 블로킹 JDBC이므로 ADR-0006의 결론은 이 ADR과 무관하게 성립합니다.
**이 ADR이 다루는 것은 매핑 계층뿐입니다.** 전송 계층은 기각한 대안 3에서 함께 봅니다.

## 결정

**JPA(Hibernate)를 씁니다. 단, 암묵적 쓰기 경로를 구조적으로 봉인합니다.**

1. 엔티티 간 **연관 매핑을 두지 않습니다.** 참조는 ID 값으로만 가집니다
2. 재고 변경은 `InventoryService`를 통한 명시적 경로로만 일어납니다 (기존 규칙 유지)
3. Outbox 릴레이의 폴링·발행 경로는 JPA를 쓰지 않습니다

3번은 B3(`FOR UPDATE SKIP LOCKED`)가 JPA 표준에 없기 때문이기도 합니다.
Hibernate 확장이나 네이티브 쿼리로 내려가야 하는 코드를 리포지토리 관례로 위장하지 않습니다.

## 근거 1 — JPA가 파는 것의 대부분이 이미 억제되어 있습니다

| JPA가 파는 것 | 이 시스템에서 |
|---|---|
| 객체 그래프 탐색, 지연 로딩 | 프록시가 `equals`/`hashCode`를 깨뜨려 방어 코드를 따로 씁니다 (ADR-0005) |
| dirty checking | 재고 변경은 락을 잡고 하는 단일 카운터 갱신입니다 |
| JPQL로 얻는 DB 독립성 | PostgreSQL 고정. H2조차 락 동작이 달라 쓰지 못합니다 (절대 규칙 8) |
| 표준 락 API | `@Lock`으로 `FOR UPDATE`는 되지만 `SKIP LOCKED`는 표준에 없습니다 |
| 보일러플레이트 절감 | Kotlin 때문에 noArg·allOpen 플러그인이 **추가**되고, 엔티티만 `data class` 금지라는 예외 규칙이 붙습니다 |

`daily_inventory`는 카운터 성 행이고(`physical_total` · `overbooking_limit` · `sold` —
ADR-0007 이 컬럼을 셋으로 늘렸지만 성질은 같습니다), `outbox_event`는 INSERT와 폴링 UPDATE뿐입니다.
**두 테이블 모두 ORM이 기여할 여지가 거의 없습니다.**

남는 이득은 두 개입니다 — `Reservation` 애그리게잇의 상태 전이 매핑,
그리고 Spring Data의 트랜잭션·리포지토리 관례.

### 테이블이 셋 늘었고, 셋 다 이 근거를 강화합니다

초안을 쓴 뒤 `inventory_hold`(ADR-0010) · `inbound_message` · `channel_policy`(ADR-0009)가 추가됐습니다.
**셋 다 행 단위이며 상태 전이를 가진 애그리게잇이 아닙니다.**

| 테이블 | 성질 | ORM 기여 |
|---|---|---|
| `inventory_hold` | 행 삽입 + `released_at` 마킹 | 없습니다 |
| `inbound_message` | 행 삽입 + `status` 마킹. `payload` 는 `JSONB` 로 **해석하지 않습니다** | 없습니다 |
| `channel_policy` | 키 단위 upsert | 없습니다 |

**테이블이 5개에서 8개가 됐는데 애그리게잇은 여전히 `Reservation` 하나입니다.**
이것은 근거 1을 강화합니다 — 새 테이블 셋에도 객체 매핑이 기여할 여지가 없습니다.

**다만 이것이 "JPA 를 걷어낼 신호" 는 아닙니다.** 애그리게잇 수가 아니라
`Reservation` 의 매핑이 여전히 상태 기계를 표현하는지가 판정 기준입니다 — 재검토 조건 4 를 보십시오.

## 근거 2 — 그럼에도 걷어내지 않는 이유

- **`Reservation`은 상태를 가진 애그리게잇입니다.**
  상태가 **9개**이고 전이가 11개입니다 — 선점(`HELD`) · 승인 대기(`PENDING_APPROVAL`) ·
  확정 · 체크인 · 체크아웃 · 노쇼(`TERMINATED`) · 취소 · 만료 · 거절(ADR-0010).
  그리고 절대 규칙 7의 비대칭(복원은 `CONFIRMED -> CANCELED` 에서만)과
  점유·선점·어느 쪽도 아님 **세 집합 구분**이 여기 붙습니다.
  카운터가 아니라 도메인 객체의 문제이며, **초안을 쓸 때(상태 3개)보다 이 근거가 세졌습니다.**
  여기서는 엔티티 매핑의 값이 실재합니다
- **이 프로젝트의 주장은 정합성 설계입니다.**
  영속성 계층에서 관례를 벗어나면 주장과 무관한 곳에서 읽는 비용이 늘어납니다.
  ADR-0005가 "언어 기능을 넓게 쓰지 않으므로 Kotlin으로 충분하다"고 판단한 것과 같은 논법입니다
- **전환 비용이 비대칭입니다.**
  JPA → JDBC는 리포지토리 구현 교체라 국소적입니다.
  반대로 지금 jOOQ를 넣으면 코드 생성이 빌드 파이프라인에 들어옵니다.
  **Tier 0 완결 전에 지불할 비용이 아닙니다**

## 근거 3 — 진짜 비용은 성능이 아니라 dirty checking이 규칙을 우회한다는 것

`03-testing-strategy.md`의 아키텍처 규칙 중 하나는 이것입니다.

> 재고를 변경하는 코드는 `InventoryService`를 통해서만 접근한다

ArchUnit은 **정적 참조**를 검사합니다. 그런데 dirty checking은 정적 참조 없이 UPDATE를 만듭니다.

```kotlin
@Transactional
fun somethingElse(id: Long) {
    val roomType = roomTypeRepository.findById(id).get()
    roomType.dailyInventories.first().sold += 1   // InventoryService도 Repository도 안 거친다
}                                                 // 커밋 시 flush. UPDATE 가 나간다
```

`InventoryRepository`에 대한 참조도, `InventoryService`에 대한 참조도 생기지 않는데
**쓰기는 일어납니다.** 규칙이 잡지 못합니다.

이것은 성능 문제가 아닙니다.
이 저장소는 *"이건 리뷰로 막을 게 아니라 컴파일 타임에 막는다"*를
아키텍처 테스트의 존재 이유로 내세웠습니다.
**막겠다고 선언한 것을 채택 기술이 우회 가능하게 만든다면, 선언 쪽이 거짓이 됩니다.**

그래서 결정의 절반이 봉인입니다.

| 우회 경로 | 봉인 | 강제 수단 |
|---|---|---|
| 연관을 타고 들어가 필드 변경 | 연관 매핑 자체를 두지 않습니다 | ArchUnit (신규) |
| 조회한 재고 엔티티의 필드 변경 | `InventoryService` 경유만 허용 | ArchUnit (기존) |
| 릴레이가 도메인 엔티티를 건드림 | 릴레이 경로는 JPA 를 쓰지 않습니다 | ArchUnit (신규) |

연관 매핑을 두지 않으면 지연 로딩 프록시도 사라지므로,
ADR-0005의 `data class` 금지 근거 중 **프록시 초기화 항목은 약해집니다.**
그래도 규칙은 유지합니다 — 비영속/영속 상태의 해시가 달라지는 문제는 프록시와 무관하게 남습니다.

**연관 매핑을 두지 않는다는 것은 "JPA 를 JPA 답게 쓰지 않는다"는 뜻입니다.**
이 대가를 인정하고 적습니다. 근거 1의 결론과 일치합니다 —
이 시스템에서 JPA 는 객체 그래프 도구가 아니라 **행 매퍼로만 쓰입니다.**

## 기각한 대안 1: 순수 JdbcTemplate / Spring Data JDBC

- **얻는 것**: 모든 쓰기가 명시적 statement 가 되어 근거 3의 문제가 원천 소멸합니다.
  정적 강제가 완전해집니다
- **잃는 것**: `Reservation` 상태 전이 매핑을 손으로 씁니다
- **판단**: 근거 3을 봉인으로 닫을 수 있다면 이 대안의 **가장 큰 우위가 사라집니다.**
  닫지 못한다고 판명되면 이쪽으로 갑니다 → 재검토 조건 1

  **"유일한" 이라고 쓰지 않습니다.** 상태 전이 매핑을 JPA 로 하는 비용과 손으로 쓰는 비용의
  비교는 **구현 전에 산출할 수 없습니다.** 지금 확실한 것은 하나입니다 —
  `ADR-0010` 이 상태를 3개에서 9개로, 전이를 11개로 늘렸으므로
  **손으로 쓰는 쪽 비용도 함께 늘었습니다.** 어느 쪽이 더 큰지는 재검토 조건 1 의 판정 시점에 봅니다.

## 기각한 대안 2: jOOQ

- **얻는 것**: 타입 세이프 SQL. `SKIP LOCKED`, 윈도우 함수 등 PostgreSQL 기능을 그대로 씁니다.
  B3·B4 구현에 유리합니다
- **잃는 것**: 코드 생성이 빌드에 들어오고 스키마 변경마다 재생성이 필요합니다.
  Flyway 와 순서 결합이 생깁니다
- **판단**: 현재 SQL 복잡도가 그 비용을 정당화하지 않습니다 → 재검토 조건 2

  **다만 "네이티브 쿼리 서너 개" 는 지금 산출할 수 없는 수치입니다.** 저장소에 구현 코드가 0개입니다.
  그래서 판정 기준을 재현 가능하게 적습니다.

| | |
|---|---|
| **집계 대상** | 리포지토리 인터페이스의 메서드 중 **`@Query(nativeQuery = true)` 또는 Hibernate 확장을 쓰는 것** |
| **분모** | 그 리포지토리들의 전체 메서드 수 |
| **판정 시점** | **`#8`(B3) · `#9`(B4) 구현 직후.** 두 항목이 `SKIP LOCKED` 와 조건부 skip 을 요구하므로 네이티브 비율이 가장 높아지는 지점입니다 |
| **현재 수치** | **산출 불가** — 구현이 없습니다 |

**즉 이 기각은 "지금 시점의 유예" 이며 판정은 미룹니다.** 산출할 수 없는 수치를 근거로 적으면
그 근거는 검증되지 않습니다.

## 기각한 대안 3: R2DBC

ADR-0006의 근거 1을 실제로 흔들 수 있는 **유일한** 대안이므로 따로 봅니다.

- 커넥션 점유 모델을 바꾸는 것은 맞습니다. 그러나 이 시스템의 대기는
  `SELECT FOR UPDATE` 로 **행 락을 쥔 트랜잭션**이 만듭니다.
  논블로킹으로 옮겨도 **트랜잭션이 사는 동안 커넥션은 그대로 점유됩니다.**
  없어지는 것은 대기 스레드 비용뿐인데, 그것은 ADR-0006 근거 1이 이미 기각한 편익입니다
- 더해 JPA 가 사라지고 `@Transactional` 의 ThreadLocal 전파가 리액티브 컨텍스트로 바뀝니다.
  **절대 규칙 3(Outbox 동일 트랜잭션)의 검증 난이도가 올라갑니다.**
  이 프로젝트가 증명하려는 명제 바로 그 지점입니다
- **판단**: 편익 대비 비용이 크게 어긋납니다

## 기각한 대안 4: 혼합 — 예약은 JPA, 재고·Outbox 는 JDBC

가장 정직한 답에 가깝습니다. 실제로 **부분 채택했습니다** — 결정 3번(릴레이 경로는 JPA 미사용)이 그것입니다.

재고까지 분리하지 않는 이유는 **재고와 예약이 같은 트랜잭션 안에서 함께 변경되기 때문입니다.**
한 트랜잭션에 두 접근 방식이 섞이면 flush 시점과 락 획득 순서(절대 규칙 2)의 관계를
추론하기 어려워집니다.

**경계는 트랜잭션 경계와 일치해야 합니다.**
릴레이는 커밋 이후에 도는 별도 트랜잭션이므로 분리해도 이 원칙을 깨지 않습니다.

## 재검토 조건

다음 중 하나가 참이 되면 이 ADR 을 재검토합니다.

1. 연관 매핑 금지를 ArchUnit 으로 강제할 수 없다고 판명 → 대안 1
2. B3·B4 구현 후 네이티브 쿼리가 리포지토리의 절반을 넘음 → 대안 2
3. 요청 경로에서 **커넥션을 점유하지 않는** I/O 대기가 지배적이 됨 → ADR-0006 과 함께 대안 3
4. **`Reservation` 의 상태 전이를 조건부 UPDATE 로만 처리하게 되어 엔티티 매핑이
   상태 기계를 표현하지 않게 됨** → JPA 의 마지막 근거가 사라집니다 → 대안 1

   `#26` 이 복원을 조건부 UPDATE(`WHERE status = 'CONFIRMED'`)로 정한 것이 이 방향의 첫 걸음입니다.
   `ADR-0010` 의 확정 전이도 같은 형태이므로, **구현 시점에 전이 대부분이 이 형태가 되는지 봅니다.**

   > **초안의 조건은 "애그리게잇이 `Reservation` 하나로 끝남" 이었습니다. 바꿨습니다.**
   > 테이블이 8개인데 애그리게잇은 하나이므로 **문자 그대로는 이미 참인데 결론은 그대로**여서
   > 조건이 판정력을 잃었습니다. 지금 대안 1로 가지 않는 이유는 그 하나가 무거워졌기 때문이므로
   > — 상태 9개, 전이 11개, 세 집합 구분 —
   > **판정 기준은 "애그리게잇 수" 가 아니라 "엔티티 매핑이 무엇을 표현하는가" 여야 합니다.**

## 결과

- `AGENTS.md` **절대 규칙 12** 추가 — 엔티티 간 연관 매핑 금지
- `03-testing-strategy.md` 에 ArchUnit 규칙 2개 추가 — 봉인을 테스트로 강제합니다
- ADR-0005 의 `data class` 금지 규칙은 유지합니다. 근거 중 프록시 항목만 약해집니다
- "왜 JPA 인가"에 대한 답이 **관례**가 아니라 **조건부 채택 + 봉인**으로 기록됩니다.
  이 ADR 의 값은 JPA 를 정당화한 데 있지 않고,
  **JPA 가 이 워크로드에서 값을 덜 한다는 사실과 걷어낼 조건을 함께 적은 데** 있습니다
