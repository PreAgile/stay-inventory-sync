# ADR-0006. 가상 스레드를 켜지 않습니다

## 상태
확정 (ADR-0005의 코루틴 기각 근거 일부를 대체합니다)

## 맥락

ADR-0005는 코루틴을 쓰지 않는 이유로 **"JDK 21 가상 스레드로 충분하다"** 를 들었습니다.
이 근거는 두 가지를 검증하지 않은 채 서 있었습니다.

1. 이 워크로드에서 가상 스레드가 실제로 무엇을 개선하는가
2. JDK 21에서 가상 스레드를 켜는 비용은 무엇인가

둘 다 확인한 결과, **가상 스레드를 켜지 않기로 합니다.**

## 결정

`spring.threads.virtual.enabled`를 켜지 않습니다.
요청 처리는 플랫폼 스레드 위에서 이루어집니다.

동시성 테스트(T1, T2)도 가상 스레드가 아니라
`CountDownLatch`로 동시 시작을 강제한 플랫폼 스레드로 구성합니다.

## 근거 1 — 상한이 스레드가 아니라 커넥션 풀에 있습니다

이 시스템의 요청 처리는 `SELECT ... FOR UPDATE`로 재고 행을 잠그고
그 트랜잭션이 끝날 때까지 커넥션을 점유합니다.

```
동시 요청 수 N
  → N개의 스레드가 필요하다        ← 가상 스레드가 싸게 만들어주는 것
  → N개의 커넥션이 필요하다        ← 가상 스레드가 해결하지 못하는 것
```

스레드를 무한히 싸게 만들어도 **커넥션 풀 크기 이상으로는 동시에 진행할 수 없습니다.**
가상 스레드를 켜면 요청을 더 많이 받아들이게 되지만,
그만큼 풀 대기 큐가 길어질 뿐 처리량은 늘지 않습니다.

이 지점은 T1과 직접 맞물립니다.
T1의 동시 요청 수 100은 커넥션 풀 크기를 초과하도록 잡은 값이며
(`03-testing-strategy.md`), 그 구간이 바로 가상 스레드가 기여하지 못하는 구간입니다.

JEP 491로 pinning이 제거된 뒤에도 이 사실은 변하지 않습니다.
**병목이 사라지는 것이 아니라 스레드에서 커넥션 풀로 옮겨갈 뿐입니다.**

### 요청 경로만 보면 논증이 절반입니다

`spring.threads.virtual.enabled`는 웹 요청 스레드만 바꾸지 않습니다.
Spring Boot 자동 구성의 task execution 과 task scheduling 에도 적용됩니다
(`ThreadPoolTaskExecutor` → `SimpleAsyncTaskExecutor`,
`ThreadPoolTaskScheduler` → `SimpleAsyncTaskScheduler`).

즉 `@Scheduled` 폴링으로 도는 **Outbox 릴레이도 이 플래그의 사정권입니다.**
그리고 릴레이는 요청 경로와 성질이 다릅니다 —
**커넥션을 놓고 외부 HTTP 를 기다립니다.** 위 논증이 그대로 적용되지 않습니다.

그러나 결론은 같습니다. 상한이 다른 곳에 있을 뿐입니다.

| 경로 | 대기의 성질 | 상한 | 가상 스레드 기여 |
|---|---|---|---|
| 요청 | DB 커넥션을 쥔 채 락 대기 | 커넥션 풀 | 없음 |
| 릴레이 | 커넥션을 놓고 외부 HTTP 대기 | 외부 레이트 리밋 (프로퍼티당 분당 20건) | 없음 |

초당 0.33건을 발행하는 데 스레드가 부족할 일은 없습니다 (`04-capacity-and-limits.md`).
**두 경로 모두 상한이 스레드가 아니라는 것이 이 ADR 의 실제 근거입니다.**

부수적으로, 가상 스레드는 데몬 스레드이므로 `@Scheduled` 로 JVM 을 살려두는 구성에서
이 플래그를 켜면 조기 종료할 수 있어 `spring.main.keep-alive` 가 추가로 필요해집니다.
켜지 않으므로 해당하지 않지만, **"켜는 비용"에 포함되는 항목입니다.**

## 근거 2 — JDK 21에서 켜는 비용

JDK 21~23에서는 `synchronized` 구간 안에서 블로킹 I/O가 일어나면
가상 스레드가 캐리어 스레드에 고정됩니다(pinning).
모니터 소유권을 가상 스레드가 아니라 캐리어 스레드 정체성으로 추적하기 때문입니다.

문제는 이 스택이 정확히 그 지뢰밭 위에 있다는 것입니다.

| 구성요소 | 이력 |
|---|---|
| HikariCP | 풀 초기화 구간에서 가상 스레드가 물려 애플리케이션이 정지하는 이슈가 보고됐습니다 |
| pgjdbc | 내부 `synchronized`를 `ReentrantLock`으로 교체하는 작업이 진행됐습니다 |

JDK 24의 JEP 491이 이 문제를 거의 제거했고, 이를 담은 첫 LTS는 JDK 25입니다.

**그러나 얻는 것이 없는 기능을 위해 런타임을 올릴 이유가 없습니다.**
근거 1에 따라 가상 스레드는 이 워크로드에서 기여하지 않으므로,
pinning은 감수할 위험이 아니라 **만들 필요가 없는 위험**입니다.

### 위험의 성격

pinning은 정확성 문제가 아니라 활성(liveness)·처리량 문제입니다.
재고가 잘못 차감되지는 않습니다.

실질적인 위험은 다른 데 있습니다.
가상 스레드 100개가 캐리어 스레드(기본값 = CPU 코어 수)에 고정된 채
커넥션을 기다리면 **T1이 타임아웃으로 죽습니다.**
정합성 버그가 아닌데 정합성 버그처럼 보입니다.

## 기각한 대안 1: 가상 스레드를 켜고 JDK 21을 유지합니다

pinning 발생 여부는 계측으로 확인할 수 있습니다.
다만 진단 옵션은 **테스트 JVM 에** 전달되어야 합니다.

```kotlin
// build.gradle.kts
tasks.withType<Test>().configureEach {
    systemProperty("jdk.tracePinnedThreads", "short")
}
```

`./gradlew test -Djdk.tracePinnedThreads=short` 는 동작하지 않습니다.
`-D` 는 Gradle 데몬 JVM 에만 설정되고, 테스트는 fork 된 별도 JVM 에서 실행되기 때문입니다.

확인 자체는 싸지만, 확인에 성공해도 근거 1이 남습니다.
**개선이 0인 기능의 위험을 측정하는 데 시간을 쓰는 것**이 되므로 기각합니다.

(이 플래그는 JDK 21 기준입니다. JDK 24+ 에서는 JFR의 `jdk.VirtualThreadPinned` 이벤트로 대체됐습니다.)

## 기각한 대안 2: JDK 25(LTS)로 올립니다

JEP 491이 pinning을 제거하므로 근거 2는 해소됩니다.
그러나 근거 1이 그대로 남으므로 **해소되는 것은 비용뿐이고 편익은 여전히 0입니다.**

더해 이 시점의 런타임 변경은
`README.md`, `AGENTS.md`, `ADR-0005`, `.github/workflows/ci.yml`을 동시에 건드립니다.
편익이 0인 변경에 지불할 비용이 아닙니다.

**재검토 조건**: 두 경로를 각각 봅니다.

- **요청 경로** — 외부 채널 호출을 릴레이가 아니라 요청 경로에서 하게 되거나,
  커넥션을 점유하지 않는 I/O 대기가 요청당 지배적인 시간이 되면 다시 판단합니다.
  현재 설계는 외부 I/O를 락 구간 밖(릴레이)으로 밀어냈으므로(ADR-0003) 성립하지 않습니다.
- **릴레이 경로** — 통보 대상 채널이 늘어 동시 발행이 필요해지고,
  그 동시성 상한이 레이트 리밋이 아니라 **워커 스레드 수로 옮겨가면** 다시 판단합니다.
  팬아웃 대상이 미정이라 현재는 산정 자체가 성립하지 않습니다 (#18).

## 결과

- ADR-0005의 코루틴 기각 근거에서 "가상 스레드로 충분하다"를 제거합니다.
  코루틴을 쓰지 않는 이유는 가상 스레드의 존재가 아니라
  **데이터 접근 스택이 블로킹 JDBC라는 사실**입니다. ADR-0005 참고
- 가상 스레드 도입 제안은 이 ADR을 근거로 기각합니다
- 이 결정은 "최신 기능을 쓰지 않는다"가 아니라 **"적용 경계를 안다"** 의 기록입니다.
  Lincheck을 쓰지 않는 판단(ADR-0005)과 같은 논법입니다
