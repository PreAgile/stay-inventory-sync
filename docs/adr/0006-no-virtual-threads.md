# ADR-0006. 가상 스레드를 켜지 않는다

## 상태
확정 (ADR-0005의 코루틴 기각 근거 일부를 대체한다)

## 맥락

ADR-0005는 코루틴을 쓰지 않는 이유로 **"JDK 21 가상 스레드로 충분하다"** 를 들었다.
이 근거는 두 가지를 검증하지 않은 채 서 있었다.

1. 이 워크로드에서 가상 스레드가 실제로 무엇을 개선하는가
2. JDK 21에서 가상 스레드를 켜는 비용은 무엇인가

둘 다 확인한 결과, **가상 스레드를 켜지 않기로 한다.**

## 결정

`spring.threads.virtual.enabled`를 켜지 않는다.
요청 처리는 플랫폼 스레드 위에서 이루어진다.

동시성 테스트(T1, T2)도 가상 스레드가 아니라
`CountDownLatch`로 동시 시작을 강제한 플랫폼 스레드로 구성한다.

## 근거 1 — 상한이 스레드가 아니라 커넥션 풀에 있다

이 시스템의 요청 처리는 `SELECT ... FOR UPDATE`로 재고 행을 잠그고
그 트랜잭션이 끝날 때까지 커넥션을 점유한다.

```
동시 요청 수 N
  → N개의 스레드가 필요하다        ← 가상 스레드가 싸게 만들어주는 것
  → N개의 커넥션이 필요하다        ← 가상 스레드가 해결하지 못하는 것
```

스레드를 무한히 싸게 만들어도 **커넥션 풀 크기 이상으로는 동시에 진행할 수 없다.**
가상 스레드를 켜면 요청을 더 많이 받아들이게 되지만,
그만큼 풀 대기 큐가 길어질 뿐 처리량은 늘지 않는다.

이 지점은 T1과 직접 맞물린다.
T1의 동시 요청 수 100은 커넥션 풀 크기를 초과하도록 잡은 값이며
(`03-testing-strategy.md`), 그 구간이 바로 가상 스레드가 기여하지 못하는 구간이다.

JEP 491로 pinning이 제거된 뒤에도 이 사실은 변하지 않는다.
**병목이 사라지는 것이 아니라 스레드에서 커넥션 풀로 옮겨갈 뿐이다.**

## 근거 2 — JDK 21에서 켜는 비용

JDK 21~23에서는 `synchronized` 구간 안에서 블로킹 I/O가 일어나면
가상 스레드가 캐리어 스레드에 고정된다(pinning).
모니터 소유권을 가상 스레드가 아니라 캐리어 스레드 정체성으로 추적하기 때문이다.

문제는 이 스택이 정확히 그 지뢰밭 위에 있다는 것이다.

| 구성요소 | 이력 |
|---|---|
| HikariCP | 풀 초기화 구간에서 가상 스레드가 물려 애플리케이션이 정지하는 이슈 보고 |
| pgjdbc | 내부 `synchronized`를 `ReentrantLock`으로 교체하는 작업이 진행됨 |

JDK 24의 JEP 491이 이 문제를 거의 제거했고, 이를 담은 첫 LTS는 JDK 25다.

**그러나 얻는 것이 없는 기능을 위해 런타임을 올릴 이유가 없다.**
근거 1에 따라 가상 스레드는 이 워크로드에서 기여하지 않으므로,
pinning은 감수할 위험이 아니라 **만들 필요가 없는 위험**이다.

### 위험의 성격

pinning은 정확성 문제가 아니라 활성(liveness)·처리량 문제다.
재고가 잘못 차감되지는 않는다.

실질적 위험은 다른 데 있다.
가상 스레드 100개가 캐리어 스레드(기본값 = CPU 코어 수)에 고정된 채
커넥션을 기다리면 **T1이 타임아웃으로 죽는다.**
정합성 버그가 아닌데 정합성 버그처럼 보인다.

## 기각한 대안 1: 가상 스레드를 켜고 JDK 21을 유지한다

pinning 발생 여부는 계측으로 확인할 수 있다.

```bash
./gradlew test -Djdk.tracePinnedThreads=short
```

확인 자체는 싸지만, 확인에 성공해도 근거 1이 남는다.
**개선이 0인 기능의 위험을 측정하는 데 시간을 쓰는 것**이 되므로 기각한다.

(이 플래그는 JDK 21 기준이다. JDK 24+ 에서는 JFR의 `jdk.VirtualThreadPinned` 이벤트로 대체됐다.)

## 기각한 대안 2: JDK 25(LTS)로 올린다

JEP 491이 pinning을 제거하므로 근거 2는 해소된다.
그러나 근거 1이 그대로 남으므로 **해소되는 것은 비용뿐이고 편익은 여전히 0이다.**

더해 이 시점의 런타임 변경은
`README.md`, `AGENTS.md`, `ADR-0005`, `.github/workflows/ci.yml`을 동시에 건드린다.
편익이 0인 변경에 지불할 비용이 아니다.

**재검토 조건**: 외부 채널 호출을 릴레이가 아니라 요청 경로에서 하게 되거나,
커넥션을 점유하지 않는 I/O 대기가 요청당 지배적인 시간이 되면 다시 판단한다.
현재 설계는 외부 I/O를 락 구간 밖(릴레이)으로 밀어냈으므로(ADR-0003) 이 조건이 성립하지 않는다.

## 결과

- ADR-0005의 코루틴 기각 근거에서 "가상 스레드로 충분하다"를 제거한다.
  코루틴을 쓰지 않는 이유는 가상 스레드의 존재가 아니라
  **데이터 접근 스택이 블로킹 JDBC라는 사실**이다. ADR-0005 참고
- 가상 스레드 도입 제안은 이 ADR을 근거로 기각한다
- 이 결정은 "최신 기능을 쓰지 않는다"가 아니라 **"적용 경계를 안다"** 의 기록이다.
  Lincheck을 쓰지 않는 판단(ADR-0005)과 같은 논법이다
