# ADR-0001. Pooled Inventory 모델을 채택한다

## 상태
확정 (Hybrid 는 조건부 유예 — 재검토 조건과 선행 조건 명시)

## 맥락

다채널 판매에서 재고를 관리하는 방식은 두 가지다.

**Allocated (배정형)** — 채널별로 고정 수량을 나눠준다.
에어비앤비 3, 야놀자 3, 직판 4.

**Pooled (공유형)** — 모든 채널이 하나의 재고 카운트를 바라본다.
어느 채널에서든 팔리면 즉시 전 채널에 반영한다.

### 어느 쪽이 성립하는지는 유통 계약이 정한다

이 선택은 기술 취향이 아니라 **채널과 맺은 계약의 형태**에 종속된다.

| 계약 모델 | 채널의 지위 | 자연스러운 재고 모델 |
|---|---|---|
| **Agency (수수료)** | 중개자. 재고를 소유하지 않고 수수료만 받는다 | **Pooled / Freesale** |
| **Merchant (도매)** | 재고를 net rate로 사서 마크업해 되판다 | **Allotment (배정)** |

Merchant 모델에서는 채널이 팔지 못한 재고의 손실을 스스로 떠안으므로,
**미리 몇 실을 확보할지**가 계약의 핵심이 된다. 배정이 필연적이다.
Agency 모델에서는 채널이 재고를 소유하지 않으므로 미리 떼어줄 이유가 없다.

국내 중저가 숙박 유통은 **agency 계약이 일반적**이다.
중개 플랫폼이 재고를 도매로 사서 되파는 것이 아니라 수수료를 받는 구조이므로,
채널이 재고를 소유하지 않는다.

*시장 점유율과 수수료율의 구체적 수치는 이 판단의 근거로 쓰지 않는다.
출처를 확인하지 않은 수치를 근거로 쓰면 pooled 채택의 최종 근거가 검증 불가능해진다.
계약 형태가 agency 인지 merchant 인지는 **실제 계약서로 확인할 수 있는 사실**이므로,
추정 수치가 아니라 그것을 근거로 둔다.*

즉 이 도메인의 기본값은 배정이 아니라 공유다.

## 결정

**Pooled를 채택한다.** 스키마상 `daily_inventory(room_type_id, stay_date, total, sold)`
단일 행이 모든 채널의 재고를 대표한다.

## 기각한 대안 1: Allocated — 전량 배정

기각 이유는 **인위적 품절**이다.
에어비앤비 배정분 3이 모두 팔렸는데 야놀자에 2가 남아 있으면,
에어비앤비 고객은 "품절"을 보지만 실제 객실은 비어 있다.
숙박업의 재고는 소멸성 자산이므로 이 손실은 회수되지 않는다.

Allocated의 장점은 동시성 경합이 채널별로 분산된다는 것이다.
그러나 이는 매출 손실을 대가로 얻는 기술적 편의이며, 우선순위가 역전되어 있다.

## 조건부 유예: Hybrid — allotment + release

**기각이 아니다.** ADR-0004(Kafka)와 같은 형태로 다룬다 —
설계가 틀린 것이 아니라 **아직 지킬 수 없기 때문에** 미룬다.

대안 1(allocated)과 성질이 다르므로 같은 제목 아래 두지 않는다.

| | 성질 | 근거 |
|---|---|---|
| **Allocated 전량 배정** | **기각** | 인위적 품절은 구조적 결함이다. 조건이 바뀌어도 오지 않는다 |
| **Hybrid** | **조건부 유예** | 설계가 틀린 것이 아니라 지금 지킬 수 없다 |

전량 배정이 아니라, **일부만 채널에 떼어주고 나머지를 공유로 두는** 방식이다.
실무 채널매니저가 실제로 지원하는 구성이며, 업계 용어로는 다음 세 장치의 조합이다.

| 장치 | 의미 |
|---|---|
| **Allotment** | 특정 채널에 미리 확보해 주는 객실 블록 |
| **Release period (cut-off)** | 계약에 명시된 반납 시점. 체크인 N일 전까지 팔리지 않으면 배정분이 판매자에게 자동 반환된다 |
| **On-request / Freesale** | 배정 소진 후의 처리. 건별 확인 후 확정하거나, 배정 없이 무제한 판매로 전환한다 |

### 채널매니저 위에서는 "채널별 카운터"가 표현되지 않는다

최초 작성 시 이 절은 hybrid 를 **채널별 재고 카운터**로 서술했다. 그 서술이 틀렸다.

Channex 의 `availability` push 는 **룸타입 단위 절대값**이며 채널별 값을 받지 않는다.
채널별 차등은 규칙 세 가지로만 표현된다.

| 규칙 | 의미 |
|---|---|
| `close_out` | 이 채널에는 팔지 않는다 |
| `availability_offset` | 전체에서 N 을 빼고 보여준다 |
| `max_availability` | 최대 N 까지만 보여준다 |

즉 hybrid 의 실제 형태는 **카운터 N 개가 아니라 카운터 1개 + 채널별 투영 규칙**이다.

```
      우리 DB (진실 1개)                채널로 나가는 것
 ┌────────────────────────┐      ┌──────────────────────────┐
 │ 전체 10 / 팔림 3       │  ──▶ │ availability = 7          │  룸타입 절대값
 │                        │      ├──────────────────────────┤
 │ 채널 정책 장부         │  ──▶ │ 채널 A : 규칙 없음        │
 │  A  배정 3             │      │ 채널 B : offset 2         │
 │  B  캡 5               │      │ 채널 C : max 5            │
 └────────────────────────┘      └──────────────────────────┘
```

**불변식이 늘어나지 않는다.** 진실 카운터는 하나 그대로이고,
늘어나는 것은 정책 장부와 투영 로직이다. 근거는 ADR-0009.

### 두 종류로 갈라진다

| | **캡형** — 노출 제한 | **보장형** — 물량 확보 |
|---|---|---|
| 뜻 | "이 채널엔 5실까지만 보여라" | "이 채널에 3실은 확보해 둬라" |
| 채널 표현 | `max_availability` 규칙 1개 | 나머지 채널에 `availability_offset` |
| 규칙 갱신 빈도 | **없음** (정적) | 배정이 팔릴 때마다 |
| 재고 모델 변경 | 없음 | 없음 (장부만 추가) |
| 상태 | **재검토 조건 3이 성립하면 즉시 가능** | 실측 3건 이후 |

보장형의 동작은 이렇게 된다.

```
전체 10, 채널 A 배정 3, A 가 1실 판매

  availability push        = 10 - 1 = 9
  채널 A       규칙 없음    → 9 실 노출 (배정 잔여 2 + 공유 7)
  나머지 채널  offset = 2   → 7 실 노출 (배정 잔여만큼 못 건드림)
```

**`offset` = 배정 잔여**다. 배정이 3실이면 갱신은 하루 최대 3회 + 취소분이다.

### 유예하는 이유

**증명해야 할 표면이 늘어나기 때문**이라고 썼던 근거 네 개 중 두 개는 이중 계상이었다.

| 최초 근거 | 실제 |
|---|---|
| 반환이 새로운 경합 지점을 만든다 | **#27 이 이미 두 테이블 락 순서를 정하는 중.** 세 번째 테이블을 끼우는 비용으로 줄어든다 |
| `INV-2` 가 재정의되어야 한다 | **#25 가 이미 재정의 중.** hybrid 와 무관하게 바뀐다 |
| 반환과 예약 시도의 우선순위 판정 | 유효 |
| outbox 이벤트 종류 증가 | 유효 |

hybrid 를 하지 않아도 지불하는 비용을 유예 근거로 세우면,
#25 · #27 이 머지되는 순간 근거의 절반이 저절로 사라진다. 그래서 지운다.

**대신 실제 증분은 이것이다.**

1. **`on-request` 는 재고 문제가 아니라 예약 생애주기 문제다.**
   "채널이 팔되 확정은 우리가 승인"이므로 상태 기계에 승인 단계가 들어온다.
   `PENDING` 의 의미가 갈라지고, 타임아웃·자동 거절·승인 대기 중 재고 홀드가 전부 새 결정이다.
   **배정 자체보다 크다. 이 ADR 의 범위에서 명시적으로 제외한다** — 위 장치 표에 적었지만 도입 대상이 아니다
2. **취소의 복원 대상 판정** — 배정분에서 팔린 예약의 취소를 배정 잔여로 되돌리나 공유로 되돌리나.
   해법은 예약 시점에 차감 출처를 기록하는 것이며 `07-reconciliation.md` 에 있다
3. **규칙 갱신 비용** — 공개 문서에 없다. `experiments/channex-unknowns.md` 의 U1 · U3

### 선행 조건 — 재검토 조건보다 먼저다

**조건이 성립해도 이것 없이는 못 한다.**

> **채널이 우리 정책을 지키는지 확인하는 경로(#21 · ADR-0009)가 먼저 있어야 한다.**

"채널 A 에 3실 배정했다"는 것은 우리 DB 에 적어놓은 문장일 뿐이다.
채널 화면에서 사람이 손으로 노출 수를 바꾸면 우리는 모른다.

| | pooled | 보장형 hybrid |
|---|---|---|
| 채널 값이 우리와 다르면 | **동기화 지연.** 곧 우리 값으로 덮는다 | **계약 위반.** 3실만 주기로 한 채널에 더 팔렸다 |
| 성격 | 잠깐 어긋난 표시 | 돈과 책임 |

즉 대사 경로 없이 hybrid 를 얹으면 **지킬 수 없는 약속을 DB 에 적는 일**이 된다.

```
ADR-0009 (축 분리) + 대사 구현  ──▶  캡형  ──▶  보장형
```

### 재검토 조건

다음 중 하나가 참이 되면 이 결정을 다시 본다.

1. **계약상 특정 채널에 객실 수를 보장**해야 한다 — merchant 계약, 베드뱅크, 홀세일러 → **보장형**
2. **기업 협약이나 단체 블록**을 재고에서 떼어 관리해야 한다 → **보장형**
3. 특정 채널의 **취소율이 유의하게 높아** 노출을 구조적으로 제한할 필요가 생긴다 → **캡형**

1번이 가장 먼저 올 가능성이 높다. Agency 채널만 있을 때는 성립하지 않지만,
B2B 유통이 붙는 순간 pooled 만으로는 계약을 이행할 수 없다.

**3번은 캡형이므로 재고 모델을 바꾸지 않는다.** 조건 중 가장 싸고, 선행 조건만 갖추면 바로 된다.

### 확장의 형태 — "특수 케이스" 주장을 담보하는 조건

pooled 가 hybrid 의 특수 케이스(모든 배정이 0)라는 주장은 **무조건 참이 아니다.**
아래 형태를 지킬 때만 참이다.

**1. 배정은 별도 테이블로 둔다.** `daily_inventory` 의 `total` · `sold` 의 의미를 건드리지 않는다.

```
channel_allotment(room_type_id, stay_date, channel,
                  allotted, sold_from_allotment, release_at)
   PK(room_type_id, stay_date, channel)
```

컬럼 추가 방식으로 가면 INV-1 · INV-2 와 T1~T4 가 전부 재작성 대상이 되고,
그 순간 "나중에 얹을 수 있다"는 주장이 거짓이 된다.

**2. 불변식은 고치지 않고 하나 얹는다.**

```
INV-4  모든 (room_type_id, stay_date)에 대해
       SUM(allotted - sold_from_allotment) <= total - sold
```

pooled 는 **INV-4 의 좌변이 항상 0** 인 상태로 정의된다.
특수 케이스 주장이 문장이 아니라 검증기 수준에서 참이 된다.

**3. 락 순서에 배정 테이블을 미리 끼워 넣는다.**

#27 이 `reservation -> daily_inventory` 를 확정하는 중이므로,
그 순서를 `reservation -> daily_inventory -> channel_allotment` 로 정해 두면
hybrid 를 얹을 때 ADR-0002 를 다시 개정하지 않아도 된다.
**테이블이 없어도 순서는 지금 선언할 수 있다. 비용은 문장 한 줄이다.**

**4. release 는 배치가 아니라 조회 시점 계산으로 시작한다.**

`release_at < now()` 인 배정은 조회 시 없는 것으로 취급한다.
스케줄러·멱등·다중 인스턴스 중복 실행·순서 역전 방어를 전부 우회하고,
위 증분 2(우선순위 판정)도 상당 부분 사라진다 — 반환이라는 별도 연산 자체가 없어진다.
배정 축소를 채널에 **통보**해야 할 때 비로소 배치를 붙인다.

## 결과

**경합이 단일 행에 집중된다.**

인기 지점의 주말 날짜는 모든 채널의 예약 요청이 동일한
`(room_type_id, stay_date)` 행으로 수렴한다.

따라서 이 시스템에서 **락 전략은 부수적 구현 세부사항이 아니라 핵심 설계 결정**이 된다.
→ ADR-0002로 이어진다.

부수적으로, 채널 재고 동기화의 필요성도 여기서 나온다.
Pooled는 "어느 채널에서 팔려도 다른 모든 채널에 즉시 반영"을 전제하므로,
반영 실패는 곧바로 오버부킹이다.

## 추가 이력

**[8/20] 기각한 대안 2(Hybrid)와 유통 계약 맥락을 추가했다.**

최초 작성 시 이 ADR 은 pooled 와 allocated 를 **둘 중 하나**로 놓았다.
그러나 실무의 기본 구성은 둘의 혼합이며, 이분법으로 서술한 것은 선택지를 좁게 본 것이다.

추가 계기는 다음 질문이었다.

> 플랫폼별로 잔여 객실이랑 가격이 각각 다르게 나오던데,
> 재고를 하나의 테이블로 두는 게 아니라 OTA 별로 따로 주는 것 아닌가?

관찰 자체는 정확했다. 다만 그 현상의 원인은 대부분 **동기화 지연·채널별 표시 정책·
요금 차이·restrictions 차이**이며 재고 모델과는 별개다.
확인 과정에서 **hybrid 가 기각 대안으로 문서에 없다**는 사실이 드러났다.

이어서 제기된 설계 — *"채널마다 계약된 최소 물량이 있고, 소진되면 끝나며,
끝까지 안 팔릴 것 같으면 그때 해당 채널에 열어준다"* — 는
업계의 **allotment + release period** 와 같은 구조다.
다만 실무는 그 해제를 수동 조작이 아니라 **계약에 반납 시점을 명시해 자동화**한다.

결정 자체(pooled)는 바뀌지 않았다. 대안 하나와 재검토 조건이 늘었다.

**[8/21] Hybrid 를 기각에서 조건부 유예로 바꾸고, 근거를 다시 계산했다.**

Channex 공개 문서를 직접 읽고 확인한 결과 최초 서술에 사실 오류가 있었다.

| 최초 서술 | 확인된 사실 |
|---|---|
| hybrid = 채널별 재고 카운터 | `availability` 는 룸타입 단위 절대값. **채널별 카운터가 표현되지 않는다.** 채널별 차등은 규칙 3종뿐 |
| 반환이 새로운 경합 지점을 만든다 | #27 이 이미 두 테이블 락 순서를 정하는 중. 세 번째 테이블을 끼우는 비용 |
| `INV-2` 재정의가 필요하다 | #25 가 이미 재정의 중. hybrid 와 무관하게 바뀐다 |
| 국내 유통 점유율 90% 이상, 수수료 10~15% | **출처를 확인하지 못했다.** 수치를 근거에서 뺐다 |

라벨도 고쳤다. 본문이 스스로 *"1번이 가장 먼저 올 가능성이 높다"* 고 말하는데
제목이 `기각`이면, 미래의 독자가 설계적으로 틀렸다고 읽고 재검토하지 않는다.
ADR-0004(Kafka)가 쓴 **조건부 유예**와 같은 형태로 통일한다.

그리고 유예 근거에 없던 것 두 개를 넣었다.

- **`on-request` 는 재고가 아니라 예약 생애주기를 바꾼다** — 배정보다 크다. 범위에서 제외했다
- **선행 조건** — 재검토 조건이 성립해도 대사 경로(#21 · ADR-0009) 없이는 못 한다

마지막으로 *"pooled 는 hybrid 의 특수 케이스"* 라는 주장이 무조건 참이 아니라는 것을
명시했다. 별도 테이블 + `INV-4` 추가 형태를 지킬 때만 참이며, 컬럼을 추가하는 방식으로
가면 그 문장이 거짓이 된다. **확장 가능성만 쓰지 않고 확장의 형태를 적어야 담보된다.**
