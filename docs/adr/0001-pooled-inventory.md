# ADR-0001. Pooled Inventory 모델을 채택합니다

## 상태
확정 (재고 모델은 pooled. **캡형 hybrid 채택**, 보장형은 조건부 유예)

## 맥락

다채널 판매에서 재고를 관리하는 방식은 두 가지입니다.

**Allocated (배정형)** — 채널별로 고정 수량을 나눠 줍니다.
에어비앤비 3, 야놀자 3, 직판 4.

**Pooled (공유형)** — 모든 채널이 하나의 재고 카운트를 바라봅니다.
어느 채널에서든 팔리면 즉시 전 채널에 반영합니다.

### 어느 쪽이 성립하는지는 유통 계약이 정합니다

이 선택은 기술 취향이 아니라 **채널과 맺은 계약의 형태**에 종속됩니다.

| 계약 모델 | 채널의 지위 | 자연스러운 재고 모델 |
|---|---|---|
| **Agency (수수료)** | 중개자. 재고를 소유하지 않고 수수료만 받습니다 | **Pooled / Freesale** |
| **Merchant (도매)** | 재고를 net rate로 사서 마크업해 되팝니다 | **Allotment (배정)** |

Merchant 모델에서는 채널이 팔지 못한 재고의 손실을 스스로 떠안습니다.
그래서 **미리 몇 실을 확보할지**가 계약의 핵심이 됩니다. 배정이 필연입니다.
Agency 모델에서는 채널이 재고를 소유하지 않으므로 미리 떼어 줄 이유가 없습니다.

국내 중저가 숙박 유통은 **agency 계약이 일반적**입니다.
중개 플랫폼이 재고를 도매로 사서 되파는 것이 아니라 수수료를 받는 구조이므로,
채널이 재고를 소유하지 않습니다.

*시장 점유율과 수수료율의 구체적 수치는 이 판단의 근거로 쓰지 않습니다.
출처를 확인하지 않은 수치를 근거로 쓰면 pooled 채택의 최종 근거가 검증 불가능해집니다.
계약 형태가 agency 인지 merchant 인지는 **실제 계약서로 확인할 수 있는 사실**이므로,
추정 수치가 아니라 그것을 근거로 둡니다.*

즉 이 도메인의 기본값은 배정이 아니라 공유입니다.

## 결정

**Pooled를 채택했습니다.** 스키마상 `daily_inventory(room_type_id, stay_date, total, sold)`
단일 행이 모든 채널의 재고를 대표합니다.

## 기각한 대안 1: Allocated — 전량 배정

기각 이유는 **인위적 품절**입니다.
에어비앤비 배정분 3이 모두 팔렸는데 야놀자에 2가 남아 있으면,
에어비앤비 고객은 "품절"을 보지만 실제 객실은 비어 있습니다.
숙박업의 재고는 소멸성 자산이라 그날 팔지 못한 객실은 다음 날로 넘길 수 없고, 이 손실은 회수되지 않습니다.

Allocated의 장점은 동시성 경합이 채널별로 분산된다는 점입니다.
그러나 이것은 매출 손실을 대가로 얻는 기술적 편의이고, 우선순위가 뒤집혀 있습니다.

## 조건부 유예: Hybrid — allotment + release

**기각이 아닙니다.** ADR-0004(Kafka)와 같은 형태로 다룹니다 —
설계가 틀린 것이 아니라 **아직 지킬 수 없기 때문에** 미룹니다.

대안 1(allocated)과 성질이 다르므로 같은 제목 아래 두지 않습니다.

| | 성질 | 근거 |
|---|---|---|
| **Allocated 전량 배정** | **기각** | 인위적 품절은 구조적 결함입니다. 조건이 바뀌어도 오지 않습니다 |
| **Hybrid** | **조건부 유예** | 설계가 틀린 것이 아니라 지금 지킬 수 없습니다 |

전량 배정이 아니라, **일부만 채널에 떼어 주고 나머지를 공유로 두는** 방식입니다.
실무 채널매니저가 실제로 지원하는 구성이고, 업계 용어로는 다음 세 장치의 조합입니다.

| 장치 | 의미 |
|---|---|
| **Allotment** | 특정 채널에 미리 확보해 주는 객실 블록 |
| **Release period (cut-off)** | 계약에 명시된 반납 시점. 체크인 N일 전까지 팔리지 않으면 배정분이 판매자에게 자동으로 돌아옵니다 |
| **On-request / Freesale** | 배정 소진 후의 처리. 건별로 확인해 확정하거나, 배정 없이 무제한 판매로 전환합니다 |

### 채널매니저 위에서는 "채널별 카운터"가 표현되지 않습니다

최초 작성 시 이 절은 hybrid 를 **채널별 재고 카운터**로 서술했습니다. 그 서술이 틀렸습니다.

Channex 의 `availability` push 는 **룸타입 단위 절대값**이고 채널별 값을 받지 않습니다.
채널별 차등은 규칙 세 가지로만 표현됩니다.

| 규칙 | 의미 |
|---|---|
| `close_out` | 이 채널에는 팔지 않습니다 |
| `availability_offset` | 전체에서 N 을 빼고 보여줍니다 |
| `max_availability` | 최대 N 까지만 보여줍니다 |

즉 hybrid 의 실제 형태는 **카운터 N 개가 아니라 카운터 1개 + 채널별 투영 규칙**입니다.

```
      우리 DB (진실 1개)                채널로 나가는 것
 ┌────────────────────────┐      ┌──────────────────────────┐
 │ 전체 10 / 팔림 3       │  ──▶ │ availability = 7          │  룸타입 절대값
 │                        │      ├──────────────────────────┤
 │ 채널 정책 장부         │  ──▶ │ 채널 A : 규칙 없음        │
 │  A  배정 3             │      │ 채널 B : offset 2         │
 │  B  캡 5               │      │ 채널 C : max 5            │
 └────────────────────────┘      └──────────────────────────┘
```

**불변식이 늘어나지 않습니다.** 진실 카운터는 하나 그대로이고,
늘어나는 것은 정책 장부와 투영 로직입니다. 근거는 ADR-0009.

### 두 종류로 갈라집니다

| | **캡형** — 노출 제한 | **보장형** — 물량 확보 |
|---|---|---|
| 뜻 | "이 채널엔 5실까지만 보여라" | "이 채널에 3실은 확보해 둬라" |
| 채널 표현 | `max_availability` 규칙 1개 | 나머지 채널에 `availability_offset` |
| 규칙 갱신 빈도 | **없음** (정적) | 배정이 팔릴 때마다 |
| 재고 모델 변경 | 없음 | 없음 (장부만 추가) |
| 상태 | **채택했습니다** (아래) | **조건부 유예** — 실측 3건 이후 |

보장형의 동작은 이렇게 됩니다.

```
전체 10, 채널 A 배정 3, A 가 1실 판매

  availability push        = 10 - 1 = 9
  채널 A       규칙 없음    → 9 실 노출 (배정 잔여 2 + 공유 7)
  나머지 채널  offset = 2   → 7 실 노출 (배정 잔여만큼 못 건드림)
```

**`offset` = 배정 잔여**입니다. 배정이 3실이면 갱신은 하루 최대 3회 + 취소분입니다.

### 캡형을 채택하는 이유

**초안은 캡형을 "재검토 조건 3이 성립하면" 으로 걸어 두었습니다. 그 조건은 이렇습니다.**

> 특정 채널의 취소율이 유의하게 높아 노출을 구조적으로 제한할 필요가 생긴다

**이 조건은 성립할 수 없습니다.** 취소율을 관측하려면 시스템이 돌아야 하고, 시스템이 돌려면
채널에 노출해야 합니다. 관측 지표(`B5`)조차 Tier 2 입니다.
**즉 "관측되면 도입한다"는 사실상 영구 유예였습니다.**

그리고 조건을 기다릴 필요가 없습니다. **균등 노출은 요구사항이 아니라 순진한 기본값입니다.**

채널마다 수수료가 다르고 취소율이 다릅니다. 숙박 사업자가 채널 믹스를 관리하는 것은
수익관리의 기본이고, *"모든 채널에 똑같이 다 노출한다"* 만 되는 시스템은
`ADR-0007` 이 오버부킹에서 말한 것과 같은 이유로 **실무에서 거부당합니다.**

> 초과 판매를 구조적으로 금지하는 시스템은 실무에서 거부당한다 — `ADR-0007`

**같은 논거가 채널 믹스에도 적용됩니다.** 거부당하면 현장이 채널 화면에서 직접 노출을 조정하고,
그 순간 `ADR-0009` 가 세운 정책 축의 원본이 뒤집힙니다 — 우리 장부가 아니라 채널이 원본이 됩니다.

### 선행 조건은 이미 충족됐습니다

초안이 이렇게 적었습니다.

> 채널이 우리 정책을 지키는지 확인하는 경로(#21 · ADR-0009)가 먼저 있어야 한다.

**`ADR-0009` 가 머지됐고, 거기서 만든 정책 장부가 캡형의 저장 구조를 그대로 제공합니다.**

```
channel_policy.kind    = CAP        노출 상한 규칙
channel_policy.source  = OURS       우리가 정했다
```

같은 테이블을 두 방향으로 씁니다 — `source = CHANNEL` 이면 현장이 채널 화면에서 바꾼 것을
우리가 기록한 것이고, `source = OURS` 면 우리가 능동적으로 설정한 것입니다. **우리가 설정한 쪽이 캡형입니다.**

### 캡형이 재고 모델을 바꾸지 않습니다

이것이 캡형과 보장형을 갈라 놓은 값어치입니다.

```
우리 DB     10                     카운터 하나. pooled 그대로
채널 A · B  10                     규칙 없음
채널 C       5                     max_availability = 5

C 손님이 5개 예약  ->  우리 DB 5  ->  A · B 도 5 로 내려간다
A 손님이 10개 예약 ->  우리 DB 0  ->  C 도 0 이 된다
```

**C 가 5를 확보한 것이 아닙니다.** 실제 판매 가능량은 `min(캡, 잔여)` 이므로
**남은 방이 있는데 매진이 뜨는 상황이 만들어지지 않습니다** — allocated 를 기각한 이유가 여기서 재발하지 않습니다.

그래서 **불변식이 하나도 늘지 않고** `INV-1` ~ `INV-4` 와 `T1` ~ `T4` 가 그대로 유효합니다.
`daily_inventory` 스키마도 손대지 않습니다.

### 캡형의 실제 증분

| 증분 | 내용 |
|---|---|
| 설정 경로 | `channel_policy` 에 `source = OURS` 로 쓰는 **운영 API**. 화면은 범위 밖입니다 |
| 투영 로직 | 장부 → 채널 `max_availability` 규칙 발행 |
| **outbox 이벤트 종류 증가** | 규칙 발행도 외부 호출이므로 dual-write 대상입니다. 초안이 "유효" 로 남긴 근거이고 **사라지지 않습니다** |

**Tier 1 입니다.** 캡형이 없어도 오버부킹 0 은 성립하므로 차단선(`T1`~`T4`)에 기여하지 않습니다.
`02-scope.md` 의 순서 규칙에 따라 **Tier 0 완결 뒤에 착수합니다.**

### 보장형은 유예를 유지합니다

**초안의 유예 근거 넷 중 둘은 이중 계상이었습니다.** 그리고 예고한 대로 사라졌습니다.

| 최초 근거 | 지금 |
|---|---|
| 반환이 새로운 경합 지점을 만든다 | `#27` 이 두 테이블 락 순서를 정하는 중입니다. 세 번째 테이블을 끼우는 비용으로 줄어듭니다 |
| `INV-2` 가 재정의되어야 한다 | **`#25` 가 재정의했습니다 (머지됨).** hybrid 와 무관하게 바뀌었습니다 |
| 반환과 예약 시도의 우선순위 판정 | **유효** |
| outbox 이벤트 종류 증가 | **유효** — 다만 캡형이 이미 지불합니다 |

**남는 실제 증분은 둘입니다.**

1. **배정 잔여 장부** — `channel_allotment` 가 없습니다. 캡형은 정책 장부로 끝나지만
   보장형은 배정 잔여를 추적해야 하고, 그것이 팔릴 때마다 나머지 채널의 `offset` 을 갱신해야 합니다
2. **규칙 갱신 비용** — 공개 문서에 없습니다. `experiments/channex-unknowns.md` 의 `U1` · `U3`

그리고 성격이 다릅니다.

| | 캡형 | 보장형 |
|---|---|---|
| 채널 값이 우리와 다르면 | **동기화 지연.** 곧 우리 값으로 덮습니다 | **계약 위반.** 3실만 주기로 한 채널에 더 팔렸습니다 |
| 성격 | 잠깐 어긋난 표시 | 돈과 책임 |

**보장형은 지킬 수 없는 약속을 DB 에 적을 위험이 있습니다.** 캡형에는 그 위험이 없습니다 —
캡이 어긋나도 다음 주기에 덮이고, 그 사이에 손해가 발생하지 않습니다.

### `on-request` 는 이 ADR 의 근거가 아닙니다

초안이 유예 근거로 이렇게 적었습니다.

> `on-request` 는 재고 문제가 아니라 예약 생애주기 문제다. ...
> **배정 자체보다 크다. 이 ADR 의 범위에서 명시적으로 제외한다**

**`ADR-0010` 이 그것을 도입했습니다.** 승인 대기 상태, 시한 초과 자동 거절, 승인 대기 중 재고 선점 —
언급된 것을 전부 다뤘습니다.

그러면 이 논거는 유예 근거로 쓸 수 없습니다. *"배정보다 큰 것"* 을 이미 했으므로
**이 문장은 이제 "배정은 그보다 작다" 는 뜻이 됩니다.** 근거에서 뺍니다.

`on-request` 자체는 `ADR-0010` 의 소관이고 재고 모델과 무관합니다.

### 재검토 조건

다음 중 하나가 참이 되면 이 결정을 다시 봅니다.

1. **계약상 특정 채널에 객실 수를 보장**해야 합니다 — merchant 계약, 베드뱅크, 홀세일러 → **보장형**
2. **기업 협약이나 단체 블록**을 재고에서 떼어 관리해야 합니다 → **보장형**
3. ~~특정 채널의 취소율이 유의하게 높아 노출을 구조적으로 제한할 필요가 생긴다 → 캡형~~
   — **이 조건을 지웠습니다.** 관측을 기다리는 조건은 데이터가 없는 상태에서 성립할 수 없고,
   그래서 캡형을 조건 없이 채택했습니다. 남은 재검토 조건은 **보장형에 대한 1·2번뿐입니다**

1번이 가장 먼저 올 가능성이 높습니다. Agency 채널만 있을 때는 성립하지 않지만,
B2B 유통이 붙는 순간 pooled 만으로는 계약을 이행할 수 없습니다.

**3번은 캡형이므로 재고 모델을 바꾸지 않습니다.** 조건 중 가장 싸고, 선행 조건만 갖추면 바로 됩니다.

### 확장의 형태 — "특수 케이스" 주장을 담보하는 조건

pooled 가 hybrid 의 특수 케이스(모든 배정이 0)라는 주장은 **무조건 참이 아닙니다.**
아래 형태를 지킬 때만 참입니다.

**1. 배정은 별도 테이블로 둡니다.** `daily_inventory` 의 `total` · `sold` 의 의미를 건드리지 않습니다.

```
channel_allotment(room_type_id, stay_date, channel,
                  allotted, sold_from_allotment, release_at)
   PK(room_type_id, stay_date, channel)
```

컬럼 추가 방식으로 가면 INV-1 · INV-2 와 T1~T4 가 전부 재작성 대상이 되고,
그 순간 "나중에 얹을 수 있다"는 주장이 거짓이 됩니다.

**2. 불변식은 고치지 않고 하나 얹습니다.**

```
INV-4  모든 (room_type_id, stay_date)에 대해
       SUM(allotted - sold_from_allotment) <= total - sold
```

pooled 는 **INV-4 의 좌변이 항상 0** 인 상태로 정의됩니다.
특수 케이스 주장이 문장이 아니라 검증기 수준에서 참이 됩니다.

**3. 락 순서에 배정 테이블을 미리 끼워 넣습니다.**

#27 이 `reservation -> daily_inventory` 를 확정하는 중이므로,
그 순서를 `reservation -> daily_inventory -> channel_allotment` 로 정해 두면
hybrid 를 얹을 때 ADR-0002 를 다시 개정하지 않아도 됩니다.
**테이블이 없어도 순서는 지금 선언할 수 있습니다. 비용은 문장 한 줄입니다.**

**4. release 는 배치가 아니라 조회 시점 계산으로 시작합니다.**

`release_at < now()` 인 배정은 조회할 때 없는 것으로 취급합니다.
스케줄러·멱등·다중 인스턴스 중복 실행·순서 역전 방어를 전부 우회하고,
위 증분 2(우선순위 판정)도 상당 부분 사라집니다 — 반환이라는 별도 연산 자체가 없어집니다.
배정 축소를 채널에 **통보**해야 할 때 비로소 배치를 붙입니다.

## 결과

**경합이 단일 행에 집중됩니다.**

인기 지점의 주말 날짜는 모든 채널의 예약 요청이 동일한
`(room_type_id, stay_date)` 행으로 수렴합니다.

따라서 이 시스템에서 **락 전략은 부수적 구현 세부사항이 아니라 핵심 설계 결정**이 됩니다.
→ ADR-0002로 이어집니다.

부수적으로, 채널 재고 동기화의 필요성도 여기서 나옵니다.
Pooled는 "어느 채널에서 팔려도 다른 모든 채널에 즉시 반영"을 전제하므로,
반영 실패는 곧바로 오버부킹입니다.

## 추가 이력

**[8/20] 기각한 대안 2(Hybrid)와 유통 계약 맥락을 추가했습니다.**

최초 작성 시 이 ADR 은 pooled 와 allocated 를 **둘 중 하나**로 놓았습니다.
그러나 실무의 기본 구성은 둘의 혼합이고, 이분법으로 서술한 것은 선택지를 좁게 본 것입니다.

추가 계기는 다음 질문이었습니다.

> 플랫폼별로 잔여 객실이랑 가격이 각각 다르게 나오던데,
> 재고를 하나의 테이블로 두는 게 아니라 OTA 별로 따로 주는 것 아닌가?

관찰 자체는 정확했습니다. 다만 그 현상의 원인은 대부분 **동기화 지연·채널별 표시 정책·
요금 차이·restrictions 차이**이고 재고 모델과는 별개입니다.
확인 과정에서 **hybrid 가 기각 대안으로 문서에 없다**는 사실이 드러났습니다.

이어서 제기된 설계 — *"채널마다 계약된 최소 물량이 있고, 소진되면 끝나며,
끝까지 안 팔릴 것 같으면 그때 해당 채널에 열어준다"* — 는
업계의 **allotment + release period** 와 같은 구조입니다.
다만 실무는 그 해제를 수동 조작이 아니라 **계약에 반납 시점을 명시해 자동화**합니다.

결정 자체(pooled)는 바뀌지 않았습니다. 대안 하나와 재검토 조건이 늘었습니다.

**[8/21] Hybrid 를 기각에서 조건부 유예로 바꾸고, 근거를 다시 계산했습니다.**

Channex 공개 문서를 직접 읽고 확인한 결과 최초 서술에 사실 오류가 있었습니다.

| 최초 서술 | 확인된 사실 |
|---|---|
| hybrid = 채널별 재고 카운터 | `availability` 는 룸타입 단위 절대값입니다. **채널별 카운터가 표현되지 않습니다.** 채널별 차등은 규칙 3종뿐입니다 |
| 반환이 새로운 경합 지점을 만든다 | #27 이 이미 두 테이블 락 순서를 정하는 중입니다. 세 번째 테이블을 끼우는 비용입니다 |
| `INV-2` 재정의가 필요하다 | #25 가 이미 재정의하는 중입니다. hybrid 와 무관하게 바뀝니다 |
| 국내 유통 점유율 90% 이상, 수수료 10~15% | **출처를 확인하지 못했습니다.** 수치를 근거에서 뺐습니다 |

라벨도 고쳤습니다. 본문이 스스로 *"1번이 가장 먼저 올 가능성이 높다"* 고 말하는데
제목이 `기각`이면, 미래의 독자가 설계적으로 틀렸다고 읽고 재검토하지 않습니다.
ADR-0004(Kafka)가 쓴 **조건부 유예**와 같은 형태로 통일합니다.

그리고 유예 근거에 없던 것 두 개를 넣었습니다. **둘 다 그 뒤에 해소됐습니다.**

- ~~**`on-request` 는 배정보다 크다. 범위에서 제외했다**~~ — `ADR-0010` 이 도입했으므로
  이 논거는 뒤집혔습니다. 근거에서 뺐습니다
- ~~**선행 조건** — 대사 경로(#21 · ADR-0009) 없이는 못 한다~~ — `ADR-0009` 가 머지되어 **충족됐습니다**

**그 결과 캡형의 유예 근거가 남지 않았습니다.** 그래서 이 개정에서 캡형을 채택으로 바꿉니다.
보장형은 배정 잔여 장부와 규칙 갱신 비용이 남아 유예를 유지합니다.

**"수단이 없다" 에서 "이유가 없다" 로 바뀌었고, 캡형은 이유마저 있었습니다** —
균등 노출이 요구사항이 아니라 순진한 기본값이라는 것이 그 이유입니다.

마지막으로 *"pooled 는 hybrid 의 특수 케이스"* 라는 주장이 무조건 참이 아니라는 것을
명시했습니다. 별도 테이블 + `INV-4` 추가 형태를 지킬 때만 참이고, 컬럼을 추가하는 방식으로
가면 그 문장이 거짓이 됩니다. **확장 가능성만 쓰지 않고 확장의 형태를 적어야 담보됩니다.**
