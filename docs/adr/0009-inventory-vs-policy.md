# ADR-0009. 재고와 정책을 분리합니다 — 원본이 둘이 되는 문제

## 상태

확정 (재검토 조건 명시)

## 맥락

*채널·PMS·대사가 무엇인지부터 필요하면 `docs/07-reconciliation.md` 의 0장을 먼저 읽으십시오.*

이 저장소의 모든 설계는 한 문장 위에 서 있습니다.

```
우리 PMS = 원본(source of truth)
채널     = 사본. 우리가 밀어넣은 값
```

`00-problem-definition.md`가 다루겠다고 선언한 것은 두 지점입니다 —
**(a) dual-write**, **(b) 중복 수신**. 둘 다 "우리 → 채널" 방향의 문제입니다.

그런데 채널매니저 Channex 는 `ari` 웹훅을 제공합니다.
재고·요금·제약이 **채널매니저 UI 나 채널 앱에서 사람 손으로 바뀌었을 때** 우리에게 통보하는 웹훅입니다.

이 웹훅이 존재한다는 것은 **사본 쪽에서도 값이 바뀐다**는 뜻입니다.
그리고 현장에서 실제로 바뀝니다.

- 사장님이 채널 앱에서 직접 마감을 풀거나 겁니다
- 채널매니저 화면에서 노출 수를 손으로 조정합니다
- 전화·워크인 예약을 채널 쪽에만 반영합니다

이것은 **(c) 역방향 쓰기**이며, 선언되지도 제외되지도 않았습니다(#21).

### 순진한 답 두 개가 모두 틀립니다

| 답 | 왜 틀리는가 |
|---|---|
| **우리가 항상 이깁니다** | 사장님의 조작을 매번 되돌립니다. 사람은 다시 바꿉니다. 무한 루프가 되고, 현장은 시스템을 신뢰하지 않게 됩니다 |
| **최신 타임스탬프가 이깁니다** | 재고의 원본이 둘이 됩니다. 이 저장소의 유일한 주장이 무너집니다. 게다가 웹훅은 순서 보장이 없어 "최신"을 알 수도 없습니다 |

두 답이 다 틀린 이유는 같습니다. **하나의 값으로 취급했기 때문입니다.**

## 결정

**하나로 보였던 것을 세 축으로 나눕니다. 축마다 원본은 하나입니다.**

| 축 | 무엇인가 | 원본 | 어긋났을 때 |
|---|---|---|---|
| **예약 사실** | 누가 언제 무엇을 샀는가 | **채널** | 채널이 이깁니다. 흡수만 합니다 |
| **재고 수량** | 남은 방이 몇 개인가 | **우리** | 우리가 이깁니다. 계산값을 재발행합니다 |
| **채널 정책** | 이 채널에 몇 개를 어떻게 보일 것인가 | **우리 정책 장부** | 채널 상태를 판정합니다 (아래) |

#### 정책 축의 원본도 하나입니다 — 채널은 관측 상태입니다

초안은 정책 축의 원본을 `양쪽` 으로 적었습니다. **"축마다 원본은 하나"라는 선언과 모순이고,
충돌 해결 기준을 주지 못합니다.** `양쪽` 이면 어긋났을 때 무엇을 기준으로 판정하는지가 없습니다.

원본은 **우리 정책 장부** 하나입니다. 채널의 현재 정책 값은 원본이 아니라 **관측 상태**입니다.
아래 판정 규칙에서 흡수가 일어나더라도 그것은 *"관측을 근거로 장부를 갱신하는 것"* 이고,
갱신된 뒤에도 **판정 기준은 여전히 장부**입니다.

이 구분이 예약 축과의 차이를 만듭니다 — 예약은 채널이 원본이라 우리가 되돌릴 수 없지만,
정책은 우리가 원본이라 되돌릴 수 있고 **그래서 기본값이 교정입니다.**

여기서 이 ADR 의 전부인 한 문장이 나옵니다.

> **`ari` 웹훅을 하나의 사건으로 읽지 않습니다.
> 페이로드의 필드마다 어느 축에 속하는지를 먼저 가릅니다.**

### 필드별 축 배분

초안은 `ari` 를 통째로 정책으로 읽었습니다. **그것이 틀렸습니다.**
`ari` 는 노출 규칙 변경과 `availability` 값 변경을 **함께** 실어 오고, 후자는 정책이 아닙니다.

| `ari` 가 알리는 것 | 사람의 의도 | 축 | 처리 |
|---|---|---|---|
| `availability` 를 **내렸습니다** | "이 채널엔 덜 팔자" — 노출 상한 | **정책** | 판정 규칙 (아래) |
| `availability` 를 **올렸습니다** | "더 팔자" — **오버부킹 요청** | **재고 축으로 넘어옵니다** | 아래 별도 절 |
| `close_out` · `availability_offset` · `max_availability` | 노출 규칙 | **정책** | 판정 규칙 |
| `restrictions` (MinLOS · CTA · CTD) | 판매 조건 | **범위 밖** (`#14`) | 기록만 합니다. 흡수도 교정도 하지 않습니다 |

갈라 보면 **채널 화면에서 사람이 하는 일의 대부분이 정책입니다.**
재고 축으로 넘어오는 것은 한 줄뿐이고, 그 한 줄에도 답이 있습니다.

### availability 를 올린 경우 — 유일하게 재고 축으로 넘어오는 입력

무조건 교정하면 **대안 1(우리가 항상 이깁니다)을 기각한 이유가 재고 축에서 재발합니다.**
사장님은 다시 올립니다. 루프입니다.

그런데 이 요청에는 이미 담을 자리가 있습니다 — `ADR-0007` 의 `overbooking_limit` 입니다.

```
채널에서 availability 10 → 12
   = "이 날짜에 2 개 더 팔고 싶다"
   = overbooking_limit 을 2 로 올려 달라는 요청
```

즉 **재고 수량을 바꾸라는 요구가 아니라 정책 한도를 바꾸라는 요구**로 번역됩니다.
번역하면 축이 정책으로 돌아오고, 원본이 둘로 갈라지지 않습니다.

```
한도 조정을 받아들인다  →  overbooking_limit 갱신. sold 와 physical_total 은 건드리지 않는다
받아들이지 않는다      →  교정하고 알린다. "왜 되돌렸는지" 가 알림에 담긴다
```

**받아들이든 않든 `physical_total` 은 채널이 바꿀 수 없습니다.** 그것이 재고 축의 원본이 우리라는 뜻입니다.
초안의 *"재고를 바꿀 수 있는 경로에 채널 화면이 없다"* 는 이렇게 고쳐 읽어야 합니다 —
**물리 객실 수를 바꾸는 경로에 채널 화면이 없습니다.**

> `ADR-0007`(오버부킹 정책)은 아직 `main` 에 없고 PR #34 에서 대기 중입니다.
> 두 PR 이 서로를 참조하므로 **머지 순서는 무관하고, 두 번째가 머지되는 시점에 양쪽 참조가 해소됩니다.**
> 한도를 담을 자리가 없다면 위 번역이 성립하지 않으므로, 이 절은 `#12` 의 결정에 의존합니다.

### 정책 축의 판정 규칙

```
ari 웹훅 수신
   │
   ├─ payload.user_id == 우리 앱 ?  ──▶ 버린다 (에코)
   │
   └─ 사람이 바꿨다
        │
        ├─ 우리 정책 장부와 일치 ?  ──▶ 아무것도 하지 않는다
        │
        └─ 불일치
             ├─ 화이트리스트에 있는 정책  ──▶ [흡수] 장부에 반영한다
             └─ 그 외                     ──▶ [교정] 장부 값으로 되돌리고 알린다
```

`availability` 값 변경은 이 규칙에 들어오기 전에 **방향으로 한 번 더 갈립니다.**

```
availability 가 바뀌었다
   ├─ 내려갔다  ──▶ 노출 상한 의도. 위 판정 규칙으로 들어간다
   └─ 올라갔다  ──▶ 한도 요청. overbooking_limit 조정 여부로 답한다 (위 절)
```

**기본값은 교정, 흡수는 화이트리스트입니다.** 근거는 예약 축과의 대칭입니다 —
예약은 되돌릴 수 없으니 무조건 흡수하고, 정책은 되돌릴 수 있으니 기본은 교정합니다.
조용히 흡수하면 장부가 언제 왜 바뀌었는지 아무도 모르게 됩니다.

`user_id` 필터는 우리가 만든 장치가 아니라 Channex 가 payload 에 넣어 주는 값입니다.
공개 문서가 용도를 명시합니다 — *"자기 앱이 만든 변경을 무시하고 싶을 때 쓸 수 있다"*.

## 이 결정이 만드는 것

**1. 채널 정책 장부.** 정책의 원본을 우리 DB 에 둡니다. 재고 테이블은 건드리지 않습니다.

**2. 장부 → 채널 투영.** Channex 는 채널별 availability 를 받지 않습니다.
availability 는 룸타입 단위 절대값이고, 채널별 차등은 규칙 세 가지로만 표현됩니다.

| 규칙 | 의미 |
|---|---|
| `close_out` | 이 채널에는 팔지 않습니다 |
| `availability_offset` | 전체에서 N 을 빼고 보여줍니다 |
| `max_availability` | 최대 N 까지만 보여줍니다 |

즉 정책 장부는 **카운터가 아니라 투영 규칙의 원본**입니다.

**3. 에코 필터.** 우리가 밀어넣은 변경이 되돌아오는 것을 `user_id` 로 걸러냅니다.

## 불변식은 늘어나지 않습니다

이 결정에서 가장 중요한 귀결입니다.

**정책은 불변식이 아니라 수렴 대상입니다.**

```
재고 : 언제 어느 순간에도 참이어야 한다        → INV-1 · INV-2 · INV-3
정책 : 유한 시간 안에 장부 값으로 수렴하면 된다  → 불변식 아님
```

채널의 정책 값이 지금 우리 장부와 다른 것은 **위반이 아닙니다.**
다음 대사 주기에 수렴하면 정상입니다. B6 이 재고에 대해 하는 일과 같은 성질입니다.

따라서 이 ADR 은 **`INV-` 를 하나도 추가하지 않습니다.**
검증해야 할 등식이 늘지 않고, T1~T4 는 그대로 유효합니다.

## 기각한 대안

### 대안 1: 우리가 항상 이깁니다 — 교정 전용

정책 축을 없애고 모든 `ari` 웹훅을 "덮어쓸 대상"으로 취급합니다.

기각 이유는 **루프**입니다. 사람이 화면에서 바꾸는 데는 이유가 있고, 되돌리면 다시 바꿉니다.
그리고 이 구조는 현장에 "시스템이 내 조작을 먹는다"를 학습시킵니다.
`00-problem-definition.md`가 문제 삼은 **확인 업무**를 오히려 늘립니다.

### 대안 2: LWW (Last Write Wins) — 최신 타임스탬프가 이깁니다

**주 기각 이유는 원본이 둘이 된다는 것입니다.** 재고 수량의 최종 권위가 상황에 따라 달라지고,
그러면 이 저장소의 유일한 주장이 무너집니다. **이 근거는 채널이 무엇을 주든 유효합니다.**

두 번째 근거는 초안보다 좁혀 적어야 합니다. 초안은 *"순서 보장이 없으니 최신을 알 수 없다"* 고
단정했는데, 정확히는 **도착 순서로는 알 수 없다**는 뜻입니다.
웹훅 페이로드에 이벤트 생성 시각이 담겨 있으면 그것으로 판정할 여지가 있습니다.

그래서 두 번째 근거를 이렇게 좁힙니다 — **source 시각 기반 LWW 를 쓰려면 먼저 확인할 것이 있습니다.**

| 확인할 것 | 확인되지 않으면 |
|---|---|
| **신뢰성** — 채널이 채운 값인가, 중계 시점인가 | 인과 순서를 대표하지 못합니다 |
| **정밀도** — 초 단위면 같은 초의 두 변경을 가를 수 없습니다 | 동률이 흔해집니다 |
| **동률 처리** — 같은 시각의 두 이벤트를 무엇으로 가르는가 | 판정이 비결정적이 됩니다 |

예약 축에는 리비전 식별자가 있어 순서를 재구성할 수 있지만 **`ari` 에는 대응물이 없습니다.**

따라서 확인 전에는 LWW 를 쓰지 않으며, **확인이 되더라도 첫 번째 근거 때문에 재고 축에는 쓰지 않습니다.**
정책 축의 동률 판정에 쓸 여지는 남겨 두고, 그 조건을 재검토 조건에 적습니다.

### 대안 3: 채널별 재고 카운터를 둡니다

정책이 아니라 재고를 채널별로 쪼갭니다. ADR-0001 의 allocated / hybrid 가 이것입니다.

기각 이유는 **표현 수단이 없다**는 것입니다.
Channex 의 availability push 는 룸타입 단위이며 채널별 값을 받지 않습니다.
채널별 카운터를 우리 DB 에 만들어도 채널에 그대로 내보낼 방법이 없고,
결국 규칙으로 투영해야 합니다 — 즉 이 ADR 의 정책 축으로 되돌아옵니다.

ADR-0001 개정본의 캡형·보장형 구분이 여기서 나옵니다.

## 결과

**`00-problem-definition.md`의 (c) 역방향 쓰기가 범위에 들어옵니다.**
다만 전면 양방향 동기화가 아니라 **정책 축으로 좁혀서** 들어옵니다.
재고 축의 원본은 여전히, 그리고 앞으로도 우리입니다.

대사의 구체적 설계 — 세 방향, ack 순서, 취소·수정 처리 — 는 `docs/07-reconciliation.md`.

**남는 부담은 장부 하나와 투영 로직입니다.** 카운터도, 불변식도 늘지 않습니다.

## 재검토 조건

1. **`availability` 조정이 한도 요청으로 번역되지 않는 경우가 나옵니다** — 채널이 물리 객실 수에 해당하는 값을 직접 편집하게 하면 번역이 성립하지 않고 **재고 축의 원본이 실제로 둘이 됩니다.** 그때는 필드별 배분이 아니라 축 분리 자체를 다시 봅니다
2. **정책 흡수 화이트리스트가 사실상 전체가 됩니다** — 그때는 정책의 원본이 채널이라는 뜻이므로 축의 방향을 뒤집어야 합니다
3. **교정 알림이 운영 소음이 됩니다** — 판정 규칙의 기본값을 교정에서 흡수로 바꿀 근거가 됩니다

## 결론

원본이 둘이 되는 문제를 **어느 쪽이 이기는가**로 풀지 않았습니다.
**무엇에 대해 이기는가를 나누어** 풀었습니다.

한 값을 두고 다투면 답이 없습니다. 축을 나누면 축마다 답이 하나입니다.
