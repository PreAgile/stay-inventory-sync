# ADR-0004. Kafka를 도입하지 않습니다 — 다만 경계는 지금 만듭니다

## 상태
확정 (재검토 조건 명시)

## 맥락

"Outbox 릴레이는 결국 규모가 커지면 Kafka로 가야 하지 않나?"

타당한 질문입니다. 다만 **언제, 왜 가야 하는가**에 답해야 합니다.

## 결정

이번 범위에서는 **DB 폴링 기반 릴레이**를 사용합니다.
단, 발행 대상을 인터페이스로 분리해 전환 비용을 최소화합니다.

```java
public interface EventPublisher {
    void publish(OutboxEvent event);
}

// 현재
class DirectChannelPublisher implements EventPublisher { ... }

// 전환 시
class KafkaEventPublisher implements EventPublisher { ... }
```

릴레이는 `EventPublisher`만 알고, 구현체가 무엇인지는 모릅니다.
**Outbox 패턴 자체가 전송 수단을 가리지 않는다는 점이 이 결정의 근거입니다.**

## Kafka가 해결하지 않는 것

가장 중요한 지점입니다.

**채널 동기화의 병목은 내부 처리량이 아니라 외부 API의 레이트 리밋입니다.**
프로퍼티당 분당 20건이라는 제약은 Kafka를 넣는다고 완화되지 않습니다.
Kafka를 도입해도 컨슈머는 여전히 초당 0.33건으로 스로틀링해야 합니다.

즉, **지금 겪는 문제에 대해 Kafka는 답이 아닙니다.**
`04-capacity-and-limits.md` 참고.

## Kafka가 실제로 해결하는 것

| 문제 | Kafka의 기여 |
|---|---|
| 컨슈머가 여럿 (채널 동기화 + 정산 + 분석) | 팬아웃. 발행 측이 소비자를 모릅니다 |
| 이벤트 재생 필요 (버그 수정 후 재처리) | 리텐션 기간 내 오프셋 리셋 |
| 릴레이 폴링이 DB에 부담 | outbox 테이블 스캔 제거 |
| 서비스 분리 | 프로세스 경계를 넘는 전달 |
| 키 단위 순서 보장 | 파티션 키 기반 |

**현재 컨슈머는 하나뿐이고, 서비스는 분리되어 있지 않으며,
outbox 테이블은 인덱스 스캔으로 충분합니다.**
다섯 가지 중 어느 것도 지금은 성립하지 않습니다.

## 도입 조건 (재검토 트리거)

다음 중 하나가 참이 되면 ADR을 다시 봅니다.

1. **컨슈머가 2개 이상이 됩니다** — 예: 정산 시스템이 예약 이벤트를 구독
2. **릴레이 폴링이 측정 가능한 DB 부하가 됩니다** — outbox 스캔이 p99에 영향
3. **서비스가 분리됩니다** — 프로세스 경계를 넘는 전달 필요
4. **이벤트 재생 요구가 발생합니다** — 과거 이벤트 재처리

1번이 가장 먼저 올 가능성이 높습니다.

## 마이그레이션 경로

### 1단계: Publisher 교체
`DirectChannelPublisher` → `KafkaEventPublisher`.
릴레이 로직은 그대로 둡니다. outbox 테이블도 그대로 유지합니다.

### 2단계: Debezium CDC로 폴링 제거
outbox 테이블의 WAL을 Debezium이 읽어 Kafka로 직접 흘려보냅니다.
릴레이 프로세스 자체가 사라집니다.

이때 `outbox_event` 테이블 스키마가 CDC에 적합해야 하므로,
`aggregate_type`, `aggregate_id`, `event_type`, `payload` 컬럼 구성을
**지금부터 Debezium Outbox Event Router의 관례에 맞춰 두었습니다.**
전환할 때 스키마를 바꿀 필요가 없습니다.

### 파티션 키

**`property_id`가 아니라 `(room_type_id, stay_date)`여야 합니다.**

동일 날짜 재고에 대한 이벤트 순서가 뒤집히면
기회손실이나 오버부킹이 발생합니다(`04-capacity-and-limits.md` 참고).
프로퍼티 단위 파티셔닝은 이 순서를 보장하지 못합니다.

이 판단은 Kafka 도입 시점이 아니라 **지금 문서화되어야 합니다.**
도입한 뒤에 파티션 키를 바꾸는 것은 재파티셔닝을 뜻하기 때문입니다.

## 결론

Kafka는 "나중에 필요할 수도 있는 것"이 아니라
**"조건이 충족되면 도입할 것"**입니다. 조건을 명시했고, 경로를 설계했고,
그 경로에 필요한 스키마를 미리 맞춰 두었습니다.

지금 도입하지 않는 것은 회피가 아니라 판단입니다.
