# ADR-0003. Outbox 패턴으로 dual-write를 제거하고, 멱등으로 중복을 흡수한다

## 상태
확정

## 맥락

예약 확정 시 두 가지가 일어나야 한다.

1. 내부 DB에 예약 저장 + 재고 차감
2. 외부 채널에 재고 변경 통보

이 둘은 서로 다른 트랜잭션 도메인에 속한다(로컬 DB vs 외부 HTTP).
2PC는 외부 채널이 참여하지 않으므로 불가능하다.

## 결정

**Outbox 패턴**을 사용한다.

```
[트랜잭션 T1]  reservation INSERT
              daily_inventory UPDATE
              outbox_event INSERT        ← 같은 트랜잭션
              COMMIT

[별도 프로세스] 릴레이가 PENDING 이벤트를 폴링
              ChannelAdapter 호출
              성공 시 PUBLISHED 마킹
```

## 기각한 대안 1: 트랜잭션 내에서 직접 외부 호출

가장 흔한 실수다. 세 가지 문제가 있다.

- 외부 API 지연이 DB 락 보유 시간이 된다 → 커넥션 풀 고갈
- 외부 호출 성공 후 커밋 실패 시 되돌릴 수 없다
- 외부 장애가 예약 접수 자체를 막는다 (가용성 결합)

## 기각한 대안 2: `@TransactionalEventListener(AFTER_COMMIT)`

커밋 후 발행이므로 락 문제는 없으나,
**커밋 직후 애플리케이션이 죽으면 이벤트가 영구 소실된다.**
이벤트가 메모리에만 존재하기 때문이다.

Outbox는 이벤트를 DB에 물리적으로 남기므로 이 창(window)이 존재하지 않는다.
이것이 두 방식의 결정적 차이다.

## 기각한 대안 3: 메시지 브로커 직접 발행

동일한 dual-write 문제가 DB↔브로커 사이로 이동할 뿐이다.
해결되지 않는다. (Kafka 논의는 ADR-0004)

## 결과 — at-least-once

릴레이가 채널 호출에 성공한 직후, `PUBLISHED` 마킹 전에 죽으면
재기동 시 동일 이벤트를 다시 발행한다.

**이는 버그가 아니라 Outbox의 정의상 필연이다.**
정확히 한 번은 발행 측에서 만들 수 없다.

따라서 **수신 측 멱등성이 필수 요구사항**이 된다.

### 멱등의 3중 방어

| 계층 | 수단 | 막는 것 |
|---|---|---|
| DB 제약 | `UNIQUE(channel, channel_reservation_id)` | 최종 방어. 경합으로 앱 로직이 뚫려도 막힘 |
| 애플리케이션 | 수신 시 기존 예약 조회 후 조기 반환 | 정상 경로에서의 중복 |
| 어댑터 | 요청에 멱등키(`outbox_event.id`) 첨부 | 채널 측 중복 처리 |

### 중복 수신 시 응답 코드

**2회차 이후도 200 OK를 반환한다.**
409나 4xx를 반환하면 채널이 이를 실패로 간주해 재시도를 반복한다.
Channex 기준 최대 10회, 약 24시간에 걸쳐 재시도가 이어진다.
멱등하게 처리했다면 그것은 성공이다.

## 검증

테스트 T3(중복 웹훅 10회), T4(Outbox 재발행)로 증명한다.
