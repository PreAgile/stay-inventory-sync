# ADR-0002. 재고 차감에 비관적 락을 사용하고, 락 순서를 고정한다

## 상태
확정

## 맥락

ADR-0001에 따라 경합이 단일 행에 집중된다.
또한 다일 예약은 여러 날짜 행을 동시에 잠근다.

## 결정

1. `SELECT ... FOR UPDATE`로 대상 날짜 행을 잠근다.
2. **락 획득 순서를 `stay_date` 오름차순으로 고정한다.**
3. 트랜잭션 격리 수준은 READ COMMITTED(PostgreSQL 기본)를 유지한다.

## 기각한 대안 1: 낙관적 락 (`@Version`)

고경합 워크로드에서 재시도가 폭발한다.
성수기 주말 단일 날짜에 수십 건의 동시 요청이 몰리면
대부분이 버전 충돌로 실패하고 재시도하며, 유효 처리량이 급락한다.

**조건부 재검토**: 경합률이 실측으로 낮다고 확인되면 낙관적 락이 우세하다.
락 대기가 없고 커넥션 점유 시간이 짧기 때문이다.
현재는 측정 데이터가 없으므로 최악의 경우(성수기 인기 날짜)를 기준으로 선택했다.

## 기각한 대안 2: SERIALIZABLE 격리 수준

정확성은 보장되나 PostgreSQL에서 직렬화 실패 예외가 빈발하며,
결국 애플리케이션에서 재시도 루프를 구현해야 한다.
낙관적 락과 동일한 문제를 더 불투명한 형태로 얻는 셈이다.

## 기각한 대안 3: Redis 분산 락

인프라 의존성이 추가되고, DB 트랜잭션과 락의 생명주기가 분리된다.
락 해제와 커밋 사이의 틈에서 일관성이 깨질 수 있으며,
이를 막으려면 결국 DB 락과 동등한 복잡도를 재구현하게 된다.
단일 DB로 해결 가능한 문제에 분산 락을 도입할 이유가 없다.

## 결과 — 락 순서 고정의 필요성

다일 예약은 여러 행을 잠근다. 예를 들어

```
요청 A: 3/1 ~ 3/3   →  3/1, 3/2 잠금
요청 B: 3/2 ~ 3/4   →  3/2, 3/3 잠금
```

A가 3/1을 잡고 3/2를 기다리는 동안 B가 3/2를 잡고 3/3을 기다리면 데드락은 없다.
그러나 요청마다 락 순서가 달라지면(예: 역순 순회) 순환 대기가 성립한다.

**`stay_date` 오름차순 정렬로 전역 순서를 강제하면 순환이 원천적으로 불가능하다.**

이 결정은 테스트 T2로 검증한다.
정렬 로직을 제거하면 T2가 실패해야 하며, 실패하지 않으면 테스트가 잘못된 것이다.

## 부가 결정

- 락 타임아웃을 설정한다. 무한 대기는 커넥션 풀을 고갈시킨다.
- 트랜잭션 범위를 최소화한다. 락 구간 안에서 외부 API를 호출하지 않는다
  (Outbox가 이를 구조적으로 보장한다 → ADR-0003).
