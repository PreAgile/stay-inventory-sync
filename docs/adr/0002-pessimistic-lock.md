# ADR-0002. 재고 차감에 비관적 락을 사용하고, 락 순서를 고정합니다

## 상태
확정

## 맥락

ADR-0001에 따라 경합이 단일 행에 집중됩니다.
또한 다일 예약은 여러 밤을 이어서 묵는 예약이므로 여러 날짜 행을 동시에 잠급니다.

## 결정

1. `SELECT ... FOR UPDATE`로 대상 날짜 행을 잠급니다.
2. **락 획득 순서를 `stay_date` 오름차순으로 고정합니다.**
3. 트랜잭션 격리 수준은 READ COMMITTED(PostgreSQL 기본)를 유지합니다.

## 기각한 대안 1: 낙관적 락 (`@Version`)

경합이 심한 워크로드에서는 재시도가 폭발합니다.
성수기 주말 단일 날짜에 수십 건의 동시 요청이 몰리면
대부분이 버전 충돌로 실패하고 재시도하며, 유효 처리량이 급락합니다.

**조건부 재검토**: 경합률이 실측으로 낮다고 확인되면 낙관적 락이 우세합니다.
락 대기가 없고 커넥션 점유 시간이 짧기 때문입니다.
지금은 측정 데이터가 없으므로 최악의 경우(성수기 인기 날짜)를 기준으로 선택했습니다.

## 기각한 대안 2: SERIALIZABLE 격리 수준

정확성은 보장되지만 PostgreSQL에서는 직렬화 실패 예외가 빈발하고,
결국 애플리케이션에서 재시도 루프를 구현해야 합니다.
낙관적 락과 같은 문제를 더 불투명한 형태로 얻는 셈입니다.

## 기각한 대안 3: Redis 분산 락

인프라 의존성이 추가되고, DB 트랜잭션과 락의 생명주기가 분리됩니다.
락 해제와 커밋 사이의 틈에서 일관성이 깨질 수 있고,
이를 막으려면 결국 DB 락과 같은 수준의 복잡도를 다시 구현하게 됩니다.
단일 DB로 해결할 수 있는 문제에 분산 락을 도입할 이유가 없습니다.

## 결과 — 락 순서 고정의 필요성

다일 예약은 여러 행을 잠급니다. 예를 들어

```
요청 A: 3/1 ~ 3/3   →  3/1, 3/2 잠금
요청 B: 3/2 ~ 3/4   →  3/2, 3/3 잠금
```

A가 3/1을 잡고 3/2를 기다리는 동안 B가 3/2를 잡고 3/3을 기다리면 데드락은 없습니다.
그러나 요청마다 락 순서가 달라지면(예: 역순 순회) 순환 대기가 성립합니다.

**`stay_date` 오름차순 정렬로 전역 순서를 강제하면 순환이 원천적으로 불가능합니다.**

이 결정은 테스트 T2로 검증합니다.
정렬 로직을 제거하면 T2가 실패해야 하고, 실패하지 않으면 테스트가 잘못된 것입니다.

## 부가 결정

- 락 타임아웃을 설정합니다. 무한 대기는 커넥션 풀을 고갈시킵니다.
- 트랜잭션 범위를 최소화합니다. 락 구간 안에서 외부 API를 호출하지 않습니다
  (Outbox가 이를 구조적으로 보장합니다 → ADR-0003).
