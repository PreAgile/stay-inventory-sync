# ADR-0010. 선점(hold)과 승인 대기를 상태 기계에 들인다

## 상태

확정

## 맥락 — 현재 모델은 즉시확정 하나만 전제한다

차감 알고리즘 7번이 재고 차감과 `reservation` INSERT 를 **같은 트랜잭션**에서 한다.
그래서 예약은 처음부터 `CONFIRMED` 로 들어가고, **`PENDING` 이 DB 에 존재하는 순간이 없다.**

실제 예약 흐름에는 **재고가 잡혀 있지만 아직 확정이 아닌 구간이 둘** 있다.

```
① 고객이 예약하기를 누르고 카드 정보를 넣는 동안
     → 이 방을 남이 채가면 안 된다. 그런데 확정도 아니다

② 결제가 끝나고 사장님이 확인을 누를 때까지 (승인형 · on-request)
     → 여기서도 재고는 잡혀 있어야 한다. 그런데 확정도 아니다
```

둘을 담을 자리가 `PENDING` 하나로 있는데 죽어 있다. 그리고 상태 전이도에는
`PENDING -> CANCELED : 결제 실패` 라고 적혀 있으나 **결제는 `02-scope.md` 에
포함으로도 제외로도 선언되어 있지 않았다**(`#28` 문제 1).

### `PENDING` 은 살아남는 것이 아니라 쪼개져야 한다

`#28` 은 `PENDING` **제거**를 제안했다. 실전 흐름을 들이면 정반대다.

| | 선점 주체 | 시한 | 만료 시 보상 |
|---|---|---|---|
| `HELD` | 고객이 결제를 안 눌렀다 | 짧다 (분) | 없음 |
| `PENDING_APPROVAL` | 사장님이 확인을 안 눌렀다 | 길다 (시간) | 있다 (카드 승인 취소) |

성질이 다른 두 대기를 한 상태에 담으면 시한도 보상 동작도 조건문으로 갈라야 하고,
**그 조건문을 잊는 시점이 온다.**

## 결정 1 — 선점을 `daily_inventory` 가 아니라 별도 테이블에서 센다

```sql
CREATE TABLE inventory_hold (
    id             BIGSERIAL   PRIMARY KEY,
    room_type_id   BIGINT      NOT NULL,
    stay_date      DATE        NOT NULL,   -- daily_inventory 와 같은 결
    reservation_id BIGINT      NOT NULL,   -- 다일 선점을 묶는 키를 겸한다
    room_count     INT         NOT NULL CHECK (room_count > 0),  -- A7
    expires_at     TIMESTAMPTZ NOT NULL,   -- 만료 판정
    released_at    TIMESTAMPTZ,            -- 전환·해제 판정. NULL 이면 살아 있다

    FOREIGN KEY (room_type_id, stay_date) REFERENCES daily_inventory (room_type_id, stay_date),
    FOREIGN KEY (reservation_id) REFERENCES reservation (id)
);

CREATE INDEX ix_hold_live ON inventory_hold (room_type_id, stay_date)
    WHERE released_at IS NULL;
```

날짜당 1행이다. `INV-4` 가 `(room_type_id, stay_date)` 단위 등식이므로
결을 `daily_inventory` 와 맞추면 집계에 날짜 범위 조건이 들어가지 않는다. 3박이면 3행이다.

`reservation_id` 가 묶는 키를 겸한다. 예약 1건이 곧 하나의 선점 묶음이므로 별도 그룹 키를
두지 않는다. 예약 없이 선점만 하는 경로(장바구니 등)가 생기면 그때 도입한다.

### 새 불변식 하나. 기존 불변식은 그대로

```
INV-1  0 <= sold <= total                          변경 없음
       total = physical_total + overbooking_limit   (ADR-0007)
INV-2  sold == SUM(점유 예약의 room_count)           변경 없음 (#25 · A7)
INV-3  check_in < check_out                        변경 없음
INV-4  sold + SUM(유효 선점의 room_count) <= total   신규 — 과선점 금지

유효 선점 = expires_at > now()          만료되지 않았고
            AND released_at IS NULL     아직 확정·해제되지도 않았다
```

**`sold` 의 의미가 바뀌지 않는 것이 이 선택의 핵심이다.**
`sold` 는 계속 "확정 판매"만 뜻하므로 `INV-2` 를 다시 열지 않아도 되고,
전환율·만료율·거절률을 별도 계산 없이 뽑을 수 있다.

`ADR-0007` 과 `A7` 이 여기서 회수된다 — `INV-4` 의 좌변에 `room_count`,
우변에 `physical_total + overbooking_limit` 이 그대로 들어온다.
**두 결정을 이 ADR 보다 먼저 처리한 이유가 이것이다.**

### 유효 선점은 조건이 둘이다 — 하나로 두면 확정 직후에 깨진다

`expires_at` 만으로 판정하면 **확정된 예약이 남은 시한 동안 재고를 두 번 차지한다.**

```
total = 1, sold = 0
t=0    선점. expires_at = t+10                INV-4:  0 + 1 = 1 <= 1   OK
t=3    결제 성공 -> CONFIRMED. sold = 1
       선점 행의 expires_at 은 여전히 t+10 > now
       INV-4:  1 + 1 = 2 > 1                                    위반
```

검증기가 빨간불을 띄우는 데서 끝나지 않는다. **확정된 방이 남은 시한 동안 판매 불가가 된다.**

두 조건이 서로 다른 축을 본다.

| 조건 | 무엇을 본다 | 누가 쓴다 |
|---|---|---|
| `expires_at > now()` | **만료** — 시간이 지났는가 | 아무도. 시간이 지나면 자동 |
| `released_at IS NULL` | **전환** — 확정되거나 해제되었는가 | 상태 전이가 같은 트랜잭션에서 |

행을 삭제하는 대안도 있었다. 판정 조건이 하나로 줄지만 기록이 사라진다 —
만료로 끝난 선점과 확정으로 끝난 선점을 사후에 구분할 수 없어 지표를 다른 곳에서 만들어야 한다.
`07-reconciliation.md` 가 에코를 버리지 않고 `IGNORED` 로 표시하는 논거와 같은 이유로 **행을 남긴다.**

## 결정 2 — 만료를 상태가 아니라 시간 조건으로 판정한다

`expires_at > now()` 를 **조회 조건**에 둔다. 만료된 선점은 애초에 세지지 않는다.

```
스케줄러가 죽는다
  → held 컬럼 방식 :  만료 재고가 영구히 잠긴다. 기회손실이 쌓인다
  → 시간 조건 방식 :  아무 일도 없다. 만료된 선점은 세지지 않는다
```

**스케줄러의 역할이 정합성에서 통보로 내려간다.** 이것이 이 결정의 전부다.

`#26` 이 복원 조건을 `WHERE status = 'CONFIRMED'` 로 쿼리에 박아 "잊어버릴 수 없는 형태"를
만든 것과 같은 수법이다. 조건이 코드가 아니라 쿼리에 있으면 지울 때 이유를 설명해야 한다.

부수 효과가 하나 있다. **만료를 만들려고 시계를 조작할 필요가 없다** —
`expires_at` 을 과거 값으로 넣으면 끝이다. 동시성 테스트에서 시간을 다루지 않아도 된다.

## 결정 3 — 락 대상은 늘지 않는다. 대신 절대 규칙이 하나 는다

```
선점 잡기
1. [check_in, check_out) 날짜를 오름차순 정렬               <- ADR-0002 그대로
2. 각 날짜의 daily_inventory 행을 SELECT ... FOR UPDATE     <- 직렬화 지점, 그대로
3. 각 날짜에 대해  sold + SUM(유효 선점) + room_count <= total  검증
4. 하나라도 실패하면 전체 롤백
5. 전부 통과하면 reservation INSERT (status = HELD)
6. 동일 트랜잭션에서 inventory_hold INSERT (날짜당 1행, expires_at = now() + 결제 시한)
```

**2번에서 잠근 `daily_inventory` 행을 3~6번에서 바꾸지 않는다.** 그 행은 순수하게 뮤텍스로 쓰인다.
그런데 선점을 잡으려는 **모든** 트랜잭션이 반드시 그 락을 먼저 지나가므로,
집계와 INSERT 사이에 다른 트랜잭션이 끼어들 수 없다.

따라서 **테이블이 하나 늘었는데 락 순서는 늘지 않는다.**
`#27` 의 `reservation -> daily_inventory` 규칙이 그대로 유효하다.

5번이 6번보다 앞인 이유는 `inventory_hold.reservation_id` 가 NOT NULL 이기 때문이다.
INSERT 는 기존 행과 경합하지 않으므로 이 순서가 락 구조를 바꾸지 않는다.

### 절대 규칙 11 이 이 결정의 방어다

> `inventory_hold` 행은 해당 `(room_type_id, stay_date)` 의
> `daily_inventory` 행 락을 보유한 상태에서만 읽고 쓴다.

이 규칙이 없으면 나중에 누군가 *"이 행은 UPDATE 도 안 하는데 왜 잠그는가"* 로 락을 지운다.
그 순간 과선점이 열리고, `INV-4` 가 깨진 원인을 역추적하기가 매우 어렵다.

**`ADR-0002` 가 `stay_date` 정렬을 절대 규칙으로 올린 것과 같은 이유다** —
지우기 쉬운 한 줄이 방어의 전부일 때.

## 결정 4 — 승인 시한 초과는 자동 거절이다

`HELD` 와 `PENDING_APPROVAL` 은 **시한 길이만 다르고 만료 장치는 하나로 통일된다.**
결제 성공 시 `expires_at` 을 승인 시한으로 **연장**한다.

```
[*] -> HELD                          expires_at = now() + 결제 시한
        |
        +- 시한 초과            -> EXPIRED           선점 자동 해제
        +- 결제 실패            -> EXPIRED           선점 자동 해제
        +- 결제 성공
             |  expires_at 을 승인 시한으로 연장
             +- 즉시확정  -> CONFIRMED               선점 해제 + sold += room_count
             +- 승인형    -> PENDING_APPROVAL
                   |
                   +- 사장님 승인    -> CONFIRMED    선점 해제 + sold += room_count
                   +- 사장님 거절    -> REJECTED     선점 해제 + 승인 취소
                   +- 시한 초과      -> EXPIRED      선점 해제 + 승인 취소

CONFIRMED -> CHECKED_IN -> CHECKED_OUT
CONFIRMED -> CANCELED                              재고 복원 (#26)
CHECKED_IN -> TERMINATED                           노쇼. 복원 없음 (결정 8)
```

`expires_at` 하나로 두 구간을 다루므로 **만료 판정에 `reservation.status` 를 볼 필요가 없다.**

기각: **자동 승인.** 기각 근거가 둘이고 성질이 다르므로 갈라 적는다.

- **운영 위험** — 사장님이 모르는 상태에서 방이 확정 판매되어 오프라인 현장과 충돌한다.
  거절할 기회가 없으므로 승인형을 도입한 이유 자체가 사라진다
- **정합성 구조** — 자동 승인은 시한 초과 시 `CONFIRMED` 로 보내며 **`sold` 를 올린다.**
  즉 만료 처리가 재고를 바꾸는 사건이 되고, 그러면 결정 2 의 lazy 판정이 성립하지 않는다 —
  누군가 실행해야 하므로 **스케줄러가 다시 정합성 경로에 들어온다**

반면 이 ADR 이 택한 자동 거절은 만료 시 **`sold` 를 건드리지 않고 선점만 해제**한다.
그것이 스케줄러를 정합성 책임에서 빼낼 수 있는 이유다.

기각: **무기한 대기.** `expires_at` 이 NULL 이 되어 만료 판정에 NULL 분기가 들어온다.
그러면 "시간이 지났는가"를 시간 비교로 답할 수 없고, 이 설계의 가장 좋은 성질을 직접 깬다.

## 결정 5 — 결제는 승인·청구 모델을 근거로 적고, 구현은 결과 신호만 받는다

```
HELD              -> 카드 승인 (authorization)
PENDING_APPROVAL  -> 승인 걸린 상태로 대기
   사장님 승인      -> capture (청구)
   사장님 거절      -> void    (환불이 아니다)
```

**승인·청구를 쓰면 환불 경로가 상태 기계에 들어오지 않는다.** 거절 시 청구를 안 하므로
되돌릴 것이 없고, `REFUNDING` · `REFUNDED` 두 상태가 사라진다.

구현 범위는 **결제 성공·실패 신호를 받는 엔드포인트까지**다. PG 연동은 범위 밖(`02-scope.md`).
절단 기준을 적용한 결과다 — 결제 그 자체가 없어도 재고 정합성 주장은 무너지지 않는다.

기각: **선결제 + 환불 보상.** `REFUNDING` · `REFUNDED` 가 들어오고 부분 환불·환불 실패가 따라온다.
Outbox 를 보상 트랜잭션에 쓰는 증명은 매력적이지만 Tier 0 를 흔들 위험이 크다.

## 결정 6 — 만료 시 승인 취소는 얇은 스케줄러가 발행한다

재고는 결정 2 로 자동 해제되지만 **카드 승인 취소는 실행자가 필요하다.**
Lazy 판정은 아무것도 실행하지 않는다.

스케줄러가 하는 일은 둘뿐이다.

```
만료 선점을 찾아  ->  released_at 마킹  +  outbox_event INSERT (승인 취소)
```

**이 스케줄러는 정합성 책임이 없다.** 장애로 며칠 멈춰도 과선점이나 오버부킹이 발생하지 않는다.
재고 해제는 이미 시간 조건이 보장하기 때문이다.

이것이 이 ADR 이 남기는 문장이다 — **장애 범위가 문서에 명시된 스케줄러는 운영하기 쓸만해진다.**
"이게 멈추면 무엇이 깨지는가"에 *"통보가 늦어진다"* 로 답할 수 있는 것과
*"재고가 틀어진다"* 로 답해야 하는 것은 운영상 완전히 다른 물건이다.

기각: **다음 조회 시 함께 처리(lazy 발행).** 예약이 안 들어오는 날짜는 승인 취소가 무한정 지연된다.
**가장 한산한 재고에서 취소가 가장 늦어지는 역전 구조**이고, 그 사이 고객 카드에 승인이 걸려 있다.

기각: **범위 밖으로 밀기.** "그럼 만료된 승인은 누가 푸는가"가 미결로 남는다.
재고 축은 닫히지만 설계 질문 하나가 열린 채 남는다.

## 결정 7 — 즉시확정 / 승인형은 룸타입 × 채널 교차 속성이다

현장은 *"이 방은 직판만 즉시확정, OTA 는 승인형"* 같은 조합이 일상이므로 속성이 교차한다.

**다만 지금 교차 테이블을 만들지 않는다.** 룸타입 속성으로 시작한다.

```
room_type.booking_mode = INSTANT | ON_REQUEST
```

**확장의 형태를 명시한다** — 증분은 `(room_type_id, channel)` 교차 테이블 한 장이며
상태 기계와 불변식은 재작성되지 않는다. 승인 시한(결정 10)이 그 테이블에 자연히 합쳐진다.

`ADR-0001` 이 hybrid 에 쓴 수법과 같다.
**확장 가능성만 적으면 담보되지 않고, 형태를 적어야 담보된다.**

## 결정 8 — 체크인 이후 종료는 취소가 아니라 중도 종료다

`#28` 문제 2 의 답이다. **`CHECKED_IN -> CANCELED` 를 만들지 않는다.**

만들면 `INV-2` 가 깨진다. `CANCELED` 는 재고 점유 집합에서 빠지는데(`#25`) 복원은 하지 않으므로
`sold` 는 그대로다. 즉 **복원 여부를 정하기 전에 그것이 취소인지 중도 종료인지를 먼저 갈라야 한다.**

```
CHECKED_IN -> TERMINATED       노쇼. 복원 없음

재고 점유 상태 = { CONFIRMED, CHECKED_IN, CHECKED_OUT, TERMINATED }
```

`TERMINATED` 를 점유 집합에 넣으면 `INV-2` 가 그대로 성립하고 **절대 규칙 7 도 유지된다.**
그리고 `#26` 의 조건부 UPDATE 가 `WHERE status = 'CONFIRMED'` 그대로 살아서
**복원 알고리즘이 커지지 않는다.**

`#25`(PR #32)가 점유 집합을 **열거가 아니라 "차감된 채로 남아 있는가"라는 규칙으로** 정의했으므로,
`TERMINATED` 는 그 규칙에서 **자동으로 점유로 도출된다.** 이 결정은 정정이 아니라 확장이다.

### 조기 퇴실은 범위 밖이다

| | 사용 | 남은 재고 |
|---|---|---|
| 노쇼 | 0박 | 당일은 이미 못 판다. 복원이 무의미하다 |
| 조기 퇴실 | 3박 중 1박 | 남은 2박은 **아직 팔 수 있다.** 부분 복원에 가치가 있다 |

조기 퇴실을 들이면 복원이 전부/전무에서 **날짜별 부분 연산**으로 바뀌고,
`INV-2` 가 "이 예약이 이 날짜를 점유하는가"를 상태만으로 판정할 수 없게 된다 —
예약당 유효 날짜 범위가 필요해진다. `#26` 이 맞물려 커진다.

### 왜 노쇼는 범위 밖으로 밀지 않았나

**범위 밖 설정의 진짜 리스크는 상황이 사라지는 것이 아니라 현장이 우회 경로를 만드는 것이다.**

노쇼는 하루 5~15% 로 일상이다(`ADR-0007`). 표현할 상태가 없으면 사장님은 가장 가까운 것을 고르고,
그것은 `CANCELED` 다. 그 순간 재고가 부풀고 그 자리에 새 예약이 들어오면 **오버부킹**이다.
상태 하나를 추가하는 비용이 우회 경로가 만드는 비용보다 훨씬 싸다.

`#14`(restrictions 제외)와 성격이 다른 지점이다 — restrictions 는 없어도 사장님이 다른 것을 누르지 않는다.

## 결정 9 — 결제 성공과 선점 만료가 경합하면 재선점을 시도한다

결제 게이트웨이 응답이 늦어 시한을 넘겨 성공 통보가 오는 경우다. 실무에서 실제로 일어난다.

```
HELD -> PENDING_APPROVAL (또는 CONFIRMED) 전이 시
   유효 선점 재검증
     ├─ 유효           -> 전이. expires_at 을 승인 시한으로 연장
     ├─ 만료 · 재고 있음 -> 같은 트랜잭션에서 재선점 후 전이
     │                     expires_at = now() + 승인 시한 (결제는 이미 끝났다)
     └─ 만료 · 재고 없음 -> 전이 거부. 승인 취소 이벤트 발행
```

재선점은 **결정 3 의 선점 잡기 경로를 그대로 돌리는 것**이므로 새 로직이 아니다.
`daily_inventory` 행 락과 `INV-4` 검증을 같이 지나가므로 과선점이 생기지 않는다.

기각: **무조건 실패 + 승인 취소.** 계약이 명확해지고 테스트가 짧아진다.
그러나 **재고가 남아 있는데도 고객을 돌려보내는 것**은 지연의 책임을 고객에게 넘기는 선택이다.
게이트웨이 지연은 고객 잘못이 아니고, 그 상황에서 파는 것이 손실이 아니다.

기각: **결제 승인 전에 재고를 재확인한다.** void 경로가 줄어들 것 같지만 줄지 않는다.
결제는 우리 트랜잭션 밖에서 진행되므로 확인과 승인 사이에 만료될 수 있다 — 재검증은 여전히 필요하다.

## 결정 10 — 결제 시한은 전역, 승인 시한은 채널별

두 값의 성질이 다르다.

| | 누가 정하는가 | 어디에 |
|---|---|---|
| 결제 시한 | **우리** — 카드 정보를 넣는 데 걸리는 시간에 대한 UX 판단 | 전역 설정 |
| 승인 시한 | **밖** — 채널 계약이 규정한다 | 채널별 |

승인 시한을 전역 상수로 두면 "이 값이 채널 계약사항"이라는 사실이 모델에서 사라지고,
나중에 채널별로 바꿀 때 시한을 읽는 모든 자리를 함께 바꿔야 한다.

결정 7 의 교차 테이블이 생기는 시점에 **승인 시한이 그 테이블에 자연히 합쳐진다.**
지금 채널 속성으로 두면 그때 컬럼 하나가 이동하는 것으로 끝난다.

## 상태 최종 목록 — 5개에서 9개로

```
제거   PENDING                  죽은 상태였다. HELD 와 PENDING_APPROVAL 로 쪼갠다
추가   HELD                     결제 대기. 선점 보유
추가   PENDING_APPROVAL         승인 대기. 선점 보유
추가   EXPIRED                  시한 초과로 종료
추가   REJECTED                 사장님이 거절
추가   TERMINATED               노쇼 (결정 8)
유지   CONFIRMED CHECKED_IN CHECKED_OUT CANCELED
```

`EXPIRED` 와 `REJECTED` 는 동작이 같다(선점 해제 + 승인 취소). 그래도 구분해 둔다 —
**거절률과 무응답률은 다른 지표**이고, 하나로 합치면 사후에 나눌 수 없다.

### 세 집합으로 갈린다

```
점유 (sold 에 반영)  = { CONFIRMED, CHECKED_IN, CHECKED_OUT, TERMINATED }
선점 (INV-4 로 계산) = { HELD, PENDING_APPROVAL }
어느 쪽도 아님       = { EXPIRED, REJECTED, CANCELED }
```

`EXPIRED` · `REJECTED` 는 **`sold` 에 한 번도 들어간 적이 없다.** `CANCELED` 는 들어갔다가 복원되었다.
결과는 같지만 경로가 다르므로 복원 알고리즘이 이 셋을 다르게 다룬다 —
`#26` 의 조건부 UPDATE 가 `WHERE status = 'CONFIRMED'` 인 이유가 여기 있다.

## 불변식과 테스트에 생기는 변화

`INV-4` 하나가 늘고 `INV-1` ~ `INV-3` 은 그대로다. `T1`~`T4` 도 그대로 유효하다.

`INV-4` 가 `INV-1` 의 상한을 함의한다. **다만 전제가 하나 필요하다** —
`SUM(유효 선점의 room_count)` 가 **음수가 아니어야** 한다.

`room_count` 가 `INT NOT NULL` 만이면 음수를 막지 못하고, 그러면
`sold + SUM(room_count) <= total` 이 통과하면서 `sold > total` 이 성립할 수 있다.
**함의가 깨진다.** 그래서 스키마에 `CHECK (room_count > 0)` 을 둔다 —
`reservation.room_count` 에도 같은 제약이 필요하다(`A7`).

그 전제 위에서도 둘 다 둔다. `INV-1` 은 하한 `0 <= sold` 도 담고 있고,
그 하한은 **복원이 두 번 일어났을 때 잡히는 유일한 등식**이다.

추가할 테스트는 `docs/03-testing-strategy.md` 의 `T7`~`T10` 이다.
`T8` 이 결정 3 의 증명이고, `T10` 이 결정 9 의 증명이며,
`INV-4` 의 `released_at IS NULL` 을 지우면 `T9` 가 실패해야 한다.

## 기각한 대안 — 선점을 어디서 세는가

이 ADR 의 존재 이유다. `sold` 에 선점을 포함시키는 선택지가 실재했고 변경량은 그쪽이 더 작다.

### 대안 1: `sold` 에 포함한다

선점도 판매로 간주해 `sold` 를 올린다. 불변식 구조와 차감 알고리즘을 그대로 재사용한다.

기각 이유는 **`sold` 가 두 가지를 뜻하게 된다**는 것이다.
확정 판매와 선점이 한 숫자에 섞이면 전환율·만료율을 뽑을 수 없고,
`INV-2` 의 점유 상태 집합에 `HELD` 를 넣어야 해서 `#25` 의 결정까지 함께 바뀐다.
그리고 만료 청소를 놓치면 그대로 재고 누수다.

### 대안 2: `daily_inventory` 에 `held` 컬럼을 분리한다

`INV-1` 이 `0 <= sold + held <= total` 로 개정된다. 단일 행에서 모든 검증이 끝난다.

기각 이유는 **만료 시 `held` 를 감소시켜야 한다**는 것이다.
그 감소를 누군가 실행해야 하므로 스케줄러가 정합성 경로에 들어오고,
**스케줄러가 죽으면 재고가 영구히 잠긴다.** 결정 2 가 없애려던 것이 정확히 이것이다.
차감·복원 경로도 4개(선점 잡기/풀기, 확정/복원)로 늘어난다.

### 대안 3: 승인형을 범위 밖으로 둔다

`PENDING` 을 제거하고 즉시확정만 다룬다. `#28` 의 원래 제안이다.

기각 이유는 **`02-scope.md` 의 절단 기준을 적용해도 남는다**는 것이다.
승인형에서 재고는 확정 없이 잡혀 있어야 하고, 그 상태를 표현할 자리가 없으면
현장은 확정으로 밀어넣거나 재고를 손으로 잡는다.
결정 8 에서 노쇼를 범위 안으로 들인 것과 같은 논거다 —
**범위 밖 설정이 상황을 없애지 못하면 우회 경로를 만든다.**

## 재검토 조건

1. **예약 없이 선점만 하는 경로가 생긴다**(장바구니·검색 결과 홀드) — `reservation_id` 가
   묶는 키를 겸할 수 없게 되므로 별도 그룹 키를 도입한다. 결정 1 의 스키마만 바뀌고 불변식은 그대로다
2. **승인 취소 스케줄러의 지연이 문제가 된다** — 결정 6 의 "정합성 책임 없음"은 유지되지만
   고객 카드에 승인이 걸린 시간이 길어진다. 그때는 발행 주기를 줄이거나 결정 5 의 범위를 넓힌다
3. **`EXPIRED` 와 `REJECTED` 의 지표 차이가 쓰이지 않는다** — 합쳐서 상태를 하나 줄인다
4. **조기 퇴실을 들여야 한다** — `INV-2` 가 예약당 유효 날짜 범위를 요구하게 되므로
   `#25` 의 판정 기준부터 다시 본다
