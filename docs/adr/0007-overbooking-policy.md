# ADR-0007. 의도적 오버부킹과 사고성 오버부킹을 구분합니다

## 상태

확정

## 맥락

`INV-1` 이 **모든** 초과 판매를 물리적으로 불가능하게 만듭니다.

```
0 <= sold <= total          total = 물리 객실 수
```

방이 10개면 11번째 예약은 구조적으로 거부됩니다. 이것이 이 저장소의 주장이었습니다.
그런데 업계에서 오버부킹은 두 종류로 갈리고, **이 불변식은 둘을 구분하지 않습니다.**

| | 성격 | 현실 |
|---|---|---|
| **의도적** 오버부킹 | 수익관리 **전략** | 노쇼가 하루 5~15% 이며, 안 팔면 그대로 소멸합니다 |
| **사고성** 오버부킹 | 시스템 **실패** | 동기화 오류·중복 수신·수기 실수. 이 저장소가 다루는 것 |

숙박 재고는 **소멸성 자산**입니다. 오늘 팔지 못한 방은 내일 팔 수 없고 그 손실은 회수되지 않습니다.
초과 판매를 구조적으로 금지하는 시스템은 **실무에서 거부당합니다.**

### 거부당하는 것보다 나쁜 결과가 있습니다

사장님이 "왜 우리가 팔겠다고 한 걸 못 팔게 하냐"고 묻는데 답이 "정합성 때문입니다"이면,
**현장은 우회 경로를 만듭니다.** 채널 화면에서 직접 재고를 올리거나 유령 룸타입을 등록합니다.

그 순간 `ADR-0009` 가 세운 **"재고 수량의 원본은 우리"** 라는 전제가 깨집니다.
즉 이 결정을 미루면 **다른 ADR 의 전제가 현장에서 무너집니다.**

## 결정

**불변식을 약화시키지 않습니다. `total` 의 의미를 재정의합니다.**

```
total = physical_total + overbooking_limit
```

| 컬럼 | 뜻 | 핵심 |
|---|---|---|
| `physical_total` | 물리 객실 수 | 거의 안 바뀝니다 |
| `overbooking_limit` | 정책이 허용한 초과 한도 | **기본값 0** |
| `sold` | 확정 판매 수량 | 변경 없음 |

`total` 은 **컬럼이 아니라 계산값**이 됩니다.

### 두 값을 모두 들고 있습니다

`total` 하나만 12로 적어 두는 쪽이 더 짧습니다. 그렇게 하지 않은 이유는 셋입니다.

- **오버부킹이 실제로 몇 건 발생했는지 셀 수 없습니다.** `B5` 의 `overbooking_prevented_total` 은
  물리 수를 기준선으로 삼아야 의미가 있습니다
- **`sold = 11` 이 정상인지 사고인지 구분할 수 없습니다.** 프런트에 "실제로 방이 부족합니다"를 알릴 근거가 없습니다
- **한도를 0 으로 되돌릴 때 돌아갈 값이 없습니다**

### 기본값 0 이 이 결정의 비용을 0 으로 만듭니다

`overbooking_limit = 0` 이면 `total == physical_total` 이므로 **현재 동작과 수학적으로 동일합니다.**
마이그레이션도, 테스트 기대값 변경도, 알고리즘 변경도 없습니다.

**지금 정하는 것은 값이 아니라 뜻입니다.**

## 무엇이 바뀌지 않는가

이 결정에서 가장 중요한 귀결입니다.

```
INV-1  0 <= sold <= total          문자 그대로 유지
INV-2  sold == SUM(점유 예약)       문자 그대로 유지
INV-3  check_in < check_out        유지
```

시스템은 여전히 **"정책이 허용한 선"을 한 칸도 넘지 않습니다.**
넘을 수 있는 것은 오직 **의도치 않은 초과**뿐이며, 그것이 이 저장소가 0 으로 만드는 대상입니다.

`T1`~`T4` 도 그대로 유효합니다. `T1`(동시 100건 → 성공 정확히 1건)은 `total = 1` 을 쓰므로
한도가 0 인 한 기대값이 변하지 않습니다.

## 왜 이것이 주장을 강하게 만드는가

> "오버부킹을 막았다"와 **"어떤 오버부킹을 막았는지 구분할 줄 안다"** 는 다른 주장입니다.

전자는 재고 카운터에 상한을 걸면 누구나 할 수 있습니다.
후자는 **정책과 사고를 같은 숫자 안에서 분리했다는 뜻**이고, 그것이 도메인을 이해했다는 증거입니다.

## 기각한 대안

### 대안 1: 불변식을 완화합니다 — `sold <= total * 1.1`

기각 이유가 셋입니다.

- **검사식에 정책이 섞입니다.** "지금 위반인가"를 알려면 계산을 해야 하고 반올림이 들어옵니다
- **정책이 바뀌면 과거 데이터의 위반 여부가 바뀝니다.** 검사식이 시간에 따라 달라지는 것은 불변식이 아닙니다
- 비율은 룸타입 1개짜리 숙소에서 무의미합니다. `1 * 1.1 = 1.1` 을 어떻게 읽어야 할까요

### 대안 2: 채널별로 초과를 허용합니다

`ADR-0009` 가 정한 축 분리를 깹니다. **채널별 차등은 정책 축이고 재고 축이 아닙니다.**
재고를 채널별로 쪼개면 원본이 여러 개가 되며, 이는 `ADR-0001` 이 allocated 를 기각한 논거와 같습니다.

### 대안 3: `total` 만 재정의하고 물리 수는 들고 있지 않습니다

변경량이 가장 작습니다(주석 한 줄). 기각 이유는 위 "두 값을 모두 들고 있습니다" 절과 같습니다 —
**지표·경고·되돌림 셋을 동시에 잃습니다.** 컬럼 하나를 아끼고 세 가지를 포기하는 거래입니다.

### 대안 4: 지금 정하지 않고 미룹니다

기각 이유는 **비용의 비대칭**입니다.

```
지금 정한다   문장 몇 개. 한도 0 이면 동작이 동일하다
나중에 정한다  total 을 읽는 모든 코드와 모든 테스트 기대값이 바뀐다
```

그리고 맥락 절에 적은 대로, 미루는 동안 현장이 우회 경로를 만들면 `ADR-0009` 의 전제가 깨집니다.

## 범위 밖

**한도를 운영하는 기능은 다루지 않습니다.**

- 수익관리 화면 (한도를 사람이 조정하는 UI)
- 노쇼율 예측 (한도를 자동 산정하는 로직)
- 오버부킹 발생 시 대체 객실 수배

이 결정은 **한도를 담을 자리와 그 의미**까지입니다. `02-scope.md` 의 절단 기준을 적용한 결과입니다 —
자리가 없으면 재고 정합성 주장이 애매해지지만, 운영 기능이 없어도 주장은 무너지지 않습니다.

## 재검토 조건

- 한도를 실제로 0 이 아닌 값으로 운영하게 되면 **오버부킹 발생 건수 지표**가 선행 조건이 됩니다.
  한도가 0 인 동안은 `sold > physical_total` 이 사고이므로 검출이 자명하지만,
  한도가 걸리면 "정책 범위 안의 초과"와 "사고"를 구분할 계산이 필요합니다
- 채널별로 다른 한도를 요구받으면 `ADR-0009` 의 정책 장부로 들어갑니다. 재고 축으로 끌어오지 않습니다
