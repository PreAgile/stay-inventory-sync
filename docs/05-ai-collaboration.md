# AI 협업 — 경계, 판단, 기록

## 원칙

AI를 **썼는가**는 정보가 아니다. 지금은 모두 쓴다.
정보는 **어디까지 위임했고, 무엇을 기각했으며, 왜 그렇게 판단했는가**에 있다.

이 문서는 그 기록이다.

---

## 위임 경계

### 위임하지 않은 것 (내가 결정)

| 영역 | 이유 |
|---|---|
| 문제 선정과 범위 절단 | 이것이 판단 그 자체다. 위임하면 남는 것이 없다 |
| 도메인 모델과 상태 전이 | 도메인 이해가 코드보다 선행한다 |
| 락 전략, 격리 수준 | 워크로드 가정에 대한 판단이 필요 |
| 정합성 보장 방식 | 시스템의 주장 그 자체 |
| 테스트가 **무엇을 증명해야 하는가** | 증명 대상 정의는 위임 불가 |
| 기각한 대안과 그 근거 | ADR의 본체 |

### 위임한 것

| 영역 | 검토 방식 |
|---|---|
| 도메인 사전조사, 외부 스펙 수집 | 원문 링크로 직접 확인 |
| 보일러플레이트, 설정 파일 | 실행으로 검증 |
| 테스트 픽스처, 더미 데이터 | 리뷰 |
| 테스트 **코드 작성** (시나리오는 내가 정의) | 의도한 실패를 유도해 검증 |
| 문서 초안, 표 정리 | 전면 수정 |

**테스트에 대한 위임 경계가 특히 중요하다.**
"무엇을 증명할 것인가"는 내가 정하고, "어떻게 코드로 표현할 것인가"만 위임했다.
그리고 각 테스트는 **의도적으로 로직을 깨뜨려 실패하는지 확인**했다.
통과하는 테스트는 아무것도 증명하지 않는다. 깨뜨렸을 때 실패해야 증명이다.

## 판단 기록

### [8/20] 재고 차감 락 전략

- **AI 제안**: 낙관적 락(`@Version`). 락 대기가 없어 처리량이 높다는 근거
- **판단**: 기각
- **근거**: Pooled inventory(ADR-0001)에서 인기 지점의 주말 날짜는 동일 행에
  경합이 집중된다. 고경합에서 낙관적 락은 재시도가 폭발한다.
  AI의 제안은 "일반적으로 처리량이 높다"는 맞는 명제였으나,
  **이 워크로드의 경합 특성을 반영하지 않았다.**
- **조건부 재검토**: 경합률이 실측으로 낮으면 낙관적이 우세. ADR-0002에 명시
- **소재**: ADR-0002

### [8/20] 도메인 사전조사

- **활용**: 오픈소스 PMS 및 채널매니저 공개 스펙 조사
- **확보**: Channex의 레이트 리밋(분당 20 ARI), 웹훅 재시도 스케줄,
  델타 동기화 원칙, PMS 인증 요구사항(큐/아웃박스 필수)
- **내 판단**:
  1. 기존 OSS(QloApps, miniCal 등)는 cron 폴링 기반이며 정합성 검증이 부재하다.
     → 이 지점을 본 프로젝트의 차별 축으로 결정
  2. 재시도 간격을 임의로 정하지 않고 Channex 실제 스케줄을 채택
  3. **진짜 병목은 내부가 아니라 외부 레이트 리밋**이라는 결론 도출 →
     부하 테스트 대신 용량 산정을 선택 (`04-capacity-and-limits.md`)
- **검증**: 모든 수치는 원문 문서에서 직접 확인. AI 요약을 그대로 신뢰하지 않음

### [8/20] 언어 선택 — Kotlin vs Java

- **초기 판단**: Java 21. 속도 우선
- **재검토 후**: Kotlin으로 확정
- **근거**: 대상 스택이 Kotlin이며, 이 프로젝트의 설계는 언어에 종속되지 않는다.
  Java를 선택할 이유가 "빠르다"뿐이었는데, 그것은 언어 기능을 넓게 쓸 때의 얘기다.
  **부분집합을 좁히면 속도 차이가 사라진다.**
- **결과**: 사용/미사용 기능 목록을 ADR-0005에 명시하고,
  리뷰 도구 설정에 금지 목록을 전달했다.
  "쓸 수 있다"와 "써야 한다"를 구분한 기록으로 남긴다.

### [8/20] Lincheck 적용 여부

- **검토**: 동시성 검증 도구로 Lincheck 사용 가능성
- **판단**: 적용 불가
- **근거**: Lincheck의 탐색 공간은 JVM 스레드 인터리빙이다.
  이 프로젝트의 동시성은 PostgreSQL의 행 수준 락과 MVCC에 있다.
  **검증 대상이 다르므로 적용해도 아무것도 증명하지 못한다.**
- **대안**: 실제 PostgreSQL 위 통합 테스트 (T1, T2)
- **소재**: ADR-0005, 03-testing-strategy.md

### [8/20] Kafka 도입 여부

- **초기 직관**: "규모가 커지면 결국 Kafka가 필요하지 않나"
- **검토 후 판단**: 도입 조건이 아직 성립하지 않음
- **근거**: Kafka는 팬아웃, 재생, 서비스 분리를 해결한다.
  **레이트 리밋은 해결하지 않는다.** 현재 병목은 후자다.
- **결과**: 기각이 아니라 **조건부 유예**. 도입 트리거 4개와 마이그레이션 경로,
  파티션 키까지 ADR-0004에 명시. 스키마도 Debezium 관례에 미리 맞춤

### [8/20] 채널 팬아웃 대상 — 내가 제기한 질문에서 나옴

- **경위**: 설계 흐름을 다시 훑던 중 "OTA에서 예약 요청이 들어와 우리 재고가
  차감되는 방향 아닌가"라고 물었다. 당시 보고 있던 자료가 아웃바운드(우리 → 채널)만
  그리고 있어 인바운드가 빠진 것처럼 읽혔고, 확인 결과 설계에는 두 방향이 다 있었다 —
  자료 쪽 누락이었다.
- **그런데** 두 방향을 나란히 놓자 별개의 공백이 드러났다.
  인바운드로 들어온 예약의 아웃바운드를 **어느 채널에** 보내는지가 정해져 있지 않다.
  유입 채널에도 다시 보내면 에코가 되고, 빼면 그 채널만 낡은 값을 갖는다.
- **AI 는 이 공백을 지적하지 않았다.** 순서 역전(PR #1)은 찾았지만 팬아웃 대상은
  놓쳤다. "예약이 들어오는 방향은 어떻게 되느냐"는 질문이 시야를 바꾸자 드러났다.
  **아웃바운드만 보고 있으면 보이지 않는 공백이었다.**
- **파생 발견**: 이 결정이 정해지지 않아 `04-capacity-and-limits.md`의 용량 산정에
  **채널 수 계수가 빠져 있다**. 채널 4곳 기준 실제 호출량은 유입 채널 제외 시 3배(`N-1`),
  전체 통지 시 4배(`N`) — 어느 쪽인지가 팬아웃 정책에 달려 있다.
  즉 팬아웃 규칙 없이는 레이트 리밋 산정 자체가 성립하지 않는다.
- **판단**: 지금 결정하지 않는다. 어댑터가 스텁이라 팬아웃에 따른 실제 호출량과
  어댑터 동작을 검증할 수 없고 Tier 0 가 완결되기 전이다.
  다만 **질문이 기록되어 있는 것과 없는 것은 다르다.**
  몰라서 안 한 것과 알고 미룬 것을 구분하기 위해 남긴다.
- **소재**: 이슈 #18

> 이 항목을 남기는 이유는 이 문서의 주장 그 자체다.
> AI 를 **썼는가**는 정보가 아니다. **어디까지 위임했고 무엇이 위임으로 덮이지 않았는가**가 정보다.
> 위 두 발견은 성격이 다르다 — 순서 역전은 조사로 나왔고, 팬아웃 공백은 질문으로 나왔다.

### [8/20] PR 리뷰 도구 — Gemini Code Assist 중단

- **경위**: Gemini Code Assist 의 무료 제공이 종료됐다. 유료 전환 여부를 결정해야 했다.
- **판단**: 중단. CodeRabbit 단독으로 간다.
- **근거**: 두 도구를 함께 쓴 이유는 관점 이중화였다. 그런데 지금까지의 변경은
  대부분 문서와 스캐폴딩이라 **두 리뷰가 엇갈린 사례가 아직 쌓이지 않았다.**
  이중화의 값을 실측하지 못한 상태에서 비용을 지불하는 것은 근거 없는 결정이다.
- **잃는 것과 메우는 방식**: 정확성·엣지 케이스 관점이 빠진다.
  다만 이 축은 원래 도구가 최종 방어선이 아니었다 — T1~T4 와 불변식 assertion
  (`03-testing-strategy.md`), ArchUnit 규칙이 담당한다.
  **읽고 지적하는 것보다 깨지면 실패하는 쪽이 강한 보증이다.**
- **조건부 재검토**: 도메인 로직이 들어찬 뒤 CodeRabbit 단독 리뷰가 놓친 결함이
  테스트에서 2건 이상 잡히면 유료 전환을 다시 검토한다. 기준 없이 되돌리지 않는다.
- **잔여 정리**: `AGENTS.md`, `.github/pull_request_template.md`, ADR-0005 의
  `.gemini/styleguide.md` 참조, `.gemini/` 설정이 아직 남아 있다. 별도 PR 로 정리한다.

## PR 리뷰 협업

이 저장소는 **CodeRabbit**을 PR 리뷰어로 사용한다.

처음에는 CodeRabbit 과 Gemini Code Assist 를 함께 썼다. **관점이 다르기 때문**이었다 —
CodeRabbit 은 변경 맥락과 코드 스멜에, Gemini 는 정확성과 엣지 케이스에 강했다.
두 리뷰가 같은 지점을 지적하면 신호가 강하고, 엇갈리면 내가 판단할 지점이었다.

**Gemini Code Assist 는 무료 제공이 종료되어 중단했다.** 판단 경위는 위 기록에 남겼다.
관점 이중화가 사라진 자리를 무엇이 대신하는지도 함께 적어 둔다.

### 리뷰 대응 원칙

봇 코멘트에 **반드시 답글로 판단을 남긴다.** 조용히 반영하거나 무시하지 않는다.

```
수용    → 수정 커밋 링크 + 왜 타당했는지 한 줄
기각    → 근거 명시. 도메인 제약인지, 범위 밖인지, 오탐인지
보류    → 백로그 항목으로 전환하고 이슈 링크
```

**PR 스레드 자체가 AI 협업의 증거다.**
이 문서에 요약을 옮겨 적는 것보다, 실제 판단이 일어난 현장이 더 강한 증거다.

## 이 프로젝트에서 AI가 만든 코드의 버그

> 실제로 발견되는 대로 기록. 예상되는 유형:
> - 락 획득 전 정렬 누락
> - `@Transactional` 경계 오류 (Outbox 삽입이 별도 트랜잭션)
> - 체크아웃 당일을 재고 차감 대상에 포함
> - 중복 웹훅에 4xx 반환 (재시도 유발)
> - JPA 엔티티를 `data class`로 선언
> - `when`에 불필요한 `else`를 붙여 sealed 망라성 검사 무력화
> - `!!` 사용으로 null 안전성 우회
