# 미확인 항목 — 연동 대상이 정해진 뒤에 확인한다

**지금 확인할 문서가 아니다.**

`docs/07-reconciliation.md` 의 설계는 특정 채널매니저에 의존하지 않는다.
이 문서는 **실제로 연동을 붙이는 시점**에 상대가 무엇을 주는지 확인할 목록이며,
Channex 를 예로 삼는다 — 공개 문서가 있어 무엇이 미확인인지 특정할 수 있기 때문이다.

세 항목은 **보장형 하이브리드(ADR-0001)의 성립 여부**를 가른다.
`ADR-0001` 이 보장형을 조건부 유예로 두었으므로, 확인도 미룬다.

문서에 없는 것을 추측으로 채우고 설계하면, 설계가 아니라 가정이 된다.
**미룬다는 것은 추측으로 채운다는 뜻이 아니다.**

---

## 이 문서에 측정 절차를 적지 않는 이유

초안에는 절차(호출 횟수·엔드포인트·순서)와 실행 스크립트가 있었다. **둘 다 뺐다.**

절차를 쓰려면 엔드포인트 경로와 파라미터를 확정해야 하는데, 그 값들이 공개 문서에서
확인되지 않았다. 즉 **미확인을 확인하러 가는 절차가 미확인을 포함하고 있었다.**
스크립트에도 `공개 문서 미검증` 이라는 주석이 그대로 남아 있었다.

그리고 실행 조건(계정·API 키·프로퍼티 ID)이 저장소 밖에 있어 **저장소를 클론한 누구도
실행할 수 없었다.** 돌려볼 수 없는 코드는 고쳐도 고쳤음을 증명할 수 없다.

`02-scope.md` 가 실제 OTA 연동을 기각한 논거가 그대로 적용된다 —
*공개 스펙을 모방한 스텁이 검증 목적에는 오히려 우월하다.*
그리고 연동 시점이 오면 확인은 bash 프로브가 아니라 **어댑터와 통합 테스트**로 한다.

**그래서 이 문서가 남기는 것은 하나다 — 무엇이 미확인이고, 답에 따라 설계가 어떻게 갈리는가.**
어떻게 측정할지는 상대 문서를 다시 읽는 그 시점에 정한다.

---

## 확인된 것

설계가 실제로 기대고 있는 사실들이다. 출처는 문서 끝에 있다.

| 확인됨 | 근거 |
|---|---|
| availability 는 룸타입 단위 절대값이며 채널별 값을 받지 않는다 | ARI 문서 |
| 채널별 차등은 `close_out` / `availability_offset` / `max_availability` 규칙만 | Availability Rules 문서 |
| 프로퍼티당 분당 availability 10회, restrictions·price 10회 | Rate Limits 문서 |
| 예약 feed 는 확인하지 않은 리비전만 반환하며 확인 후 사라진다 | Bookings 문서 |
| 웹훅 payload 에 변경 주체 식별자가 있고 자기 변경 무시 용도다 | Webhook 문서 |
| 웹훅 호출 순서는 이벤트 발생 순서와 다를 수 있다 | Webhook 문서 |

## U1. 읽기와 규칙 갱신이 쓰기 예산을 잠식하는가

리밋 문서는 `Availability Requests` 라고만 적고 어느 엔드포인트가 포함되는지 열거하지 않는다.

| 경우 | 함의 |
|---|---|
| 읽기가 리밋 밖 | drift 검출 주기를 자유롭게 정할 수 있다 |
| 읽기가 쓰기 예산을 공유 | **읽기 1회당 쓰기 1회를 잃는다.** 주기 산정에 읽기를 넣어야 한다 |
| 읽기에 별도 리밋 | 별도 예산으로 관리 |

규칙 생성·수정이 같은 예산을 쓰는지도 함께 미확인이다.
공유한다면 **보장형의 배정 갱신 빈도가 곧바로 제약된다.**

```
확인 결과가 "잠식하지 않는다"  →  현재 예산 표 유지
확인 결과가 "잠식한다"         →  04-capacity-and-limits.md 의 예산 표를 개정하고
                                 drift 검출 주기와 배정 갱신 빈도를 쓰기 예산에서 차감한다
```

## U2. 규칙이 여러 개 걸릴 때 어떻게 되는가

보장형 하이브리드는 배정 채널 외의 채널에 `availability_offset` 을 건다.
동시에 취소율 높은 채널에는 `max_availability` 캡을 걸고 싶다.
같은 (룸타입, 채널) 에 두 규칙이 걸리면 어떻게 되는가.

```
전체 10,  offset 2,  max 5   →  8 인가, 5 인가, min(8,5)=5 인가
                              →  아니면 애초에 거부되는가
```

### 관찰의 한계를 미리 적어 둔다

**실제 채널에 무엇이 보이는지는 상대 staging 에서 완전히 관측되지 않는다.**
실제 OTA 연결 없이는 최종 노출값을 볼 수 없다.

따라서 1차로 답할 수 있는 것은 **"두 규칙이 공존 가능한가"** 까지다.
공존이 되더라도 우선순위는 상대에게 문의해 문서화한다 — **추측하지 않는다.**

```
공존 불가  →  캡형과 보장형은 상호 배타다. ADR-0001 에 명시한다
공존 가능  →  우선순위가 확인되기 전까지 보장형을 착수하지 않는다
```

## U3. 규칙의 날짜 단위와 갱신 비용

규칙의 범위는 시작일·종료일·요일이다. 그런데 **배정 잔여는 날짜마다 다르다.**

```
9/01  배정 3 중 1 판매  →  offset 2
9/02  배정 3 중 3 판매  →  offset 0
9/03  배정 3 중 0 판매  →  offset 3
```

날짜별로 값이 다르면 규칙이 날짜마다 하나씩 필요한가. 그리고 값이 같은 연속 구간을
병합하면 규칙 수가 실제로 줄어드는가. 갱신이 부분 수정인지 삭제 후 재생성인지도 미확인이다.

```
날짜당 규칙 1개가 필요하고 갱신이 리밋을 소비한다면
  →  보장형은 "배정 기간을 짧게, 배정 채널을 하나로" 제한하지 않으면 성립하지 않는다
  →  이 제약을 ADR-0001 의 보장형 절에 명시한다
```
