# 장애와 회복 — 무엇을 방어하고, 무엇을 못 막고, 그때 누가 무엇을 하나

이 문서는 **실패를 종류별로 갈라** 각각의 방어와 회복 경로를 적는다.
그리고 **막지 못하는 것을 같은 무게로 적는다.** 막는 것만 적으면 이 문서는 자랑이 되고,
자랑은 사고가 났을 때 아무 도움이 되지 않는다.

기준은 하나다 — **실패가 시끄러운가 조용한가.**
시끄러운 실패는 재시도와 알림으로 처리한다. 조용한 실패는 구조로 막거나,
막을 수 없으면 **검출 장치를 둔다.**

## 1. 예약 요청이 애매하게 끝났다

가장 다루기 어려운 실패다. **실패한 것이 아니라 결과를 모르는 것**이기 때문이다.

```
클라이언트 ──POST /reservations──▶ 우리
                                   예약 생성 · 재고 차감 · 커밋
           ◀──────X 응답 유실       (네트워크 끊김 / 타임아웃)
클라이언트: 예약이 됐나? 안 됐나?
```

재시도할 수밖에 없다. 그때 무슨 일이 생기는가가 이 절의 전부다.

### 무엇이 잘못돼 있었나

**서버가 멱등 키를 만들고 있었다.**

```kotlin
channelReservationId = request.channelReservationId ?: UUID.randomUUID().toString()
```

요청마다 새 키가 생기므로 **재시도가 서로 다른 두 요청으로 보인다.**
`UNIQUE (channel, channel_reservation_id)` 는 살아 있는데 **판정 대상이 사라졌다.**

이 UUID 는 원래 반대 목적으로 들어왔다 — *"NULL 을 허용하면 `UNIQUE` 가 직접
예약을 막지 못한다."* `NULL` 을 없앤 판단은 맞았지만, 키를 서버가 만들면
그 제약이 재시도를 식별할 수 없다.

그리고 키를 **주는** 경우에도 중복은 `500` 이었다. 재고는 지켜지고 **계약이
지켜지지 않았다** — 채널은 `500` 을 실패로 보고 계속 재시도한다.

### 어떻게 고쳤나 (ADR-0014)

> **멱등은 서버가 혼자 만들 수 없다.** "같은 요청" 을 정의하는 것은 호출부다.

| 경로 | 키 |
|---|---|
| 채널 예약 | `channelReservationId` |
| 직접 예약 | **`Idempotency-Key` 헤더** |

**둘 다 없으면 `400` 이다.** 서버가 대신 만들지 않는다.

중복은 `409` 가 아니라 **`200` 이고 기존 예약을 돌려준다.** 재시도한 호출부가
알고 싶은 것은 "실패했나" 가 아니라 **"내 예약이 어떻게 됐나"** 이다.
취소가 이미 그 형태다.

판정은 **웹훅 경로와 같은 2단**이다.

| 층 | 무엇 | 막는 것 |
|---|---|---|
| 조기 조회 | `findByChannelAndChannelReservationId` | 흔한 재시도 |
| `UNIQUE` 위반 포착 | `DataIntegrityViolationException` | 경합으로 조기 조회가 뚫린 경우 |

**두 번째를 트랜잭션 밖에서 잡는다.** 서비스 안에서 잡으면 그 트랜잭션은 이미
rollback-only 로 표시돼 있어 커밋 시점에 다시 터진다 — Inbox 가 같은 이유로
`@Transactional` 을 안 붙인다.

### 남은 것 — 서버가 할 수 있는 것은 여기까지다

**호출부가 재시도할 때 같은 키를 보내야 한다.** 우리 프론트엔드도 호출부이고,
그쪽이 매번 새 키를 만들면 이 방어는 아무것도 막지 못한다.
서버가 할 수 있는 것은 **키가 없을 때 거부하는 것**까지다.

**직접 예약 경로에 이 셋이 없는 것이 비대칭이고, 그 비대칭이 이 문서를 쓰게 만든 이유다.**

## 2. 저장은 됐는데 통보가 안 나갔다 (또는 반대)

dual-write 다. 순서를 바꿔도 해결되지 않는다 — 두 시스템이 서로의 커밋을 모른다.

```
① DB 커밋 → 채널 통보    DB 만 성공하고 죽으면  → 채널은 방이 있다고 믿고 판다 (유실)
② 채널 통보 → DB 커밋    통보만 성공하고 죽으면 → 있는 방을 못 판다 (유령)
```

**Outbox 가 이것을 하나의 트랜잭션으로 접는다.** 재고 차감·예약 생성·`outbox_event` INSERT
가 같은 커밋 안에 있다. 통보는 "보냈다" 가 아니라 **"보내야 한다는 사실"** 로 저장되고,
그 사실은 DB 트랜잭션의 원자성을 그대로 물려받는다.

발행은 릴레이가 따로 한다. 그래서 남는 창이 하나 있다.

```
릴레이: 채널 호출 성공 ──▶ PUBLISHED 마킹 ──X 실패
        → 같은 이벤트가 다시 발행된다 (at-least-once)
```

**이 창은 닫지 않는다. 닫으려면 다시 2PC 가 필요하다.**
대신 중복을 흡수한다 — 멱등키로 `outbox_event.id` 를 채널에 넘기고,
채널이 그것으로 두 번째를 흡수한다.

그리고 **중복보다 나쁜 것이 순서 역전**이다. 재발행이 최신 값을 낡은 값으로 덮어쓰면
멱등으로 흡수되지 않는다. 그래서 키 단위 버전 스탬프(ADR-0012)가 낡은 발행을 건너뛰고,
그것도 놓치는 경우를 §4 의 재동기화가 수렴시킨다 — **키셋 커서로 전 구간을 덮는다**(`#71`).

## 3. 외부 채널이 죽었다

**실패를 한 덩어리로 다루지 않는 것이 이 절의 핵심이다.**
`ChannelSyncResult` 가 네 갈래이고, 릴레이가 각각을 다르게 처리한다.

| 갈래 | 무엇 | 다음 시도 | `retry_count` | DEAD |
|---|---|---|---|---|
| `Success` | 성공 (채널이 흡수한 경우 포함) | — | — | — |
| `RateLimited` | 429 | `max(retryAfter, 60초)` | **안 올린다** | **절대 안 간다** |
| `Retryable` | 5xx · 타임아웃 · 연결 실패 | 1/2/4/8/15/30분 | +1 | `> 5` 회 |
| `Permanent` | 4xx (429 제외) | — | 안 올린다 | **즉시** |

### `RateLimited` 에서 `retry_count` 를 올리지 않는 이유

```
올리면: 리밋이 오래 걸린 채널의 정상 이벤트가 다섯 번 만에 DEAD 로 떨어진다
       → 사장님이 예약을 많이 받았다는 이유로 통보가 죽는다
```

**소진 판정은 "몇 번 실패했는가" 이지 "몇 번 미뤘는가" 가 아니다.**
이 구분이 없던 시절의 결함이 README 「부딪힌 것」 4번이다 —
아무도 안 읽던 `retry_count` 한 줄이 DLQ 를 얹는 순간 정상 이벤트를 죽이는 경로가 됐다.

### `retry_count` 는 시도 횟수가 아니다 — 소진 예산이다

이 필드의 의미를 정확히 적어야 한다. **`retry_count` 는 "재시도 가능한 실패를
몇 번 썼는가" 이고, "몇 번 시도했는가" 가 아니다.**

| 갈래 | 올리나 | 그래서 |
|---|---|---|
| `Retryable` | 예 | 예산을 쓴다. 5 를 넘으면 소진 |
| `RateLimited` | 아니오 | 실패가 아니라 미룸이다 |
| `Permanent` | 아니오 | **한 번 시도했는데 값은 0 으로 남는다** |

**세 번째 줄이 함정이다.** 4xx 로 즉시 DEAD 가 된 이벤트는 `/ops/outbox/dead` 에서
실패 횟수 0 으로 보인다. 한 번 시도해서 거부당했는데 0 이다.

이것을 버그로 보지 않는 이유는 필드의 정의가 **예산**이기 때문이다 —
`Permanent` 는 예산을 쓸 이유가 없다(재시도해도 같다). 다만 **정의를 적어 두지 않으면
운영자가 이 0 을 "시도조차 안 했다" 로 읽는다.** 실제 시도 횟수가 필요하면
`inbound_message` 처럼 `attempt_count` 를 따로 두어야 한다.

반대로 **소진으로 DEAD 가 될 때는 마지막 실패를 센다.** `status` 만 바꾸면
행은 DEAD 인데 `retry_count` 는 5 로 남아, *"`retry_count > 5` 면 DEAD"* 라는 계약과
운영 화면이 어긋난다.

### 어댑터가 예외를 던지면

`runCatching` 이 `Retryable` 로 흡수한다. **어댑터 버그가 이벤트를 영구 소실시키지 않는다.**

### 임계값 — 무엇을 넘으면 사람을 부르나 (`#68`)

지표만 있고 판정 기준이 없었다. **운영자가 숫자를 보고 그것이 정상인지 알 수 없다.**

값의 근거는 두 가지다 — **채널 레이트 리밋**(분당 20건)과 **예약 리드타임**.

| 지표 | 주의 | 호출 | 근거 |
|---|---|---|---|
| `outboxBacklog.dead` | ≥ 1 | ≥ 1 | **DEAD 는 자동 회복 경로가 없다.** 하나라도 사람이 봐야 한다 |
| `oldestPendingAgeSeconds` · **당일·익일** | 300 (5분) | 900 (15분) | 그 방은 지금 팔리고 있다. 15분이면 이미 잘못된 값으로 팔렸다 |
| `oldestPendingAgeSeconds` · **그 이후** | 3600 | 21600 (6시간) | 하루 안에 고쳐지면 손해가 없다 |
| `outboxPublishLag.p95` | 60 | 300 | 분당 20건 리밋에서 정상 큐는 1분 안에 빠진다 |
| `overbookingPrevented` 증가 | 시간당 ≥ 10 | 시간당 ≥ 50 | 차단이 늘면 **재고가 실제로 부족하거나 채널이 낡은 값을 들고 있다** |

**두 번째·세 번째 줄이 이 표의 핵심이다.** 같은 지연이라도 **오늘 밤 재고와
6개월 뒤 재고의 허용치가 다르다** — 같은 숫자로 판정하면 둘 중 하나가 틀린다.

지금 `oldestPendingAgeSeconds` 는 날짜를 구분하지 않으므로 **이 구분을 쓰려면
지표를 날짜 구간별로 쪼개야 한다.** 그것은 남긴다 — **값을 정해 두면 무엇을
쪼개야 하는지가 드러난다.**

`overbookingPrevented` 는 **절대값이 아니라 증가율**로 본다. 인메모리 카운터라
재기동 시 0 이 되므로 절대값은 의미가 없고 `since` 와 함께 읽어야 한다.

> **노출 형태는 정하지 않았다.** `/ops/metrics` 응답에 `status` 필드를 넣는 방법과
> 대시보드에서 판정하는 방법이 있는데 **관측 인프라가 붙는 시점의 모양에 달렸다.**
> 값과 근거를 먼저 정해 두면 그때 옮기기만 하면 된다.

### 헬스체크 (`#69`)

actuator 의존성도 `management:` 설정도 없었다. **다중 인스턴스를 논하면서
인스턴스가 살아 있는지 판정할 수단이 없었다.**

| | 무엇을 보나 | 왜 |
|---|---|---|
| `/actuator/health/liveness` | 프로세스만 | **DB 를 보면 안 된다** — DB 장애로 오케스트레이터가 살아 있는 프로세스를 죽여 회복을 방해한다 |
| `/actuator/health/readiness` | **DB 커넥션** | 200 만 돌려주면 커넥션을 못 잡는 인스턴스가 트래픽을 받는다 |

`health` 외 엔드포인트는 열지 않는다 — `env`·`beans` 는 운영 정보를 노출하고
지표는 `/ops/metrics` 가 낸다.

**스케줄러가 조용히 죽는 경우는 직접 신호가 없다.** `@Scheduled` 가 예외로 죽으면
프로세스는 살아 있고 통보만 멈춘다. `oldestPendingAgeSeconds` 임계값이 그 역할을
겸하지만 간접이다 — 직접 신호는 남긴다.

### `/ops` 인증 (`#74`)

`/ops` 하위 전체를 정적 API 키로 막는다. **패턴으로 막으므로 엔드포인트가 늘 때
자동으로 적용된다** — 목록으로 막으면 새 경로를 추가하는 것을 잊는다.

범위 밖 결정(`docs/02-scope.md`)을 뒤집는 것이 아니라 **"붙을 위치" 를 실제로
붙인 것**이다. 그 결정을 내릴 때의 `/ops` 는 읽기와 단일 행 갱신뿐이었고,
**한 번에 500건을 외부로 보내는 경로가 들어오면서 전제가 바뀌었다.**

키가 비어 있으면 **애플리케이션이 뜨지 않는다.** "설정을 잊으면 인증이 꺼진다" 는
형태를 만들지 않는다 — 꺼진 것을 아무도 모른다.

**도메인 경로(`/reservations`·`/webhooks`)는 막지 않는다.** 채널이 부르는 경로에
키를 요구하면 파트너 계약이 바뀐다.

### 아직 비어 있는 것

**HTTP 타임아웃 값이 정해져 있지 않다.** 어댑터가 스텁이라 connect/read 타임아웃이
코드에 없다. 그런데 릴레이의 임대(1분)는 *"채널 호출 타임아웃보다 넉넉하게"* 잡은
값이므로, **기준이 되는 숫자가 없는 상태에서 파생된 값**이다. 실제 어댑터가 붙을 때
둘을 같이 정해야 한다.

## 4. 채널과 숫자가 어긋났다

어긋남은 방어의 실패가 아니라 **정상적으로 일어나는 일**이다. 세 원인이 있고
대응이 서로 다르다(`07-reconciliation.md`).

수렴 장치가 둘인데 **방향이 반대다.**

| | 하는 일 | 자동 보정 |
|---|---|---|
| **정기 재동기화** | 비교하지 않는다. 절대값을 **밀어넣는다** | 한다 |
| **diff 리포트** | 밀어넣지 않는다. **대조만** 한다 | 안 한다 |

### 재동기화가 비교하지 않는 이유

비교하려면 채널 값을 읽어야 하고, 읽는 시점과 쓰는 시점 사이에 또 창이 생긴다.
**절대값을 그냥 밀어넣으면 그 창이 없다.** 그래서 스냅샷은 멱등키를 받지 않는다 —
받으면 두 번째 재동기화가 흡수되어 아무 일도 하지 않고, **그 사실이 조용하다.**

실패해도 재시도하지 않는다. 다음 주기가 같은 값을 다시 보낸다.

#### 한 바퀴로 전 구간을 덮는다 — 처음 판은 그러지 못했다

처음 판에는 **커서가 없었다.** 매 주기 같은 앞 500건을 읽었고, 격자가 상한을 넘으면
501번째부터는 영원히 선택되지 않았다. 격자는 (룸타입 × 날짜)이므로
**룸타입 10개 × 60일이면 이미 600** 이다. 그리고 로그가
*"남은 구간은 다음 주기가 처리한다"* 고 **사실과 다르게** 말하고 있었다.

> **최종 방어선이 부분만 덮는다는 것을 몰랐다.** 이 문서의 첫 판이 4번을 "완결" 로
> 적었고 리뷰가 반증했다. **방어선을 만든 사람이 그 방어선의 범위를 확인하지 않은 것이다.**
> 이 문단을 지우지 않는 이유는 그 사실이 판정보다 중요하기 때문이다.

`#71` 로 고쳤다. **키셋 커서**를 `resync_cursor` 에 두고 이전 주기가 멈춘 지점
뒤부터 읽는다. 구간 끝에 닿으면 커서를 처음으로 되돌린다.

```
격자 N · 상한 L  →  ceil(N / L) 주기에 한 바퀴
```

**`OFFSET` 을 쓰지 않는다.** 격자가 자라므로 앞에 행이 끼어들면 `OFFSET` 은 이미
보낸 것을 다시 보내거나 **안 보낸 것을 건너뛴다.**

그리고 **전송 실패도 진행으로 센다.** 실패한 건에서 멈추면 그 건이 영구히 막아
뒤쪽이 다시 굶는다 — `#71` 과 같은 형태의 실패가 다른 원인으로 재현된다.
실패는 다음 바퀴가 다시 시도한다.

**보고를 셋으로 나눴다.** `hasMore`(아직 남았다) · `cycleCompleted`(한 바퀴 끝) ·
`skipped`(임대를 못 잡아 돌지 않았다). **"돌지 않았다" 와 "돌았는데 보낼 것이
없었다" 를 구분하지 않으면 재동기화가 멈춘 것을 못 본다.**

### diff 가 자동 보정하지 않는 이유

원인 셋의 대응이 다르기 때문이다. 그리고 diff 는 `null` 과 `0` 을 구분한다 —
**`0` 은 "매진이라고 안다" 이고 `null` 은 "그 날짜를 아예 모른다"** 이며,
후자는 통보가 도달한 적이 없다는 뜻이다. `delta` 도 `null` 로 둔다.
같은 숫자로 뭉개면 "채널이 0 이라고 답했다" 와 "채널이 답을 안 했다" 가 같아진다.

### 조용한 누락을 어떻게 잡는가

가장 무서운 실패는 **응답이 `Success` 인데 채널에 반영되지 않은 경우**다.
재시도도, 알림도, 로그도 없다. 스텁이 이 상황을 주입할 수 있고
(`dropSilently`), diff 가 그것을 잡는 것을 테스트가 고정한다 —
*"어댑터가 조용히 누락한 날짜를 잡아낸다 — 실패도 예외도 없었다"*.

## 5. 인바운드 중복과 순서

§1 의 표에 적은 3중 방어가 여기 있다. **셋이 서로 다른 것을 막는다** — 겹치는 것이
아니라 각자의 구간이 있다.

### 순서는 완결이 아니다 — 정렬이 역전을 만든다

순서키를 주지 않는 채널은 **순서를 복원할 수 없다.** 이 사실은 숨기지 않고
어댑터별 제약으로 표시한다 — **복원할 수 없는 채널이 있다는 사실 자체가 설계
정보이고**, 그 채널은 drift 검출에 더 의존해야 한다.

**순서키를 주는 채널에도 문제가 있었다.** 정렬이 `sequence_key`(`VARCHAR`)를
그대로 써서 **문자열 정렬**이 됐다.

```
 sequence_key |  ev
--------------+------
 10           | 취소     ← 먼저 처리된다
 2            | 생성
```

취소가 먼저 `IGNORED` 된 뒤 생성이 확정되어 **최신 취소가 사라졌다.**
**순서 역전을 막으려는 정렬이 역전을 만들었다.** 코드 주석은 이 상황을 이미
예상했지만(*"순서가 뒤집혔다"*) 뒤집힘을 외부 요인으로만 보고
**정렬 자체가 원인이 될 수 있다는 것은 보지 못했다.**

`#72` 로 고쳤다(ADR-0013). **둘을 같이 고쳐야 했다.**

| 문제 | 고친 것 |
|---|---|
| 같은 배치 안의 역전 | 어댑터가 정규화한 `sequence_rank` 로 정렬 |
| **배치를 넘는 역전** | **묘비** — 더 높은 rank 의 취소가 있으면 낡은 생성을 막는다 |

정렬은 한 배치 안에서만 순서를 정한다. 취소와 생성이 다른 폴링 주기에 도착하면
정렬이 개입할 자리가 없고, 그때 늦게 온 생성이 예약을 확정한다.

**낡은 생성은 예약을 만들지 않는다.** 만들었다가 취소하면 그 사이에 다른 예약이
그 방을 볼 수 있고 `outbox_event` 가 두 번 나가 채널에 잘못된 중간 상태를 보낸다.

#### 고치다 더 심각한 것을 찾았다 — 취소가 유실되고 있었다

멱등 키가 `(channel, external_id, sequence_key)` 였다. **순서키를 주지 않는 채널에서
생성과 취소가 같은 키를 갖는다** — `NULLS NOT DISTINCT` 가 둘을 같은 알림으로 본다.

```
INSERT 생성 (CH, R-1, NULL)  -> 성공
INSERT 취소 (CH, R-1, NULL)  -> 중복으로 거부
```

**그리고 조용했다.** recorder 가 `Duplicate` 로 흡수해 `2xx` 를 주므로 채널은
전달됐다고 믿고 다시 보내지 않는다 — **취소가 영구히 유실된다.**

키에 `event_type` 을 넣어 같은 사건의 재전송만 중복으로 판정한다.
**넓히면서 멱등을 잃지 않았는지**를 테스트로 고정했다 — `#72` 를 고치고 `T3` 를
깨면 남는 것이 없다.

수신 실패는 `5xx` 로 답한다. **기록조차 실패하면 `2xx` 를 줄 수 없다** —
그때 `2xx` 를 주면 채널은 전달됐다고 믿고 다시 보내지 않으며, 그 알림은 사라진다.

## 6. DB 가 죽었다

### 지금 있는 것

```yaml
maximum-pool-size: 20
connection-init-sql: SET lock_timeout = '5s'
```

`lock_timeout` 이 세션에 걸려 있다. **무한 대기는 커넥션 풀을 고갈시킨다** —
한 요청이 영원히 기다리면 그 커넥션이 영원히 안 돌아오고, 그것이 20번 반복되면
서비스 전체가 멈춘다. JPA 의 `lock.timeout` 힌트는 PostgreSQL 에서 먹지 않으므로
세션 설정으로 내려간다.

### 데드락은 재시도하지 않는다 — 구조로 없앤다

락 순서를 `reservation → daily_inventory`, 날짜는 오름차순으로 고정한다(ADR-0011).
**순환이 만들어지지 않으면 데드락이 구조적으로 불가능하다.**

재시도 흡수는 명시적으로 기각했다 — *"고경합에서 재시도가 폭발하고 유효 처리량이
급락한다."* 그리고 데드락을 잡아 재시도하면 **락 순서가 틀렸다는 신호가 사라진다.**
테스트는 `40P01`(데드락)과 `55P03`(락 타임아웃)을 구분해 단언한다.
구분하지 않으면 *"순환"* 과 *"느렸다"* 를 같은 것으로 보고하게 된다.

### DB 가 완전히 죽으면

| 경로 | 무슨 일이 | 데이터를 잃는가 |
|---|---|---|
| 예약·취소 API | 500 | 아니오 — 쓰기가 시작되지 않았다 |
| **웹훅 수신** | **5xx** | **아니오 — 채널이 재시도한다** |
| 릴레이 | 집기 실패 → 다음 주기 | 아니오 — `PENDING` 이 남아 있다 |
| 재동기화 | 실패 → 다음 주기 | 아니오 |

**웹훅 행이 이 설계의 배당금이다.** Inbox 가 없으면 "받았는데 DB 가 죽어서 사라진"
알림이 생긴다. 있으면 DB 가 죽은 동안 우리가 할 일은 **정직하게 5xx 를 주는 것**뿐이고,
복구되면 채널이 다시 보낸다.

### 아직 비어 있는 것

~~`SQLException` → HTTP 매핑이 없다~~ — `#65` 로 닫았다.

전역 `@RestControllerAdvice` 하나로 모았다.

| 예외 | 응답 |
|---|---|
| `IllegalArgumentException` | `400` |
| 커넥션 획득 실패 · 트랜잭션 생성 실패 | `503` + `Retry-After: 5` |
| 락 타임아웃 | `503` + `Retry-After: 2` |

**`Retry-After` 를 함께 준다.** `503` 만 주면 호출부가 자기 백오프를 쓰고
그 값이 우리 회복 시간과 무관하다.

**데드락은 흡수하지 않는다.** 락 순서를 고정해 구조적으로 불가능하게 만들었고
(ADR-0011), 만약 온다면 그것은 **락 순서가 틀렸다는 신호**이므로 `500` 으로 남긴다.

그리고 컨트롤러마다 붙이던 구조가 실제로 구멍을 만들고 있었다 —
`InventoryDiffController` 의 `require(from < to)` 가 `400` 이 아니라 `500` 이었다.
**운영자가 날짜를 뒤집으면 잘못된 입력이 장애로 보고된다.**

## 7. 인스턴스가 늘었다

**같은 프로세스 안의 겹침**은 세 스케줄러 모두 `fixedDelay` 로 막는다.
`fixedRate` 는 이전 실행이 끝나지 않아도 다음을 시작한다.

**인스턴스 사이의 겹침**은 릴레이만 막는다.

| 스케줄러 | 방어 | 다중 인스턴스 |
|---|---|---|
| Outbox 릴레이 | **집기-임대 한 문장** | 안전 · 테스트로 증명 |
| 정기 재동기화 | **조건부 UPDATE 임대** (`#67`) | 안전 · 테스트로 증명 |
| Inbox 워커 | **집기-임대 CTE** (`#66`) | 안전 · 테스트로 증명 |

### 릴레이가 안전한 이유 — `SKIP LOCKED` 만으로는 부족했다

행 락은 트랜잭션이 끝나면 풀린다. **집기와 발행이 다른 트랜잭션이면 집자마자 락이
사라진다.** 그래서 집기와 임대를 한 문장으로 접었다.

```sql
UPDATE outbox_event SET next_attempt_at = now() + LEASE
 WHERE id IN (SELECT id FROM outbox_event
               WHERE status = 'PENDING' AND next_attempt_at <= now()
               ORDER BY id FOR UPDATE SKIP LOCKED LIMIT :n)
RETURNING ...
```

`next_attempt_at` 을 미래로 밀어 놓는 것이 임대다. 다른 인스턴스의 폴링 조건에서
빠지므로 락이 풀린 뒤에도 겹치지 않는다. 테스트는 인스턴스 2대 × 60이벤트에서
**어댑터 호출 횟수가 정확히 60** 인 것을 본다 — 결과가 아니라 **호출 횟수**를 세는
것이 핵심이다. 결과만 보면 멱등이 중복을 가려 준다.

### Inbox 워커 — 논증 없는 비대칭이었다

`findPending` 에는 `SKIP LOCKED` 도 임대도 없었다. 막는 것은 조기 반환과
`reservation` 의 `UNIQUE` 였고, **결과는 한 번만 반영되지만 한쪽 트랜잭션이
예외로 롤백된다** — 안전하지만 조용히 낭비했다.

`#66` 으로 닫았다. **낭비보다 나쁜 것은 릴레이와 다른 규율을 쓰는 것**이었다 —
다음 사람이 어느 쪽을 표준으로 볼지 알 수 없다.

**고치다 `#72` 를 되돌릴 뻔했다.** `UPDATE ... RETURNING` 은 **행 순서를 보장하지
않는다** — 안쪽 `ORDER BY` 는 어느 행을 집을지만 정한다. 첫 판이 `rank 10` 을
`rank 2` 보다 먼저 돌려줘 **고쳐 놓은 순서 역전이 되살아났고 테스트가 잡았다.**
CTE 로 감싸 바깥 `SELECT` 에 `ORDER BY` 를 다시 뒀다 — **정렬을 쿼리에 남긴다.**

### 재동기화 — 최종 방어선이 동시에 가장 큰 부하원이었다

처음 판에는 방어가 전혀 없었다. **인스턴스가 3대면 전량이 3번 나가고 레이트 리밋을
3배로 태운다.** 스냅샷은 멱등키를 일부러 받지 않으므로 채널도 흡수하지 못한다.

`#67` 로 고쳤다. 방식은 **릴레이와 같은 임대**다 — 트랜잭션 락으로 잡으면 외부 호출
동안 커넥션을 붙잡으므로, 조건부 UPDATE 로 `leased_until` 에 미래 시각을 심고 곧
커밋한다. 못 잡은 주기는 `skipped` 로 보고하며 **그것은 실패가 아니다.**

임대 길이는 **10분**이다. 릴레이(1분)보다 긴 이유는 한 주기의 전송량이 훨씬 크기
때문이다. 짧으면 아직 도는 인스턴스의 임대가 풀려 두 대가 겹치고, 길면 죽은
인스턴스가 남긴 임대만큼 재동기화가 멈춘다. **죽은 경우도 시각이 지나면 스스로 풀린다.**

> 같은 패턴을 두 곳에 쓴 것은 취향이 아니다. 이 저장소가 릴레이에서 이미
> *"`SKIP LOCKED` 만으로는 다중 인스턴스가 막히지 않는다"* 를 배웠고,
> **배운 것을 두 번째 자리에도 적용한 것**이다.

## 8. 사람이 개입해야 하는 순간

"확인 업무를 없앤다" 가 목표였으므로, **남은 개입은 예외여야 하고 그 예외에는
경로가 있어야 한다.**

| 신호 | 어디서 보는가 | 무엇을 누르는가 |
|---|---|---|
| DEAD 이벤트가 쌓인다 | `GET /ops/metrics` 의 `dead` | `GET /ops/outbox/dead` 로 원인 확인 → `POST /ops/outbox/{id}/retry` |
| 발행 지연이 길어진다 | `outboxPublishLag` 의 `p95` · `max` | 채널 상태 확인. 429 면 기다린다 |
| 통보가 아예 안 나간다 | `outboxBacklog.oldestPendingAgeSeconds` | 릴레이 생존 확인 |
| 채널과 숫자가 다르다 | `GET /ops/inventory-diff` | 원인 판정 → **`POST /ops/resync` 로 즉시 수렴** 또는 캡 조정 |
| 특정 채널만 과판매된다 | `overbookingPrevented` 증가 | `PUT /ops/channel-policy` 로 캡 조정 |

### 지표를 이렇게 낸 이유

**평균을 내지 않는다.** 재고 통보의 지연은 꼬리가 문제이고, 평균은 그 소수를 지운다.
그래서 `p50` · `p95` · `max` 를 함께 낸다.

**backlog 를 따로 낸다.** 발행된 것만으로 분포를 내면 **영원히 안 나가는 이벤트가
쌓일 때 분포가 오히려 좋아 보인다.** 나간 것의 지연과 못 나간 것의 개수는 다른 질문이다.

**`overbookingPrevented` 는 `since` 와 함께 낸다.** 인메모리 카운터라 재기동 시 0 이
되므로, `total` 만 읽으면 반드시 오해한다.

### 아직 비어 있는 것

- ~~재동기화 수동 트리거가 없다~~ — `POST /ops/resync` 로 추가했다(`#67`).
  **동시 클릭은 임대가 막고 뒤에 온 쪽이 `409`** 를 받는다. 조용히 성공을 돌려주면
  운영자는 두 번 돌았다고 믿는데 실제로는 한 번 돌았다.

"안 함" 과 "이 조건이면 함" 은 다르다.

### 이 목록에서 읽어야 할 것

**공백이 두 종류로 갈린다.**

- **판단이 이미 끝난 것** — 데드락 재시도, 직렬화 실패 처리, 토큰버킷은
  ADR 에서 **기각**했다. 없는 것이 아니라 안 하기로 한 것이다
- **아직 판단하지 않은 것** — 위 표가 그것이다

**둘을 섞으면 "빠뜨린 것" 과 "고른 것" 이 구분되지 않는다.** 그래서 나눠 적는다.
